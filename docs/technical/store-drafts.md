# 가게 등록·수정 임시저장

> 2026-09-11 `local-preview-all-changes` 구현 기준. 아직 배포되지 않은 로컬 프리뷰 계약이다.

## 결정

가게 등록과 수정은 모두 같은 임시저장 UX를 쓴다.

- 회색 보조 버튼은 `취소`가 아니라 **임시저장**이다.
- 입력·이미지 변경이 1초 동안 멈추면 브라우저에 자동 저장한다. 계속 입력하더라도 첫 변경 뒤
  최대 5초 안에는 한 번 저장해, 큰 이미지 Blob을 매 키 입력마다 다시 쓰지 않으면서 손실 구간도 제한한다.
- 다시 들어오면 저장 시각을 보여주고 **이어서 작성 / 새로 작성** 또는
  **이어서 작성 / 최신 정보 유지**를 고르게 한다.
- 새로 작성·최신 정보 유지를 고르면 오래된 초안을 삭제한다.
- 최종 등록·수정이 성공하면 해당 초안을 삭제한다.
- 편집 중 서버 원본이 바뀐 경우 fingerprint 차이를 감지해, 초안이 최신 값을 덮을 수 있음을 먼저 알린다.

수정 화면에도 임시저장이 필요하다. 등록만 보호하면 긴 운영시간·휴무일·소개·이미지 수정을 하다가
이탈한 사장님의 손실은 그대로 남는다. 두 화면은 `useStoreForm` 관문 하나를 공유한다.

## 저장 위치와 비용

`frontend/src/utils/storeDraftStorage.js`가 origin별 **IndexedDB**
`reserve-local-drafts/store-forms`에 저장한다. 키는 회원·모드·가게별로 분리한다.

```text
member:{memberId}:store:create:new
member:{memberId}:store:edit:{storeId}
```

폼 값은 dayjs를 문자열로 직렬화하고, 새 이미지는 브라우저 structured clone이 지원하는 `File/Blob`으로
보관한다. 만료는 30일이며 가게 폼 진입 때 다른 가게의 만료 초안까지 함께 정리한다.
키 입력마다 API·MySQL·S3 요청이 생기지 않고 최종 제출 때만 기존 multipart
요청 한 번을 보내므로 현재 규모에서 가장 싼 구조다.

브라우저 환경에서 사용자의 임의 폴더에 조용히 파일을 쓰는 것은 허용되지 않는다. File System Access API는
지원 범위가 좁고 매번 사용자 권한이 필요하므로 폼 초안에는 맞지 않는다. IndexedDB는 큰 Blob과 구조화 값을
브라우저가 관리하므로 localStorage보다 적합하다.

## 한계와 안전 경계

- 같은 기기·브라우저 프로필·origin에서만 이어진다. 다른 기기 동기화는 하지 않는다.
- 시크릿 모드, 사이트 데이터 삭제, 브라우저 저장공간 회수, quota 부족 때 사라질 수 있다.
- 로컬 초안은 서버의 정본이 아니다. 수정 화면의 서버 원본이 달라지면 사용자 확인 없이 합치지 않는다.
- IndexedDB도 XSS가 실행되면 읽힐 수 있다. 비밀번호·토큰·결제정보 같은 시크릿은 절대 넣지 않는다.
- 새 이미지까지 저장하므로 quota 오류를 사용자에게 보여주고 이미지 수·크기를 줄이도록 안내한다.
- `beforeunload`는 아직 로컬 저장이 끝나지 않은 변경이 있을 때만 브라우저 기본 이탈 경고를 요청한다.
  브라우저가 경고 표시를 보장하지 않으므로 `pagehide`와 컴포넌트 unmount에서도 마지막 저장을 시작한다.

## 언제 서버 초안으로 바꾸나

다음 요구가 실제로 생길 때만 별도 `store_draft` 도메인을 만든다.

1. PC에서 쓰던 내용을 휴대폰에서 이어야 한다.
2. 관리자와 사장님이 같은 초안을 공동 편집해야 한다.
3. 브라우저 데이터 삭제 뒤에도 복구해야 한다.

그때도 매 키 입력 DB write는 금지한다. 변경 병합 키·낙관적 버전·10초 안팎 debounce·명시적 저장·만료 배치를
함께 설계하고, 이미지는 초안 전용 S3 prefix와 만료 lifecycle을 쓴다. 현재는 그 운영비와 충돌 복잡도가
실제 사용자 가치보다 크므로 만들지 않는다.
