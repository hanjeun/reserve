# 광고 결제 시도 · 대사 · 환불

검증 기준: **2026-09-07 로컬 프리뷰 코드**. 운영 배포·운영 DDL·실제 PG 환불은 실행하지 않았다.
예약 결제와 공통 운영 이력은 [결제 런북](payments.md), 최신 실행 결과는 [품질 로드맵](quality-roadmap.md)을 따른다.

## 먼저 알아둘 것

- 광고 노출 상태와 돈의 상태는 다르다. `CANCELLED`는 노출 중단이지 미결제·환불 완료 증거가 아니다.
- 광고마다 현재 주문번호가 있고, 발급한 각 주문번호는 `ad_payment_attempt`에 보존한다.
- 환불 버튼은 **요청**이다. 취소 API의 응답만으로 완료 표시하지 않는다. PG 재조회에서 주문번호·KRW·원금·전체 취소액이 맞아야 `REFUNDED`다.
- 결과를 잃은 환불을 자동으로 다시 발신하지 않는다. 대사로도 결말이 확인되지 않으면 운영자가 확인한다.
- 기존 광고의 현재 주문번호는 이관할 수 있지만, 과거 코드가 이미 덮어쓴 주문번호를 자동 복원하지는 못한다.

## 저장소와 책임

| 코드 | 책임 |
|---|---|
| `Advertisement` | 콘텐츠·노출 기간·노출 상태·현재 merchantUid |
| `AdPaymentAttempt` | 시도별 고정 주문번호/광고/가게/소유자/금액, PG 관측, 미결 사유, 취소 의도, 발신/확인 시각 |
| `AdPaymentLedgerService` | 짧은 DB 단계. 잠금 → 검증 → 저장. PG 호출 없음 |
| `AdPaymentService` | PG 통신 조정. `Propagation.NEVER`로 호출자의 DB 트랜잭션 안에서 실행되는 회귀 차단 |
| `PortoneWebhookService` | 기존 inbox 처리 안에서 예약 원장을 먼저 찾고, 알려진 광고 시도를 광고 처리기로 라우팅 |
| `AdPaymentReconciliationScheduler` | 미결 재조회와 기존 광고 소량 이관 |
| `DataLifecycleGuard` | 미결·미이관 광고를 폐업/탈퇴 차단 건수에 포함 |

원장은 엔티티 cascade 대신 고정 id를 저장한다. 원금·주문번호·소유자 id는 생성 뒤 변경하지 않는다.
원장의 `ownerId`는 거래 연결 식별자이며 익명 데이터가 아니다. 접근 제한·최종 보존/파기 정책은 별도 승인이 필요하다.
환불 키·lease 토큰·원본 PG 응답·구매자 PII는 관리자 응답 DTO에 포함하지 않는다.

## 상태 판정

아래 PG 결과는 매번 서버에서 다시 조회한다. 브라우저 URL/SDK 응답이나 웹훅 본문 상태만 믿지 않는다.

| 확인 결과 | 원장/동작 |
|---|---|
| `READY`, 결제 관측 이력 없음 | 같은 주문번호 재사용. 미결 상태 유지 |
| `NOT_FOUND` | 결제 실패 확정 아님. 같은 주문번호만 재사용 가능하며 새 주문번호는 발급하지 않음 |
| 조회 실패·알 수 없는 상태 | `REVIEW_REQUIRED`, 새 결제 차단 |
| PG `FAILED`, 과거 PAID/환불 발신 없음 | `FAILED`. 다른 미결 시도도 없을 때 재시도용 새 주문번호 발급, 이전 행 보존 |
| `PAID`, 원금/통화 일치, 취소액 0, 서비스 제공 가능 | 원장 `PAID`. 현재 `PENDING_PAYMENT`만 `ACTIVE`로 전이; 중복 콜백은 재활성화하지 않음 |
| 취소/폐업/정지/숨김/기간 경과/과거 주문번호의 늦은 `PAID` | 광고를 되살리지 않고 대사 사유 기록. 취소 의도가 없으면 자동 환불하지 않음 |
| 저장된 취소 의도 + 확정 `PAID` | 첫 환불 발신 의도/키를 커밋한 뒤 전액 취소 요청 |
| 취소 API `REQUESTED`·`UNKNOWN`·`FAILED`·`SUCCEEDED` | 모두 `REFUND_PENDING`으로 재조회. 개별 취소 응답만으로 전체 환불 완료를 단정하지 않음 |
| PG `CANCELLED`, 전체 취소액 = 고정 원금 | 원장 `REFUNDED`, 최초 확인 시각 보존 |
| 부분 취소·취소액 누락·주문번호/원금/통화 불일치 | 대사 필요. 자동 잔액 환불·금액 수정 없음 |
| 이미 확인된 전액 환불 이후 `PAID` | 기존 환불 확인 시각을 지우지 않고 불일치로 보류, 두 번째 자동 환불 금지 |

`PAID`를 한 번 관측하면 이후 `FAILED` 응답으로 결제 전 상태까지 되돌려 새 주문을 허용하지 않는다.
외부에서 요청된 취소가 아직 진행 중이면 추가 취소 발신을 보류한다.
관리자가 중단한 `SUSPENDED` 광고를 결제 콜백이 `ACTIVE`로 되돌리지 않는다.

## 트랜잭션 · 경합 · 장애 복구

모든 광고 금융 쓰기의 행 잠금 순서는 **Store → Advertisement → AdPaymentAttempt**다.
광고 생성, 가게 수정/폐업/제재도 같은 Store 행 경계에 맞춘다. 외부 PG 대기 동안 이 잠금을 유지하지 않는다.

1. DB에서 소유권을 확인하고 5분 lease와 토큰을 저장한다.
2. 트랜잭션 밖에서 PG를 조회한다.
3. 다시 행을 잠그고 토큰을 비교한다. 다른 실행이 인계받았으면 오래된 응답은 폐기한다.
4. 환불할 경우 고정 키·취소 의도·발신 예정 시각을 먼저 커밋한다.
5. PG 취소 호출 후 응답을 저장한다. DB 반영 실패나 프로세스 종료 뒤에도 원장의 발신 기록은 남는다.
6. 다음 GET 대사가 전체 취소액을 확인한다. 같은 시도에 두 번째 자동 POST를 만들지 않는다.

`refundDispatchedAt`은 네트워크 도달 증명이 아니라 **발신 전에 저장한 의도 시각**이다.
4번 커밋 뒤 실제 HTTP 호출 전에 종료되면 환불이 시작되지 않았을 수도 있다. 자동 재발신 대신 아래 수동 절차를 쓴다.
이미 PAID/REFUNDED로 끝난 시도는 정기 조회 대상에서 빠진다. 이후 변경은 웹훅 또는 관리자 대사로 확인한다.

PortOne 취소 요청에는 저장한 `Idempotency-Key`와 예상 취소 가능 잔액 `currentCancellableAmount`를 함께 보낸다.
키는 ASCII 16–256자 범위의 따옴표 문자열 헤더이며, PortOne의 키 보존 시간은 3시간이다.
그 시간을 넘긴 재시도 안전성을 키 하나에 의존하지 않는다. 타임아웃도 실패 확정 근거가 아니다.
[PortOne V2 공통 안내](https://developers.portone.io/api/rest-v2/overview), [취소 API](https://developers.portone.io/api/rest-v2/payment).

## 관리자 화면과 API

관리자 → 결제 운영 → **광고 결제**. 기존 DataTable·확인 모달·버튼을 재사용한다.
`확인 필요`는 사유 코드가 있는 시도, `전체 이력`은 정상/종료 시도까지 포함한다. 페이지 기본 20, 최대 100이다.

| API | 성격 |
|---|---|
| `GET /api/admin/ad-payments?page=0&size=20&openOnly=true` | ADMIN 전용 원장 조회. PG 호출·DB 상태 전이 없음 |
| `POST /api/admin/ad-payments/{id}/reconcile` | 쓰기 작업. PG 재조회하며, 이미 저장된 취소 의도가 있으면 첫 환불 요청도 실행 가능 |
| `POST /api/admin/ad-payments/{id}/refund` | ADMIN 전용, PG PAID와 대사 사유를 확인한 특정 시도의 전액 환불 의도 등록 후 처리 |
| `GET /api/payment/status?type=ad&merchantUid=...` | 본인 소유 주문만 DB 조회. 과거 시도도 조회 가능. PG 호출 없음, 다른 사람/없는 주문 동일 404, `no-store` |

`reconcile`은 읽기 전용 버튼이 아니다. 확인창에서 주문번호와 부수 효과를 확인한다.
`refund`도 중복 발신 제한이나 과거 환불 확인을 우회하지 않는다. 임의로 미결 사유를 지우는 API는 제공하지 않는다.
준비/검증 API의 409 뒤에도 별도 트랜잭션의 실패/불일치 기록은 남는다.

## 수동 대사 절차

대상: 응답을 잃은 환불, 부분 취소, 오래된 NOT_FOUND/READY, 이미 숨긴 광고의 PAID, 원금 불일치, 과거 REFUNDED 모순.
권한: 운영 담당자와 저장소 소유자의 **현재 건별 승인**, 정확한 TEST/LIVE 채널 확인이 먼저다.

1. 원장을 GET으로 조회한다. 시도 id, 주문번호, 고정 원금, 사유, 마지막 조회/발신 시각을 확인한다.
2. 같은 채널의 PortOne 콘솔에서 주문번호와 모든 취소 이력·금액·완료 여부를 대조한다. 원본 개인정보/시크릿은 문서에 복사하지 않는다.
3. 단순 조회 실패라면 `대사·처리`의 부수 효과를 확인한 뒤 승인 범위에서 재조회한다.
4. 결제는 됐지만 서비스 제공이 불가능하고 아직 발신한 환불이 없다면, 전액 환불 승인을 받은 특정 시도에만 `환불 요청`을 사용한다.
5. 이미 발신 기록이 있는데 결말이 불명확하면 다시 누르거나 새 키를 만들지 않는다. 진행 중 취소가 없는지 PG 측에서 확인한다.
6. PG에서 미발신/확정 실패가 입증돼 추가 처리가 필요하면, 별도 승인 후 PortOne 콘솔에서 복구한다. 이후 GET 대사로 전체 취소를 확인한다.
7. NOT_FOUND/부분 취소/과거 누락 주문을 자동 종결시키지 않는다. 필요한 운영 증거와 정책을 정한 뒤 별도 구현/처리한다. 원장 행 삭제나 수동 REFUNDED UPDATE로 우회하지 않는다.
8. 결과 문서에는 시도 id·상태·금액 대조 결과·검증 시각·승인 범위만 남긴다. 상태가 여전히 미결이면 폐업/탈퇴 차단도 유지한다.

이미 덮어써진 주문번호는 PortOne 기간별 거래 내역과 별도로 대조해야 한다. 현재 매핑이 없는 웹훅을 광고로 추측하지 않는다.
기존 `REFUNDED` 표시도 이관 시 참고 값으로만 보관한다. PG 확인 전에는 완료로 인정하거나 자동 재환불하지 않는다.
미이관 광고도 폐업/탈퇴를 차단하므로, 배포 직후에는 과거 광고 검토 요청이 늘 수 있다.

## 배치 설정과 운영 영향

- `advertisement.payments.reconciliation-enabled`: 기본 `true`. 로컬 테스트에서는 `false`.
- `advertisement.payments.reconcile-delay-ms`: 기본 300000ms. 시작 5분 뒤 첫 실행.
- 실행당 기존 광고 이관 최대 10건, 재조회 기한이 된 시도 최대 10건. 여러 인스턴스가 겹쳐도 행 잠금/lease로 동일 시도를 조정한다.
- 오래된 미결 건도 영구 실패로 버리지 않는다. `nextCheckAt` 순으로 처리하며, 사유가 있는 미결 건은 최소 5분 뒤 다시 확인한다.
- 자동 배치를 끄더라도 사용자/관리자/웹훅 요청은 별개다. 정지시켰다고 모든 금융 쓰기가 멈추는 것은 아니다.

새 서버·유료 서비스를 만들지는 않지만 **배포하면** DB 저장량과 제한된 PG 조회/스케줄러 작업이 추가된다.
여러 대의 서버에서 실행할 때의 총 요청량, 인덱스와 잠금 대기는 운영에서 따로 측정한다.
이 프리뷰 작업 중에는 서버 자원·클라우드 요금 설정을 변경하지 않았다.

## 배포 및 롤백 경계

- [ ] 승인된 TEST 주문으로 중복/역순 서명 웹훅, 환불 응답 유실, MySQL 인계/잠금을 확인한다.
- [ ] 새 `ad_payment_attempt` 테이블·unique/index와 `advertisement.status` 타입을 확인한다. [수동 DDL 런북](manual-ddl.md) 참고.
- [ ] 기존 광고의 현재 UID 이관과 과거 누락 UID 대사 계획을 확인한다. 과거 로컬 상태를 PG 증거로 간주하지 않는다.
- [ ] 배치/권한/개인정보 보존 정책과 실제 부하를 확인한다.
- [ ] 새 코드 CI·승인·배포 뒤 금융 원장을 읽기 전용으로 표본 대조한다.

구버전 백엔드는 새 상태와 원장을 모른다. 새 금융 쓰기가 시작된 뒤 구버전으로 무조건 되돌리지 않는다.
장애 시 중복 실행을 피하고, 필요한 금융 쓰기 중단 범위·진행 중 PG 요청·원장 증거를 확인한 뒤 호환 가능한 전진 수정 또는 승인된 롤백을 선택한다.
테이블/키/발신 기록을 지우지 않는다. 이미 보낸 환불을 코드 롤백으로 되돌릴 수는 없다.

## 로컬 회귀의 범위

- 실제 H2 커밋 경계 + 모의 PG: UID 보존, 소유권, 중복 콜백, 늦은 PAID, 금액/통화/id 불일치, 환불 결과 4종, 응답 유실, lease 인계, 외부 진행 중 취소, 폐업/제재 경계.
- MockRestServiceServer: 고정 키 헤더와 예상 잔액 계약.
- 모의 API 브라우저: 관리자 읽기와 명시적 환불 요청 분리, 환불 확인 중/완료 문구 구별.
- 이 검사는 실제 MySQL·PG 통신·서명 PAID 이벤트·운영 복원을 대체하지 않는다. 최신 통과 수치는 [품질 로드맵](quality-roadmap.md)에만 기록한다.
