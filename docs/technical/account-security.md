# 계정 보안

## 계정 탈취 대응

관리자는 회원 목록에서 보호를 시작하거나 복구 메일을 다시 보낼 수 있어요. 관리자 자신의 활성 MFA 세션과 등록 패스키·인증 앱의 5분 확인을 요구해요. 확인은 한 관리자 세션·대상 회원의 인증 버전·작업에 한 번만 사용할 수 있어요. 관리자 계정은 이 화면의 보호 대상에서 제외해요.

보호 시작은 회원 행을 잠그고 모든 로그인 세션과 진행 중인 인증을 폐기해요. 인증 버전이 바뀌면 이전 기기 등록은 즉시 효력을 잃고, DB 커밋 뒤 이전 버전의 Redis 기기 기록을 삭제해요. 이용 정지와 별도로 보호 상태를 유지하며 비밀번호·소셜·패스키 로그인, 갱신, 일반 비밀번호 재설정을 제한해요.

가입·이메일 로그인 설정·비밀번호 재설정·새 환경 이메일 인증에서 RESERVE가 직접 확인한 주소를 보안 연락처로 기록해요. 보안 연락처와 등록 수단이 있는 회원만 보호할 수 있어요. 운영 제재의 해제로 계정 보호가 해제되지는 않아요.

DB 커밋 뒤 확인된 보안 이메일로 한 시간 유효한 복구 링크를 보내요. 메일 발송 여부를 보호 결과와 구분해요. 관리자가 링크를 재발송하면 이전 링크와 복구 요청을 폐기해요. 링크의 비밀값은 해시만 저장해요. 소유자는 링크와 기존 패스키·인증 앱·일회용 복구코드 중 하나로 본인 확인을 마쳐요. 복구코드를 쓸 때는 새 코드를 먼저 보관해요. 보관을 확인하면 기존 코드를 소비하고 새 코드를 등록하면서 보호를 해제해요. 복구는 일반 로그인과 별도의 IP·회원 제한을 사용해요. 복구 완료도 보안 이메일로 알려요.

잠긴 계정 화면에서는 확인한 보안 이메일로 5분간 유효한 인증 코드를 요청할 수도 있어요. 공개 발송 응답은 계정 존재와 배달 상태에 관계없이 같아요. 서버는 코드를 해시로 저장하고 요청 식별자·회원의 인증 버전에 묶어 한 번만 확인해요. 이메일 확인은 복구 전용 인증 요청을 열며, 등록한 인증 수단으로 확인을 마치면 보호가 해제돼요.

보호 해제 후 비밀번호·소셜 로그인에는 기존 추가 인증이 필요하고 마지막 인증 수단의 해제를 제한해요. 복구 요청은 일반 로그인 세션을 발급하지 않아요. 복구 수단에 접근할 수 없으면 문의로 안내해요.

## 로그인

이메일·비밀번호와 Google·Kakao·Naver를 지원해요. access token은 API 인증, refresh token은 기기별 로그인 유지에 사용해요. 서버는 서명·발급자·용도·만료·회원 상태·인증 버전·현재 세션을 확인해요.

로그인 유지는 기본 미선택이며 이메일·패스키·소셜 로그인과 추가 인증에 같은 선택을 적용해요. 선택한 일반 회원의 새 세션은 마지막 토큰 발급·갱신부터 30일, 최초 발급부터 최대 90일이에요. 사업자·관리자가 선택하면 기본 14일·최대 30일이에요. 미선택은 브라우저 세션 쿠키를 사용하며 서버에서 마지막 발급·갱신부터 1시간, 최초 발급부터 기본 최대 30일을 적용해요. 만료한 세션은 다시 로그인해야 해요. 기존 세션은 발급 당시의 기간을 이어가고, 일반 회원의 장기 세션으로 승격된 권한을 사용하려면 다시 로그인해요. 안내에 필요한 기간은 공개 읽기 API인 `GET /api/auth/login-policy`에서 조회해요.

로그인 유지를 고르지 않고 소셜 또는 패스키 로그인을 마치면 필요한 추가 인증과 약관 동의 뒤에 선택지를 보여줘요. 유지에 동의하면 현재 기기의 세션과 인증 수단을 유지하면서 동일한 역할별 기간으로 쿠키를 갱신해요. 이번만 사용하면 브라우저 세션으로 계속 이용해요. 이메일 로그인에는 로그인 화면에서 선택한 설정을 적용해요.

갱신은 서명한 선택과 저장된 만료 시각을 사용하고, 소셜 콜백은 state로 확인한 최초 요청의 선택을 사용해요. 브라우저가 세션 쿠키를 복원할 수 있고 열린 화면의 주기 조회도 세션 갱신을 일으킬 수 있어요. 공용 기기에서는 사용 후 명시적으로 로그아웃해요. [쿠키 수명](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)을 참고해요.

재사용이 확인된 토큰 계열과 로그아웃으로 종료한 세션은 MySQL에서 즉시 폐기해요. 커밋 뒤 기존 Redis 릴레이로 회원 범위의 세션 재확인 신호를 보내요. 신호를 받은 개인 스트림은 MySQL에서 해당 세션을 다시 확인해 폐기된 연결만 종료해요. Redis 신호가 유실돼도 API와 스트림의 다음 권한 확인에서 폐기를 적용해요. 재사용은 서버 경고에 기록하고, 정기 작업은 만료된 세션 행을 정리해요.

비밀번호 변경·탈퇴·인증 수단 변경은 기존 인증을 폐기해요. 공급자 계정 변경 알림도 서명과 대상을 확인해 처리해요.

로그인 초기 상태는 캐시하지 않는 `GET /api/auth/session`에서 확인해요. 익명 방문도 200으로 응답하며 유효한 refresh token 여부만 갱신 가능성으로 안내해요. 이 조회는 쿠키를 발급하지 않아요. 실제 갱신은 기존 검증·회전 절차를 거쳐요.

로컬 앱은 `http://localhost:5173`을 사용해요. 127.0.0.1의 앱 페이지는 같은 경로와 검색 조건을 유지해 localhost로 이동해요. OAuth 복귀 주소와 로그인 쿠키의 호스트를 맞추기 위한 동작이에요.

서비스에서 로그아웃해도 소셜 공급자의 로그인 세션은 남을 수 있어요. 공급자 인증 화면을 다시 보지 않고 콜백으로 돌아올 수 있으며, 중복 이메일 검사는 공급자 사용자 정보를 받은 뒤에 해요. 같은 이메일의 기존 계정을 자동 연결하지 않고 기존 방식으로 로그인한 뒤 보안 설정에서 연결해요. 공급자 화면에서 뒤로 돌아오면 외부 이동의 로딩만 해제하며 진행 중인 비밀번호·패스키 요청은 임의로 초기화하지 않아요.

소셜 로그인 실패와 제재 결과는 인증을 진행한 브라우저 세션에 잠깐 보관해요. 주소의 참조로 같은 브라우저에서 한 번만 조회하며, 서버가 확인한 오류 코드와 제재 상태를 화면에 표시해요.

소셜 연결은 이메일 로그인을 자동 해제하지 않아요. 연결·해제, 비밀번호 설정·변경·해제 전에는 현재 회원·세션·인증 버전·작업 종류에 묶인 5분 확인을 먼저 마쳐요. 신뢰 브라우저도 현재 비밀번호·최근 연결 계정의 공급자 인증 등 기본 본인 확인이 필요해요. 새 환경은 추가 확인을 거치고 관리자는 기존 필수 인증을 유지해요. 확인 요청은 다른 작업·회원·세션이나 MFA 수단 관리에 재사용하지 않아요.

소셜 연결은 사전 확인을 OAuth state·공급자·세션·현재 환경에 묶어 콜백까지 전달해요. 연결 정보 저장·기존 세션 폐기·새 세션 발급을 같은 DB 트랜잭션으로 마쳐요. 필요한 확인을 마치기 전에 공급자 연결을 저장하지 않고, 같은 작업의 완료 단계에서 인증을 다시 요구하지 않아요. 비밀번호 변경·로그인 수단 해제는 기존 전체 세션 폐기와 다시 로그인을 유지해요. 저장의 응답을 받지 못하면 기존 세션 상태를 조회해 다시 로그인하고 보안 설정을 확인하도록 안내해요. 저장을 자동으로 다시 보내지 않아요.

이메일 확인 코드는 코드발송을 눌렀을 때 보내요. 인증된 계정의 접속 환경·로그인 수단 확인은 비동기 SMTP 작업의 결과를 최대 10초 기다린 뒤 응답하며 실패·작업 거절·시간 초과를 성공으로 표시하지 않아요. SMTP 수락은 수신함 도착 확인과 달라요. 가입·비밀번호 찾기의 일반 응답은 계정 존재를 드러내지 않는 기존 정책을 유지해요.

본인 확인·인증 수단 등록의 응답이 끊기면 같은 요청의 서버 확인 상태를 조회하고 일회용 코드를 다시 소비하지 않아요. 등록 뒤 표시하지 못한 복구코드는 다시 노출하거나 자동 재발급하지 않고 보안 설정의 재발급으로 안내해요. 등록부터 코드 보관·세션 교체까지 개인 실시간 조회를 보류해요. 확인한 관리 작업은 인증 버전을 바꾼 뒤에도 원래 브라우저·환경에서만 세션을 이어가고 기본 인증을 MFA 완료로 승격하지 않아요.

로그인 마무리 응답이 끊기면 해당 확인이 발급한 현재 회원·버전·정확한 세션만 서버에서 확인해요. 공개 완료 참조는 인증 수단이 아니며 새 쿠키를 발급하지 않아요. 발급 후 회원 조회만 실패했다면 같은 화면에서 조회를 다시 시도해요. 복구코드를 재발급한 관리는 이미 교체된 세션으로 복귀하고 관리 요청만 닫아요. 확인을 취소하면 원래 변경을 실행하지 않고 대기 상태를 해제해요.

## 접속 환경과 시간제 제한

### 공유 인증 제한

공유 인증 한도는 `reserve.security.auth-limits.enabled`의 기본값이 `false`예요. 활성화에는 환경별 Redis, IP 보호와 분리한 32바이트 base64 키 `fingerprint-key`, 8~64자의 버전 식별자 `epoch`가 필요해요. 배포 변수는 `RESERVE_SECURITY_AUTH_LIMITS_ENABLED`·`RESERVE_SECURITY_AUTH_LIMITS_EPOCH`, 비밀 설정은 `RESERVE_SECURITY_AUTH_LIMITS_FINGERPRINT_KEY`예요.

활성화하면 로그인 IP/계정, 가입·코드·메일, 로그인 수단 변경, 일반 회원 수정의 기존 수치와 축을 Redis에서 공유해요. HMAC과 환경 namespace로 식별자를 가리고 서버 시각과 Lua로 원자적으로 소비해요. 성공한 로그인·코드 확인은 현재 HTTP 요청이 실제로 소비한 증표 하나만 반환하며, 중복 반환이나 이전 리필 창의 반환으로 실패 누적을 지우지 않아요. 반환 결과가 불명확하면 소비를 유지해요.

공유 거절은 기존 `429`, 장애·타임아웃·메모리·권한·결과 불명은 `503`과 `Retry-After`로 처리해요. 로컬 제한으로 새 인증을 우회하지 않아요. 기존 refresh·로그아웃·인증 취소와 MFA 상태 조회의 별도 관문, DB 티켓의 실패 횟수·만료·일회 소비는 유지해요.

앱만 재시작하면 누적 제한을 유지해요. Redis의 실제 기동 식별자가 바뀌거나 marker·epoch가 달라지면 최장 인증 제한 창인 10분 동안 새 인증·메일을 보류해요. AOF/RDB로 marker를 복원해도 새 Redis 기동에는 같은 대기를 적용해요. 복구 대기를 반복 요청으로 연장하지 않으며 제한된 앱 계정은 `INFO server`를 읽을 수 있어야 해요. Redis 영속화·ACL·기능 활성화는 별도 운영 승인 대상이에요.

처음 공유 제한으로 전환할 때 기존 앱의 로컬 누적은 Redis로 자동 이전되지 않아요. 기존 로컬 제한이 적용되는 인증·회원 수정 접수를 멈춘 시점부터 최장 10분을 확보하는 승인된 전환 절차가 필요해요. 기존 앱이 접수하는 동안 marker를 미리 준비한 시간만으로 이 기간을 충족했다고 판단하지 않아요. 이 전환 절차와 영향 시간을 확정하기 전에는 공유 제한을 활성화하지 않아요.

운영 준비 시 전용 키·epoch와 제한 ACL을 승인된 보호 환경에 준비한 뒤 `python3 scripts/prepare-ip-protection.py prepare-auth-limits --apply`로 복구 대기를 시작해요. 10분 뒤 `check-auth-limits`의 읽기 전용 검사를 통과해야 활성화할 수 있어요. 배포도 이 검사를 거치며 marker를 즉시 허용 상태로 초기화하지 않아요. 기존 IP 보호만 활성화한 구성은 종전 제한 ACL도 읽기 전용 검사에서 허용해요.

IP 보호는 `reserve.security.ip-protection.enabled`의 기본값이 `false`예요. 활성화에는 환경별 Redis와 별도 32바이트 키의 base64 값인 `reserve.security.ip-protection.fingerprint-key`, 실제 nginx만 포함하는 `trusted-proxies` CIDR 목록이 필요해요. 키는 보호 설정으로 전달하고 프론트·로그·저장소에 넣지 않아요. 앱 포트 직접 접근 차단과 프록시의 X-Real-IP 덮어쓰기를 먼저 확인해요. 신뢰 프록시를 지정하지 않으면 직접 연결 주소만 사용해요.

배포는 `RESERVE_SECURITY_IP_PROTECTION_ENABLED`·`RESERVE_SECURITY_IP_PROTECTION_TRUSTED_PROXIES` 변수와 `RESERVE_SECURITY_IP_PROTECTION_FINGERPRINT_KEY` Secret을 전달해요. 운영 활성화에는 Redis의 제한 계정 `reserve_app`과 내부망 nginx 주소 `172.30.30.2/32`가 필요해요. 공유 네트워크 전체를 신뢰하지 않아요. Redis·키·프록시 준비 검사가 실패하면 컨테이너 전환 전에 중단해요. 프록시와 직접 접근 차단의 전환 절차는 [배포](deployments.md)를 따라요.

Redis 앱 권한은 `scripts/redis-app.rules`의 명령과 `reserve:prod:*` 키·채널로 제한하고 기존 관리자 인증과 분리해요. 비밀번호 대신 해시를 담은 ACL 파일을 보호된 경로에 저장하고 읽기 전용으로 연결해요. 활성화 전 검사에서는 호스트 포트 미공개·권한 범위·ACL 지속 설정·메모리 여유 25% 이상·`noeviction`을 확인해요. IP Lua는 OOM 실행을 허용하지 않으며, 메모리·권한·연결 장애를 추가 인증 성공으로 취급하지 않아요. Redis 상태가 유실되면 신뢰 이력은 다시 확인하고 기존 관리자 MFA는 유지해요.

활성화하면 새 로그인에서 회원·인증 버전에 연결한 신뢰 브라우저를 확인해요. 같은 IP라도 처음 보는 브라우저는 확인을 요구해요. 본인 확인 후 이용자가 선택하면 임의 식별자 HttpOnly·Secure·SameSite=Lax·호스트 전용 쿠키를 최대 30일 보관해요. 운영 쿠키 이름은 `__Host-reserve_browser`, 로컬은 `reserve_browser`예요. 쿠키만으로 로그인하지 않고 관리자 필수 MFA를 대신하지 않아요.

신뢰 쿠키와 운영체제·브라우저 종류가 같을 때 동일 IP 또는 IPv4 /24·IPv6 /64 안의 작은 변화는 기본 로그인으로 이어가요. 만료 전에 그 환경에서 로그인을 마치면 등록 정보와 쿠키를 그날부터 30일 갱신해요. 일반 조회·세션 갱신·설정 본인 확인은 기기 등록 기간을 갱신하지 않아요. 더 큰 네트워크 변화·종류 변경·누락·중복 쿠키·만료는 기존 추가 확인을 요구해요. 새 접속 환경에서 본인 확인을 마치면 로그인 세션을 먼저 발급한 뒤 기기 등록 여부를 물어요. 괜찮아요, RESERVE 홈, 화면 이탈은 로그인 상태를 유지하고 새 기기를 등록하지 않아요. 저장 실패 시 로그인 완료와 기기 등록 결과를 구분해 안내해요.

새 환경은 등록한 패스키·인증 앱·복구코드로 확인하며, 추가 수단이 없는 일반 회원·사업자는 등록 이메일의 일회용 코드로 확인해요. 새 수단 등록·유예로 확인을 건너뛸 수 없고 관리자 MFA를 이메일로 대체하지 않아요. 회원·인증 버전·5분 요청·현재 IP와 브라우저 문맥을 확인한 뒤 세션을 발급해요. 등록을 선택하면 방금 발급된 세션과 원래 요청·접속 환경을 다시 대조하고 한 번만 기록해요. 인증 중 환경이 달라지거나 요청이 만료되면 다시 시작을 안내해요. 기존 세션의 망 변경·refresh만으로 계정을 잠그지 않아요.

접속 위험을 계산하는 IP·회원·브라우저 식별자와 환경 분류는 전용 HMAC으로 가명화해 Redis에 보관해요. 기기 목록에는 운영체제·브라우저 종류와 세션의 가명 참조를 연결해요. 원문 IP·User-Agent를 신뢰 이력에 저장하지 않아요. 신뢰 브라우저는 회원·인증 버전별 최대 8개·각 30일이고 확인 요청은 5분이에요. 이메일 코드는 해시만 보관하며 1분 재발송 제한·최대 5회 확인·일회용 소비를 적용해요. 인증 실패·인증 제한 응답이 한 IP에서 5분 동안 20회 누적되면 15분 제한하고, 24시간 안에 반복되면 1시간 제한해요. 제한 중 재요청으로 기한을 연장하거나 계정을 영구 정지하지 않아요. 응답은 `429`와 `Retry-After`를 사용해요. 이 IP 차단은 인증 진입·확인에 적용하고 공개 조회나 이미 로그인한 회원의 일반 API까지 차단하지 않아요.

로그인 및 보안의 로그인 기기는 현재 회원·세션·인증 버전에 묶인 5분 본인 확인을 거쳐 관리해요. 현재 비밀번호, 최근 연결 계정의 소셜 인증, 등록한 패스키·인증 앱 코드·복구코드 중 허용된 수단 하나로 확인해요. 패스키나 인증 앱을 등록했다는 이유만으로 소셜·비밀번호 확인을 반복하지 않아요. 등록 수단이 없는 회원도 비밀번호·연결 소셜 계정으로 확인할 수 있어요. 등록한 코드로 시작할 때도 소셜 확인을 먼저 강제하지 않아요.

현재 로그인만으로 기기 관리 확인이 끝나지는 않아요. 관리자·복구 보호 계정은 기존 필수 MFA를 마친 유효한 세션이 필요하고, 새 접속 환경에서 IP 보호가 추가 확인을 요구하면 등록 수단이나 허용된 이메일 확인을 거쳐요. 기기 관리 확인은 로그인 MFA 완료로 승격하거나 로그인 방법 변경·인증 수단 관리·관리자 작업에 재사용하지 않아요. 패스키 및 인증 앱 관리에서 추가 인증이 시작된 뒤에는 등록한 인증 수단만 사용해요. 기기 관리 인증을 취소하거나 완료하지 못하면 같은 항목의 인증 수단 선택으로 돌아와요.

기기 목록은 접속 환경 보호가 꺼져 있어도 MySQL의 유효한 로그인 세션을 보여줘요. 보호가 켜져 있으면 Redis의 신뢰 정보와 대조하고, 등록과 연결되지 않은 세션은 브라우저 종류를 추정하지 않고 로그인 시각으로 구분해요. 이전 등록 정보와 세션의 연결을 확인할 수 없으면 해당 등록은 확인 필요로 표시해요. 신뢰 등록은 보호가 켜져 있을 때 지금 사용하는 브라우저에서만 가능하며, 등록 뒤 같은 확인으로 목록을 계속 관리할 수 있어요. 확인 기한은 연장하지 않아요. 등록을 해제하면 다음 로그인에 접속 환경 확인을 요구해요. 원격 로그아웃은 선택한 브라우저에 연결된 세션이나 선택한 개별 세션만 종료해요. 현재 세션과 다른 회원은 대상이 아니에요. 목록 응답에는 원문 IP·브라우저 식별 쿠키·세션 식별자를 포함하지 않아요.

서명된 공급자 이벤트·PG 웹훅, 로그아웃·세션 복구·인증 취소와 진행 중 OAuth 콜백은 각자의 기존 인증 관문을 유지해요. Redis 장애 때 기존 로컬 요청 제한을 유지하고, 새 환경의 기본 인증만으로 신뢰 확인을 우회하지 않아요. 관리자 MFA·직접 패스키 로그인은 이력 조회 장애만으로 잠그지 않아요. 이 정책은 VPN·국가를 판정하지 않아요. 격리 Redis 검사는 기존 `RESERVE_REDIS_INTEGRATION=true` 시험 관문에서 실행해요. 실제 활성화는 프록시·키·Redis 용량과 장애·복구 확인 뒤 별도로 진행해요.

## 패스키와 인증 앱

`reserve.mfa.enabled=true`이면 관리자만 추가 인증이 필수예요. 일반 회원·사업자는 기본적으로 등록 여부와 관계없이 선택한 이메일·소셜 방법으로 로그인하며, IP 보호를 켠 경우 새 환경의 확인을 추가해요. 패스키는 로그인 화면에서 직접 선택할 때 사용하며 마이페이지에서 등록·해제할 수 있어요. 신규 등록을 중지해도 관리자가 설정한 인증은 유지해요.

- 로그인 화면의 패스키 버튼은 브라우저의 저장된 인증 수단 선택창으로 바로 이어져요. 기본 로그인 뒤 추가 인증이 필요하거나 인증 수단 관리 중 본인 확인이 필요하면, 서버가 허용한 수단을 한 줄에서 선택해요. 패스키를 취소하거나 코드 확인이 실패하면 같은 인증 요청의 선택 화면으로 돌아가요.
- 로그인 화면의 등록 아이콘은 먼저 로그인한 뒤 본인 계정의 보안 설정으로 이어져요. 일반 회원·사업자는 같은 설정에서 선택해 등록하며, 등록 전 기본 인증과 현재 기기 세션을 확인해요.
- 패스키는 기기·비밀번호 관리자에 저장해요. 브라우저·운영체제의 기본 WebAuthn 창을 사용하고 특정 저장소나 인증기 종류로 제한하지 않아요. WebAuthn의 challenge·RP ID·허용 출처·서명·사용자 확인을 서버에서 검증하며 개인 키와 생체 정보는 서버에 보내지 않아요. 인증 앱의 QR·6자리 코드와는 다른 수단이에요.
- OTP는 30초·6자리 TOTP를 사용해요. ±1 구간만 허용하고 이미 사용한 구간을 다시 받지 않아요.
- 관리자는 기본 로그인 뒤 추가 인증을 마쳐야 앱 토큰을 발급해요. 로그인 유지 선택과 인증 버전·만료 검증을 보존하며 관리·패스키 로그인 요청으로 이를 건너뛸 수 없어요. 중간 요청은 5분·최대 5회·일회용이며 HttpOnly 쿠키에 연결해요.
- 일반 회원·사업자의 수단 추가·해제·복구코드 재발급은 현재 비밀번호 또는 5분 이내에 확인한 연결 소셜 계정으로 관리할 수 있어요. 관리자에게는 등록한 인증 수단의 추가 확인을 요구해요. 관리 요청은 현재 회원·기기 세션·인증 버전에 묶고, 기본 인증만 확인한 관리를 MFA 완료 세션으로 승격하지 않아요.
- 등록·해제 뒤 기존 세션을 폐기하고, 본인 확인을 마친 현재 브라우저만 갱신된 쿠키로 이어줘요. 로그인한 상태에서 수단을 등록하면 복구코드 보관 전에 현재 브라우저를 이어주며, 신규 로그인은 코드 보관과 완료 절차를 유지해요. 이미 전달된 관리 등록 세션은 보관 완료 응답이 끊겨도 같은 브라우저에서 확인해요. 복구코드는 10개를 한 번만 표시하고 해시만 저장해요. 사용한 코드는 폐기해요.
- 일반 회원·사업자는 마지막 인증 수단도 해제할 수 있어요. 확인한 비밀번호·소셜 로그인이 남으면 추가 인증 완료 권한을 붙이지 않은 기본 세션으로 현재 브라우저를 유지해요. 전체 해제는 keepCurrentSession을 명시한 요청에만 세션을 이어주고, 기존 요청은 재로그인을 유지해요. 독립된 기본 로그인 확인 없이 마지막 패스키를 해제하면 완료와 재로그인 안내를 표시해요. 해제 뒤 회원 조회만 실패한 경우에는 해제를 반복하지 않고 조회를 다시 확인해요. 관리자의 추가 인증과 마지막 수단은 해제할 수 없어요. 관리자가 모든 수단과 복구코드를 잃은 경우의 수동 복구는 별도 운영 절차로 처리해요.

`reserve.mfa.rp-id`와 `reserve.mfa.origins`는 실제 앱 출처로 고정해요. OTP의 `reserve.mfa.encryption-key`는 독립된 Base64 AES-256 키예요. 활성화 시 출처와 키를 검사하고, 백업·복구에도 같은 키가 필요해요. 로컬은 localhost용 RP·출처와 운영과 다른 키를 사용해요. 개발용 localhost 출처를 운영에 섞지 않아요.

## 예약 관리 권한

사업자 예약 조회·집계는 관리자 계정으로 접속해도 본인 가게로 제한해요. 가게의 승인·거절·완료·노쇼·취소·숨김은 실제 소유권을 검사하며 관리자 역할로 우회하지 않아요. 관리자 전체 예약은 별도 읽기 API `GET /api/reservations/admin/page`를 사용해요. 관리자 휴지통·감사 기능은 기존 관리 경로에서 처리해요.

직접 휴지통 경로도 회원 → 예약 → 결제 잠금을 공유하고 진행 중 예약·미해결 결제·환불을 숨기지 않아요. 거래 증거는 일반 가게·관리자 목록의 개인정보 가림과 분리하며, 별도 경로에서 추가 인증·목적·접근 기록을 확인해요.

## 키와 빌드 경계

서버 키는 브라우저의 `VITE_` 환경변수에 넣지 않아요. 결제 채널·지도 JavaScript 식별자와 Sentry DSN은 브라우저에 공개되는 값이므로 공급자에서 실제 앱 출처를 제한해요. 권한이 있는 서버 키와 혼용하지 않아요.

키·로컬 설정은 Git과 Docker 빌드 문맥에서 제외해요. `scripts/check-secret-boundaries.mjs`는 현재 소스와 지정한 빌드 환경 파일을 검사하고 값 대신 경로·행·규칙만 출력해요. Git 이력과 공급자에서의 실제 폐기는 별도로 확인해요. 로컬 DB 암호는 공개 기본값 대신 보호한 로컬 설정이나 `DB_PASSWORD_LOCAL`에서 받아요.

JWT·MFA·채팅·피드·공급자 토큰 키를 분리해요. 암호화 키를 교체하기 전에 기존 자료와 복구 이미지의 복호화 가능성을 확인하며, 로컬 키를 운영 키로 복사하지 않아요. 키 보관 위치·권한·배포 전달·대응 복구를 함께 확인해요. Sentry는 헤더·검색 매개변수·본문을 수집하지 않고 세션 재현의 텍스트·미디어 가림을 유지해요.

## 비밀번호와 이메일

비밀번호는 8~64자·영문과 숫자를 포함하고 UTF-8 72바이트 이하여야 해요. bcrypt로 저장하고 알려진 유출 목록과 대조해요. 이메일 인증은 목적·만료·시도 제한을 확인해요.

비밀번호 찾기는 이메일 로그인이 설정된 활성 계정에만 코드를 보내요. 요청 응답은 가입 여부와 로그인 방식에 관계없이 같고, 만료·불일치·시도 소진 등의 코드 실패도 같은 문구로 안내해요. 코드 확인 후 서버의 만료 시각을 사용하고, 비밀번호 변경 단계에서 코드가 만료되거나 거절되면 이메일을 보존해 코드 요청 단계로 돌아가요. 이메일 로그인을 해제한 직후에는 연결된 소셜 로그인 방법을 로그인 화면에 안내해요.

인증 코드·등록 비밀·복구코드는 URL이나 브라우저 저장소에 남기지 않아요. 공급자 토큰은 별도 키로 암호화하고, 탈퇴 후 연결 해제는 저장한 작업으로 재시도해요.

## 일반 프로필 수정

이름·알림, 계정 사진 업로드·초기화, 위치, 마케팅 수신 동의는 같은 수정 한도를 사용해요. 회원당 분당 12회·IP당 분당 45회이며 IP 제한 뒤에는 회원 한도를 소비하지 않아요. 조회·로그인 수단·MFA·탈퇴의 기존 관문과 구분해요. 기본은 앱 메모리 제한이며 공유 인증 제한을 활성화하면 이 수정 한도도 Redis에서 공유해요.

이름은 가입과 같은 2~20자 길이로 제한하고, 공백만 있는 값과 제어 문자는 거부해요. 이름 없이 알림만 바꿀 수 있어요. 위치는 위도·경도를 함께 전달하고 유한값·위도 -90~90·경도 -180~180을 확인해요. 주소·상세주소는 각각 최대 255자, 우편번호는 최대 10자이며 주소 없는 좌표 저장은 기존 주소를 보존해요.

사진 초기화 확인창과 사진 저장의 후속 처리는 실행을 시작한 회원·역할·세션과 현재 컴포넌트를 확인해요. 계정 전환·로그아웃·화면 종료 뒤 남은 확인창은 실행하지 않으며 늦은 응답으로 현재 계정을 갱신하지 않아요.

## 개인 검색

개인 검색은 현재 회원의 예약·웨이팅·대화 권한으로 제한해요. 검색만으로 읽음·업무 상태를 바꾸지 않아요. 공개 캐시에 저장하지 않으며 계정·세션이 바뀌면 이전 결과를 폐기해요.

관련 코드는 backend의 config·member·email 영역에 있어요.
