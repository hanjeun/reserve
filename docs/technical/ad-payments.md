# 광고 결제 시도 · 대사 · 환불

광고 결제는 예약과 다른 원장(`AdPaymentAttempt`)과 상태기계를 써요. 예약 결제와 공통 운영 절차는 [결제 런북](payments.md), 최신 검증 결과는 [품질 로드맵](quality-roadmap.md)에 있어요.

## 먼저 알아둘 것

- 광고 노출 상태와 돈의 상태는 달라요. `CANCELLED`는 노출 중단이지 미결제·환불 완료 증거가 아니에요.
- 광고마다 현재 주문번호가 있고, 발급한 모든 주문번호는 `ad_payment_attempt`에 보존해요.
- 환불 버튼은 **요청**이에요. 취소 API 응답만으로 완료 표시하지 않고, PG 재조회에서 주문번호·KRW·원금·전체 취소액이 맞아야 `REFUNDED`예요.
- 결과를 잃은 환불을 자동으로 다시 발신하지 않아요. 대사로도 결말이 확인되지 않으면 운영자가 확인해요.
- 기존 광고의 현재 주문번호는 이관할 수 있지만, 과거 코드가 이미 덮어쓴 주문번호는 자동 복원하지 못해요.
- 광고 환불에는 사용 일수만큼 빼는 일할 계산이 없어요. 당일을 포함해 `ACTIVE` 광고를 취소하면 그 결제 시도의 고정 원금 전액을 취소 요청하고, PG가 전체 취소액을 확인한 뒤에만 `REFUNDED`예요.

## 저장소와 책임

| 코드 | 책임 |
|---|---|
| `Advertisement` | 콘텐츠·노출 기간·노출 상태·현재 merchantUid |
| `AdPaymentAttempt` | 시도별 고정 주문번호/광고/가게/소유자/금액, PG 관측, 미결 사유, 취소 의도, 발신/확인 시각 |
| `AdPaymentLedgerService` | 짧은 DB 단계. 잠금 → 검증 → 저장. PG 호출 없음 |
| `AdPaymentService` | PG 통신 조정. `Propagation.NEVER`로 호출자의 DB 트랜잭션 안에서 실행되는 회귀 차단 |
| `PortoneWebhookService` | 기존 inbox 처리 안에서 예약 원장을 먼저 찾고, 알려진 광고 시도를 광고 처리기로 라우팅 |
| `AdPaymentReconciliationScheduler` | 미결 재조회와 기존 광고 소량 이관 |
| `DataLifecycleGuard` | 미결·미이관 광고를 폐업/탈퇴 차단 건수에 포함 |

- 원장은 엔티티 cascade 대신 고정 id를 저장해요. 원금·주문번호·소유자 id는 생성 뒤 바꾸지 않아요.
- 원장의 `ownerId`는 거래 연결 식별자라 익명 데이터가 아니에요. 접근 제한·최종 보존/파기 정책은 별도 승인이 필요해요.
- 환불 키·lease 토큰·원본 PG 응답·구매자 PII는 관리자 응답 DTO에 넣지 않아요.

## 상태 판정

PG 결과는 매번 서버에서 다시 조회해요. 브라우저 URL/SDK 응답이나 웹훅 본문 상태만 믿지 않아요.

| 확인 결과 | 원장/동작 |
|---|---|
| `READY`, 결제 관측 이력 없음 | 같은 주문번호 재사용. 미결 상태 유지 |
| `NOT_FOUND` | 결제 실패 확정 아님. 같은 주문번호만 재사용 가능하며 새 주문번호는 발급하지 않음 |
| 조회 실패·알 수 없는 상태 | `REVIEW_REQUIRED`, 새 결제 차단 |
| PG `FAILED`, 과거 PAID/환불 발신 없음 | `FAILED`. 다른 미결 시도도 없을 때 재시도용 새 주문번호 발급, 이전 행 보존 |
| `PAID`, 원금/통화 일치, 취소액 0, 서비스 제공 가능 | 원장 `PAID`. 현재 `PENDING_PAYMENT`만 `ACTIVE`로 전이; 중복 콜백은 재활성화하지 않음 |
| 취소/폐업/정지/숨김/기간 경과/과거 주문번호의 늦은 `PAID` | 광고를 되살리지 않고 대사 사유 기록. 취소 의도가 없으면 자동 환불하지 않음 |
| 저장된 취소 의도 + 확정 `PAID` | 첫 환불 발신 의도/키를 커밋한 뒤 전액 취소 요청 |
| 취소 API `REQUESTED`·`UNKNOWN`·`FAILED`·`SUCCEEDED` | 모두 `REFUND_PENDING`으로 재조회. 개별 취소 응답만으로 전체 환불 완료를 단정하지 않음 |
| PG `CANCELLED`, 전체 취소액 = 고정 원금 | 원장 `REFUNDED`, 최초 확인 시각 보존 |
| 부분 취소·취소액 누락·주문번호/원금/통화 불일치 | 대사 필요. 자동 잔액 환불·금액 수정 없음 |
| 이미 확인된 전액 환불 이후 `PAID` | 기존 환불 확인 시각을 지우지 않고 불일치로 보류, 두 번째 자동 환불 금지 |

- `PAID`를 한 번 관측하면 이후 `FAILED` 응답으로 결제 전 상태까지 되돌려 새 주문을 허용하지 않아요.
- 외부에서 요청된 취소가 아직 진행 중이면 추가 취소 발신을 보류해요.
- 관리자가 중단한 `SUSPENDED` 광고를 결제 콜백이 `ACTIVE`로 되돌리지 않아요.

## 트랜잭션 · 경합 · 장애 복구

모든 광고 금융 쓰기의 행 잠금 순서는 **Store → Advertisement → AdPaymentAttempt**예요. 광고 생성, 가게 수정/폐업/제재도 같은 Store 행 경계를 지나요. 외부 PG를 기다리는 동안에는 잠금을 쥐지 않아요.

1. DB에서 소유권을 확인하고 5분 lease와 토큰을 저장해요.
2. 트랜잭션 밖에서 PG를 조회해요.
3. 다시 행을 잠그고 토큰을 비교해요. 다른 실행이 인계받았으면 오래된 응답은 버려요.
4. 환불할 경우 고정 키·취소 의도·발신 예정 시각을 먼저 커밋해요.
5. PG 취소 호출 후 응답을 저장해요. DB 반영 실패나 프로세스 종료 뒤에도 원장의 발신 기록은 남아요.
6. 다음 GET 대사가 전체 취소액을 확인해요. 같은 시도에 두 번째 자동 POST를 만들지 않아요.

`refundDispatchedAt`은 네트워크 도달 증명이 아니라 **발신 전에 저장한 의도 시각**이에요. 4번 커밋 뒤 실제 HTTP 호출 전에 종료되면 환불이 시작되지 않았을 수도 있어요. 자동 재발신 대신 아래 수동 절차를 써요.
이미 `PAID`/`REFUNDED`로 끝난 시도는 정기 조회 대상에서 빠져요. 이후 변경은 웹훅이나 관리자 대사로 확인해요.

PortOne 취소 요청에는 저장한 `Idempotency-Key`와 예상 취소 가능 잔액 `currentCancellableAmount`를 함께 보내요. 키는 ASCII 16–256자 범위의 따옴표 문자열 헤더이고, PortOne의 키 보존 시간은 3시간이에요.
그 시간을 넘긴 재시도 안전성을 키 하나에 기대지 않아요. 타임아웃도 실패 확정 근거가 아니에요.
참고: [PortOne V2 공통 안내](https://developers.portone.io/api/rest-v2/overview), [취소 API](https://developers.portone.io/api/rest-v2/payment).

## 관리자 화면과 API

관리자 → 결제 운영 → **광고 결제**. 기존 DataTable·확인 모달·버튼을 재사용해요.
`확인 필요`는 사유 코드가 있는 시도, `전체 이력`은 정상/종료 시도까지 보여 줘요. 페이지 기본 20, 최대 100이에요.

| API | 성격 |
|---|---|
| `GET /api/admin/ad-payments?page=0&size=20&openOnly=true` | ADMIN 전용 원장 조회. PG 호출·DB 상태 전이 없음 |
| `POST /api/admin/ad-payments/{id}/reconcile` | 쓰기 작업. PG 재조회하며, 이미 저장된 취소 의도가 있으면 첫 환불 요청도 실행 가능 |
| `POST /api/admin/ad-payments/{id}/refund` | ADMIN 전용, PG PAID와 대사 사유를 확인한 특정 시도의 전액 환불 의도 등록 후 처리 |
| `GET /api/payment/status?type=ad&merchantUid=...` | 본인 소유 주문만 DB 조회. 과거 시도도 조회 가능. PG 호출 없음, 다른 사람/없는 주문 동일 404, `no-store` |

- `reconcile`은 읽기 전용 버튼이 아니에요. 확인창에서 주문번호와 부수 효과를 확인해요.
- `refund`도 중복 발신 제한이나 과거 환불 확인을 우회하지 않아요. 미결 사유를 임의로 지우는 API는 없어요.
- 준비/검증 API가 409를 내도 별도 트랜잭션의 실패/불일치 기록은 남아요.

## 수동 대사 절차

**대상:** 응답을 잃은 환불, 부분 취소, 오래된 NOT_FOUND/READY, 이미 숨긴 광고의 PAID, 원금 불일치, 과거 REFUNDED 모순.
**권한:** 운영 담당자와 저장소 소유자의 **현재 건별 승인**, 정확한 TEST/LIVE 채널 확인이 먼저예요.

1. 원장을 GET으로 조회해요. 시도 id, 주문번호, 고정 원금, 사유, 마지막 조회/발신 시각을 확인해요.
2. 같은 채널의 PortOne 콘솔에서 주문번호와 모든 취소 이력·금액·완료 여부를 대조해요. 원본 개인정보/시크릿은 문서에 복사하지 않아요.
3. 단순 조회 실패라면 `대사·처리`의 부수 효과를 확인한 뒤 승인 범위에서 재조회해요.
4. 결제는 됐지만 서비스 제공이 불가능하고 아직 발신한 환불이 없다면, 전액 환불 승인을 받은 특정 시도에만 `환불 요청`을 써요.
5. 이미 발신 기록이 있는데 결말이 불명확하면 다시 누르거나 새 키를 만들지 않아요. 진행 중 취소가 없는지 PG 측에서 확인해요.
6. PG에서 미발신/확정 실패가 입증돼 추가 처리가 필요하면, 별도 승인 후 PortOne 콘솔에서 복구해요. 이후 GET 대사로 전체 취소를 확인해요.
7. NOT_FOUND/부분 취소/과거 누락 주문을 자동 종결시키지 않아요. 필요한 운영 증거와 정책을 정한 뒤 별도로 구현/처리해요. 원장 행 삭제나 수동 REFUNDED UPDATE로 우회하지 않아요.
8. 결과 문서에는 시도 id·상태·금액 대조 결과·검증 시각·승인 범위만 남겨요. 상태가 여전히 미결이면 폐업/탈퇴 차단도 유지해요.

> 주의: 이미 덮어써진 주문번호는 PortOne 기간별 거래 내역과 따로 대조해야 해요. 현재 매핑이 없는 웹훅을 광고로 추측하지 않아요.

- 기존 `REFUNDED` 표시는 이관 시 참고 값으로만 보관해요. PG 확인 전에는 완료로 인정하거나 자동 재환불하지 않아요.
- 미이관 광고도 폐업/탈퇴를 막으므로, 배포 직후에는 과거 광고 검토 요청이 늘 수 있어요.

## 배치 설정과 운영 영향

| 설정·동작 | 값 |
|---|---|
| `advertisement.payments.reconciliation-enabled` | 기본 `true`. 로컬 테스트에서는 `false` |
| `advertisement.payments.reconcile-delay-ms` | 기본 300000ms. 시작 5분 뒤 첫 실행 |
| 광고 기간 정리 | 기본 10분 간격, 서버 기동 30초 뒤 첫 실행 |
| 실행당 처리량 | 기존 광고 이관 최대 10건, 재조회 기한이 된 시도 최대 10건 |

- 기간 정리는 시작일이 지난 `PENDING_PAYMENT`/`PAYMENT_FAILED` 광고를 `CANCELLED`로 바꾸지만 결제 시도 원장은 보존해요. 브라우저도 이런 건에 결제 버튼을 보여 주지 않아요.
- 새 신청의 중복 검사는 오늘 이후 시작하는 결제 대기/실패 건만 막아요. 지난 신청이 정리 배치를 기다리는 짧은 구간이나 서버 재기동 뒤에도 새 신청을 영구 차단하지 않아요.
- 여러 인스턴스가 겹쳐도 행 잠금/lease로 같은 시도를 조정해요.
- 오래된 미결 건도 영구 실패로 버리지 않아요. `nextCheckAt` 순으로 처리하고, 사유가 있는 미결 건은 최소 5분 뒤 다시 확인해요.
- 자동 배치를 꺼도 사용자/관리자/웹훅 요청은 별개예요. 배치를 멈췄다고 모든 금융 쓰기가 멈추지는 않아요.

새 서버·유료 서비스는 없지만, 배포하면 DB 저장량과 제한된 PG 조회/스케줄러 작업이 늘어요. 여러 서버에서 실행할 때의 총 요청량, 인덱스와 잠금 대기는 운영에서 따로 측정해요.

## 배포 및 롤백 경계

- [ ] 승인된 TEST 주문으로 중복/역순 서명 웹훅, 환불 응답 유실, MySQL 인계/잠금을 확인한다.
- [ ] 새 `ad_payment_attempt` 테이블·unique/index와 `advertisement.status` 타입을 확인한다. [수동 DDL 런북](manual-ddl.md) 참고.
- [ ] 기존 광고의 현재 UID 이관과 과거 누락 UID 대사 계획을 확인한다. 과거 로컬 상태를 PG 증거로 간주하지 않는다.
- [ ] 배치/권한/개인정보 보존 정책과 실제 부하를 확인한다.
- [ ] 새 코드 CI·승인·배포 뒤 금융 원장을 읽기 전용으로 표본 대조한다.

> 주의: 구버전 백엔드는 새 상태와 원장을 몰라요. 새 금융 쓰기가 시작된 뒤에는 구버전으로 무조건 되돌리지 않아요.

장애 시 중복 실행을 피하고, 필요한 금융 쓰기 중단 범위·진행 중 PG 요청·원장 증거를 확인한 뒤 호환 가능한 전진 수정 또는 승인된 롤백을 골라요. 테이블/키/발신 기록은 지우지 않아요. 이미 보낸 환불은 코드 롤백으로 되돌릴 수 없어요.

- 모의 API 브라우저: 관리자 읽기와 명시적 환불 요청 분리, 환불 확인 중/완료 문구 구별.

이 검사는 실제 MySQL·PG 통신·서명 PAID 이벤트·운영 복원을 대신하지 않아요. 최신 통과 수치는 [품질 로드맵](quality-roadmap.md)에만 기록해요.
