# 메신저 헤더 정렬과 실행 서버 경로 오류

> 2026-09-14 `local-preview-all-changes` 로컬 프리뷰 후속. UI 수정과 실제 서버 오류의 미해결 범위를 구분한다. 커밋·통합·배포하지 않았다.

## 반영한 것

- 실제 목록과 DEV 예시가 `MessengerListHeading`을 공유한다. 제목·새로고침을 72px 헤더의 같은 중심에 두고, PC 닫기도 같은 높이 변수로 계산한다. 새로고침·닫기는 각각 44px 터치 영역이다.
- 새로고침은 조회 중 `aria-disabled`와 동작 관문으로 중복 호출을 막고 키보드 포커스·로딩 아이콘·접근성 이름을 유지한다. hover는 전경만 primary이며 불필요한 타일·눌림 효과를 넣지 않는다.
- 커버 사진 위에 겹치던 별도 RESERVE 제목을 제거했다. 접근성 제목 ‘메시지’는 시각적으로 숨겨 유지하며, 사진에 이미 들어 있는 브랜드와 관리자 카드의 실제 상대 표시 정보는 보존한다.
- 일반 사용자 새로고침은 내 대화만 조회한다. `BUSINESS`·`ADMIN`에만 기존 받은 문의 조회를 적용한다. 서버 권한을 넓히지 않았다.
- `chatListQueryPolicy`에서 목록·받은 문의·unread의 즉시 재시도를 끈다. 429를 제외한 4xx에서는 주기·포커스·재연결 자동 갱신도 멈춘다. 원래 오류와 명시적 재시도는 유지한다. 새 화면 진입/쿼리 재마운트 자체를 금지하는 정책은 아니다.
- 네트워크 장애·429·5xx는 목록 30초, 닫힌 런처 배지 60초 등 기존 주기를 유지한다. 열린 방의 조회·전송·읽음·폴링·경합 방어는 변경하지 않았다.

Core를 일괄 교체하지 않고 RESERVE 메신저 Pattern과 기존 색상·접근성·모션 규칙을 사용했다. 동결 스냅샷은 변경하지 않았다.

## 실제 로딩 오류: 확인된 사실

별도 Chrome 확인용 탭에서 기존 로그인 세션으로 관측했다. 토큰·쿠키·대화 본문은 출력하지 않았다.

| 읽기 요청 | 실제 HTTP 응답 |
|---|---|
| `GET /api/member/me` | 200 |
| `GET /api/chat/conversations?page=0` | 404 |
| `GET /api/chat/store-inbox?page=0` | 404 |

목록 404 본문은 ‘요청하신 경로를 찾을 수 없습니다.’다. 현재 `GlobalExceptionHandler`의 미등록 경로 예외 메시지와 일치한다. CORS/다운로드 실패가 아니라 HTTP 응답이 돌아온 경우다. 수동 새로고침에서도 각 목록 요청 1건씩 같은 404를 재현했다.

현재 `chatService`·API 상수와 `ChatApiController` 소스 경로는 일치한다. 디스크의 컴파일된 컨트롤러에도 해당 매핑이 있다. 8080 프로세스는 9월 12일부터 실행 중이고 디스크 컨트롤러는 9월 14일에 갱신돼 **실행 서버에 현재 코드가 반영되지 않았을 가능성이 높다.** 다만 DevTools 재로딩 가능성이 있어 프로세스 시작 시각만으로 특정 원인을 확정하지 않는다. 실제 JVM 클래스패스·컨트롤러 등록 목록·재시작 후 정상 응답은 확인하지 못했다.

따라서 프론트 보정이나 채팅 내역 삭제를 이 경로 404의 해결로 보고하지 않는다. 지원 방 GET은 방 생성/읽음을 겸할 수 있어 이번 재확인에서는 호출하지 않았다. 이전 지원 GET 404는 [이전 기록](support-inquiry-and-chat-reset-2026-09-14.md)과 구분한다.

## 검사 경계

- 메신저 관련 6개 테스트 파일의 초기 131개가 통과했다. 이후 배지 정책 테스트 2개를 추가하고 `MessengerShell.test.jsx`·`chatListQueryPolicy.test.js` 20개를 다시 실행해 모두 통과했다. 새로고침 포커스 관문 보정 뒤 `MessengerContent.test.jsx`·`MessengerVisuals.test.jsx` 59개도 다시 통과했다. 중복을 제외하면 133개이며 전체 프론트/백엔드 통합 검사는 아니다.
- 변경 JSX·정책·테스트·DEV 예시 ESLint: 경고 0.
- 실제 Chrome 목록 헤더에서 새로고침/닫기 중심 높이 차이는 약 0.4px이었다. 커버의 중복 제목 제거도 실제 화면에서 확인했다.
- 실제 새로고침 대기 중에도 해당 버튼에 키보드 포커스가 남고 Escape로 닫힌 뒤 런처에 복귀함을 확인했다. 중복 클릭·Enter는 컴포넌트 테스트에서도 호출하지 않는다.
- 별도의 무API DEV 예시에서 960×900 PC 패널과 390×844 모바일 페이지의 가로 넘침이 없고 제목/새로고침이 같은 중심임을 확인했다. PC 새로고침/닫기 차이는 약 0.4px, 모바일 제목/새로고침 차이는 0px이다. 예시 대화는 실제 계정 왕복·조회 성공 증거가 아니다.
- 실제 404 수동 재시도 뒤 후속 작업 중 추가 채팅 자동 응답은 관측되지 않았다. 목록/배지의 4xx 중단·일시 장애 유지·수동 성공 후 재개는 별도 정책 테스트로 확인했다.
- 사용자 Chrome 창 크기와 나무위키 탭은 변경하지 않았다. 확인용 탭만 정리하고 별도 IAB 임시 크기 override는 종료 전에 해제한다.
- 실제 정상 대화 조회·두 계정 전송/답변·재접속·운영 DB·배포 검증은 실행하지 않았다. 전체 production build도 이번 국소 수정에서는 실행하지 않았다.
- `index.css`·`feature-surfaces.css` PostCSS 파싱/잘못된 한글 selector 검사와 변경 tracked 파일 `git diff --check`, 새 파일의 후행 공백 검사도 통과했다.

## 다음 관문

1. 실행 중인 로컬 백엔드의 설정/경로 반영을 확인한다. 재시작은 `ddl-auto: update`와 외부 작업 scheduler 영향 경계를 확인한 뒤 진행해야 한다.
2. 현재 대화 기록은 삭제하지 않았다. 기존 초기화 요청은 계정 범위·복구 수단을 확정한 뒤 별도로 처리한다.
3. 실제 목록·SUPPORT 조회가 정상화된 뒤 첫 문의 안내와 사용자의 명시적 전송·관리자 답변을 검증한다.
