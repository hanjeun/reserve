# API 버전 관리

제품 JSON API를 `/api/v1/...`로 옮기는 방식과 릴리스 순서예요. 아직 도입 전 계획이고, 실제 코드와 배포 상태가 이 문서보다 우선해요.

## 결정

- 새 표준 경로는 `/api/v1/...`이에요. `/v1/...`만 쓰면 SPA·정적 파일 경로와 API 경계가 흐려져요.
- **API 버전 `v1`과 앱 릴리스 버전(`v2.x.y`)은 별개예요.** API 버전은 외부 계약 세대, 앱 버전은 배포 묶음이에요.
- 기존 `/api/...`는 `/api/v1/...` 도입과 동시에 없애지 않아요. 한 릴리스 이상 두 경로를 같은 컨트롤러에 연결하고 프론트를 먼저 옮겨요.
- URL만 바뀌고 응답 계약이 같은 동안에는 컨트롤러·서비스를 복제하지 않아요.
- 버전 파일(`frontend/package.json`, `backend/build.gradle`)은 릴리스 후보를 고정할 때 CHANGELOG와 함께 올려요.

## 구현 방식

`/api/` 문자열은 프론트와 백엔드 곳곳에 있고, 결제 웹훅·인증 갱신·보안 매처·CSP 수집처럼 단순 치환으로 끝나지 않는 경로도 섞여 있어요. 일부만 먼저 바꾸면 로그인·결제·공개 조회 동작이 환경별로 갈라질 수 있어요.

Spring Boot 3.5.6(Spring Framework 6)에는 Spring Framework 7의 네이티브 API 버전 기능이 없어요. 경로 버전 때문에 Boot 4로 먼저 올리지는 않고, 다음 방식으로 해요.

1. `ApiPaths`에 `LEGACY_PREFIX = "/api"`, `V1_PREFIX = "/api/v1"`를 둬요.
2. 각 제품 컨트롤러의 클래스 매핑에 구 경로와 v1 경로를 함께 선언해요.
3. Spring Security 공개·인증·관리자 매처에 두 경로를 같은 정책으로 추가해요.
4. 프론트 `API_ENDPOINTS`를 `/api/v1`으로 한 번에 전환해요.
5. MockMvc 계약 테스트로 구 경로와 v1 경로의 상태·응답 본문·권한을 대조해요.

> 주의: nginx rewrite나 서블릿 필터로 URI를 몰래 바꾸지 않아요. 로컬·테스트·운영 라우팅이 달라지고, Spring Security·감사 로그에 원 요청과 실제 핸들러가 다르게 남기 때문이에요.

## 대상과 예외

v1 대상:

- 가게, 예약, 리뷰, 즐겨찾기, 광고, 결제, 회원, 사업자 인증
- 채팅·문의·메일함과 관리자 JSON API
- 주소 검색 프록시

별도 검토가 필요한 경로:

| 경로 | 처리 |
|---|---|
| PortOne 웹훅 | 외부 콘솔 주소를 바꾸기 전에 구 경로와 v1 경로를 장기간 병행 |
| OAuth 시작·콜백 `/oauth2/...` | 제품 REST API 버전과 분리 |
| `/actuator/...`, 정적 자산, SPA 라우트 | v1 대상 아님 |
| CSP 보고 수집 | 브라우저 정책 헤더와 함께 바뀌므로 별도 호환 기간 |

## 릴리스 순서

1. **API v1 도입 2.x 마이너**: `/api/v1`과 `/api`를 병행하고 프론트를 v1로 전환해요. 구 경로는 지우지 않아요.
2. **호환 종료 릴리스**: 접근 로그와 외부 연동 확인에서 구 경로 사용이 없고 공지 기간이 끝난 뒤 제거해요. 공개 계약을 깨는 제거라면 앱 메이저 버전으로 처리해요.

API v1·AI 답변·MFA·새 광고 정책 같은 큰 변경은 검증 가능한 마이너 묶음으로 나눠 내요. 패치 버전은 이미 배포된 버전의 회귀 수정에만 써요.

## 도입 관문

- 모든 컨트롤러 경로와 프론트 호출 경로의 자동 대조
- 공개/회원/사업자/관리자 권한별 구 경로·v1 경로 MockMvc 계약 테스트
- 로그인 갱신, 파일 업로드, 주소 검색, 결제 준비·검증·환불, PortOne 웹훅 회귀
- Vite 개발 프록시와 nginx 운영 프록시에서 같은 경로 확인
- PC·모바일 핵심 흐름과 production build
- 구 경로 사용량을 구별할 수 있는 서버 로그 또는 메트릭
