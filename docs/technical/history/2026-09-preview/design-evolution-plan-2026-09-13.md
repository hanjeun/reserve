## 1. 헤더와 페이지 메뉴

- PC·모바일은 현재 PC의 RESERVE 워드마크 하나를 공유한다. R 로고로 바꾸는 반응형 분기는 제거한다.
  현재 워드마크는 Pretendard 22px/850/-0.8px 자간의 텍스트 표현이다. 정사각 `RESERVE_logo.png`를
  새로 편집하거나 투명 벡터 로고를 제작한 것은 아니다.
- 왼쪽은 브랜드, 오른쪽은 **검색 아이콘 → 기존 둥근 프로필/페이지 메뉴**다. 높이 64px,
  검색과 프로필 동작 영역 44px, 중립 opacity hover·키보드 focus-visible·모션 감소 정책을 유지한다.
  일반 로고·텍스트는 scale로 누르지 않는다. 사진/3D 효과와 scroll-snap 메인 배너의 예외는 별도 패턴이다.
- 검색 아이콘은 실제 `/search` 링크다. 결과 목록의 검색어는 다시 열 때 입력칸에 넘기고,
  검색 화면에서 취소하면 진입 화면으로 돌아간다. 검색 실행용 파란 버튼이나 본문 중복 입력을 추가하지 않는다.
- 주요 탐색 화면은 `홈 · 탐색 · 혜택 · 웨이팅 · 피드` 탭을 유지한다. 하위 결과/상세/계정에서는 탭을
  숨기되 헤더는 유지한다. 모바일 하위 화면은 뒤로가기와 워드마크를 함께 표시하고 PC는 뒤로가기를 숨긴다.
- 프로필의 로그인·약관·역할별 페이지 메뉴와 메신저 단일 런처는 보존한다. 메뉴/메시지 아이콘으로
  같은 진입점을 반복하지 않는다. 모바일을 PC 중앙의 고정 폭 앱 프레임으로 만들지 않는다.

### 추가 아이콘은 실제 기능에 맞춰 선택

이번에는 추가하지 않는다. 공간을 채우기 위한 아이콘은 목적을 흐린다.

| 후보 | 판단 | 추가 시 조건 |
|---|---|---|
| 내 예약 캘린더 | 하나가 꼭 필요하면 1순위. 예약 확인·QR·결제라는 실제 재방문 행동 | `/my-reservations` 링크와 기존 로그인 복귀 가드 사용. 새 예약 생성 버튼과 구분 |
| 알림 벨 | 중장기 후보 | 예약 변경·웨이팅 호출 등을 모아 보는 알림함과 실제 unread·읽음 처리 구현 뒤. PC 세션 알림만으로 알림함이 있다고 표현하지 않음 |
| 즐겨찾기 하트/북마크 | 현재 프로필 메뉴와 중복이므로 보류 | 실제 이용 빈도로 최상위 진입이 필요한지 확인 뒤 선택 |
| 햄버거 메뉴 | 기존 프로필 페이지 메뉴와 중복이므로 보류 | 프로필과 전역 탐색 메뉴의 역할을 분리하기로 결정한 경우에만 |
| 메시지 | 별도 헤더 아이콘은 보류 | 현재 채널톡형 런처와 PC 패널·모바일 화면을 유지 |

## 2. 참조를 하나의 쇼핑몰 UI로 통일하지 않는다

다음은 RESERVE에 맞춘 **설계 제안**이다. 외부 서비스의 브랜드·사진·전체 DOM/CSS를 가져오는 계획이 아니다.

| 화면 성격 | 주 참조 | 가져올 구조 | 그대로 가져오지 않을 것 |
|---|---|---|---|
| 전역 헤더·전용 검색 | [KREAM](https://kream.co.kr/) | 브랜드/탐색과 검색 액션 분리, 전용 검색에 탐색 보조 정보 배치 | 쇼핑 장바구니·상품 브랜드 모델, 전 화면 네모 검색 입력 강제 |
| 홈·목록·예약 상세·내 예약 | [캐치테이블](https://app.catchtable.co.kr/) | 사진/이름/소개/평점 위계, 작은 필터, 예약 상태 중심의 행형 요약 | 음식 업종 전용 조건, PC 고정 모바일 폭, 기존 카드 비율을 바꾸는 일괄 크롭 |
| 혜택·피드 | [KREAM STYLE](https://kream.co.kr/social)와 캐치테이블 탐색 탭 | 콘텐츠의 발견 → 상세 → 가게/예약 연결, 명료한 기간·조건·출처 | 가짜 할인·인기·리뷰·광고 미표기, 기능 없는 좋아요 |
| 입력·작업 도구 | [Ant Design Form](https://ant.design/components/form/), [Table](https://ant.design/components/table/)와 현재 공통 컴포넌트 | 입력/검증/상태 의미, 필터·정렬·서버 페이지네이션·작업 밀도 | 공개 탐색 배너/물체 아이콘을 관리자·사업자 작업 화면에 반복 |

참고 확인 범위: KREAM 공개 홈과 검색 레이어의 검색 액션·이슈·갱신 시각 있는 인기 검색어,
캐치테이블 공개 홈의 탭·사진·분야 바로가기를 브라우저에서 확인했다. KREAM STYLE은 공개 경로를
확인했고, 로그인 후 내 주문/예약·쿠폰·관리 화면까지 실측한 것은 아니다. 사용자 제공 이미지는
디자인 참고 자료이며 기능 구현이나 외부 자산 사용 권한의 증거가 아니다.

## 3. 기존 페이지를 하나씩 전환

초기 App.jsx의 명시적 URL 24개를 기준으로 묶었다. 소식 상세 `/benefits/:id` 추가 후 현재는 25개다.
관리자/사업자 내부 탭·모달은 URL 수보다 많으므로 페이지 수를 완료율로 사용하지 않는다.
아래는 대규모 전환 백로그다. 최신 배치의 로딩/오류 표시 보완은 [전수 점검](skeleton-audit-2026-09-13.md)에서 별도로 기록한다.

| 순서 | 실제 페이지 | 다음 디자인 작업 | 반드시 보존할 것 |
|---|---|---|---|
| A1 | `/` | 사진·서비스·작은 추천 카드의 치수와 상태를 공식 패턴으로 정리 | PC/모바일 전용 배너 원본, API 실패/0건 구분, 실제 평점 |
| A2 | `/search` | 전용 검색을 하나의 표준 입력/닫기/카테고리 패턴으로 정리. 인기 검색어는 아래 별도 기능 | Enter/키보드 제출, 자동 포커스·취소 복귀, 정적 빠른 검색과 실제 인기의 구분 |
| A3 | `/stores` | 컴팩트 오른쪽 필터·원본 카드·12건 페이지네이션 패턴 확정 | 검색/분야/정렬/페이지 URL, 위치 권한·실패 복귀, 자연 이미지 비율 |
| A4 | `/store/:id` | 가게 정보 위계, 섹션 탭/구분, 예약 CTA와 문의의 주/보조 관계 | 서버 예약 가능 조건·금액, 원본 사진, 기존 채팅·지도·리뷰 경계 |

| B3 | `/my-favorites` | 탐색 카드/요약 행 중 사용 목적에 맞춰 선택, 빈/실패/해제 상태 정리 | 원본 이미지, 실제 찜 상태·로그인 가드 |

| C3 | `/signup/social`, `/oauth2/callback` | 약관과 처리 중/실패 화면의 밀도·브랜드 통일 | 소셜 동의·인증 경계, 콜백에서 새 전역 탐색 단계를 만들지 않음 |

| D2 | `/my-stores` | 소유 가게 요약·관리 진입·등록 빈 화면 정리 | 가게 상태·수정/폐업 권한, 일반 추천과 관리 액션 구분 |
| D3 | `/business` | 예약/통계/광고/상담의 작업 도구 패턴으로 정리 | 서버 검색/건수/페이지·금융 상태·오류 출처, 필요한 데이터 밀도 |
| D4 | `/admin` | 내부 탭별 상태/툴바/테이블/확인 모달을 마지막으로 전환 | ADMIN 가드·대사/환불/신고 근거·감사로그·부분 실패 표시 |
| E | `/benefits`, `/benefits/:id`, `/waiting`, `/feed` | 혜택 기획전 v2를 우선 설계하고 웨이팅 → 피드로 진행 | 소식 v1을 쿠폰 발급으로 표현하지 않음. 준비 중을 실제 대기 접수·게시글로 포장하지 않음 |

페이지를 전환할 때는 기본/hover/active/선택/disabled/로딩/0건/오류와 모바일·PC 골격을 함께 기록한다.
폼 오류·날짜 선택·브랜드 CTA의 상태색은 중립 탐색 hover와 다르다. 모든 테두리/선택색/모서리를
일괄 삭제하거나 모든 요소를 같은 카드/같은 높이로 만드는 방식은 사용하지 않는다.

## 4. 인기 검색어 — 계획만

- 검색 전용 화면 안에서 `서비스 찾기 / 빠른 검색 / 인기 검색어` 역할을 나눈다.
  PC는 짧은 다열 순위, 모바일은 짧은 한/두 열 목록을 제안한다. 갱신 시각·집계 범위를 표시한다.
- 실제 집계 API가 생기기 전에는 현재 QUICK_SEARCHES를 인기 순위로 이름만 바꾸지 않는다.
  트래픽이 적으면 ‘빠른 검색’만 보여 주거나 인기 영역을 숨긴다. 순위 변화·NEW 배지를 꾸며내지 않는다.
- 수집은 명시적 검색 제출 기준으로 설계한다. 타이핑 입력마다 저장하지 않고 봇/반복 요청·중복·
  민감한 자유 텍스트·금지어의 공개 노출을 검토한다. 집계 기간·최소 노출량·원문 보존/삭제는 별도 결정한다.
- v1은 일정 주기 집계와 작은 캐시를 검토하고 전용 검색 서버/Redis를 선행 요구하지 않는다.
  자동완성·최근 검색·개인화는 서로 다른 기능이며 이 항목과 묶어 자동 구현하지 않는다.
- 선택한 검색어는 기존 `/stores?keyword=…`로 연결한다. 데이터/API·집계·보존 정책 승인이 구현 선행 조건이다.

## 5. 혜택 → 웨이팅 → 피드

디자인 시안은 사용자 요청 순서인 **혜택 → 웨이팅 → 피드**로 진행한다. 실제 서비스 구현 순서는
웨이팅의 도메인/호출 정책 확정 여부에 따라 조정할 수 있다. 소식·혜택 안내 v1은 아래 최신 배치에서 연결했다.
쿠폰·웨이팅·피드 모델과 새 테이블은 이번에 만들지 않았다.

| 탭 | v1 디자인/기능 제안 | 선행 결정 |
|---|---|---|
| 혜택 | 지역/서비스 필터, 기간·대상·조건이 읽히는 혜택 목록/상세, 해당 가게로 이동 | 공지/홍보와 실제 쿠폰의 구분. 실제 쿠폰은 발급·대상·사용·취소/환불 연계 모델을 별도 설계 |
| 웨이팅 | 가능 가게 탐색 → 인원/접수 → 내 대기 현황 → 호출/입장/취소, 사장님 대기열 | 원격/현장 접수, 영업 단위·중복 방지·순번·호출 만료·노쇼·알림. 예상 시간은 근거 없이 표시하지 않음 |
| 피드 | 가게/서비스 이야기와 소식의 이미지/텍스트 목록 → 상세 → 가게 연결, 초기는 운영/사업자 콘텐츠 우선 제안 | 공개 읽기·작성/편집 권한·광고 표기·신고/모더레이션·차단. 사용자 게시·댓글/좋아요는 별도 확장 |

현재 backend의 promotion은 가게 홍보글이지 쿠폰 원장이 아니다. 최신 배치에서는 별도 공개 GET 목록/상세와
최소 응답 DTO만 추가했다. 기존 작성자 전용 promotion API/CUD와 community의 인증 경계는 유지한다.
community 전체를 공개 피드로 바로 연결하지 않는다.
검색한 backend에는 매장 웨이팅 도메인이 없으며 관리자 상담 `waiting-count`를 재사용하지 않는다.

## 6. 디자인 시스템은 보존 → 확장 → 검증 → 이동

1. **보존:** 변경 전 토큰/공통 컴포넌트/CSS/문서·의존성/라이선스·브랜드 자료를 hash manifest와 ZIP으로
   동결한다. 미커밋 변경이 포함된 현재 프리뷰 보관본이며, 과거 순수 구버전이나 운영 배포본이라고 표현하지 않는다.
2. **분류:** 일반 Core(색·타입·간격·상태·접근성·Button/Form/Card)와 RESERVE Patterns(헤더/탐색/가게/예약/
   메신저/업무 도구)를 나눈다. 현재 글로벌 CSS도 여러 역할이 섞여 있으므로 파일명만 보고 범용으로 이식하지 않는다.
3. **확장:** 기존 토큰을 모두 교체하지 않는다. 필요한 surface/layout/navigation 패턴 토큰을 이름 있게
   추가하고 현재 일반 버튼·폼·날짜·선택/오류·focus-visible·다크/포인트색·모션 감소 계약을 유지한다.
4. **두 번째 사용처:** 같은 패턴이 두 번째 실제 페이지에 필요할 때 공통 컴포넌트로 추출한다.
   페이지별 inline 보정·global 선택자 덧칠·3개 초과 prop 분기 대신 의미 있는 형제 패턴을 사용한다.
5. **표본 후 이동:** 예약 요약/입력/상태 결과/업무 테이블 등 대표 화면 하나씩 합의한 뒤 위 인벤토리를
   한 화면씩 전환한다. 각 배치에 실제 PC·모바일 확인과 변경 대상 검사를 하고 완료/미확인을 기록한다.
6. **신규 프로젝트:** 동결 스냅샷은 복구/참고용이다. 이후 별도 generic starter에 auth/API/S3/브랜드/역할
   결합을 제거하고 설치 의존성·라이선스·샘플·상태 문서를 갖춘 뒤 사용한다. 현재 ZIP은 바로 실행/공개 배포할 패키지가 아니다.

헤더 추가 아이콘과 기능 정책이 없는 새 도메인은 별도 사용자 확인 뒤 정한다. 전체 기존 화면과
새 탭을 일괄 개편하지 않는다. 기존 큰 기능 순서/통합·배포 관문은
[큰 단계 진행 현황](roadmap-progress-2026-09-13.md)을 유지한다.

## 7. 후속 광고·메신저·저장소 요청

후속 배치에서는 메신저 런처를 흰 배경·브랜드 블루 아이콘/X와 선택형 사진으로 수정했다.
광고의 작은 소개 카드·단일 플로팅 영역 조정과 새 DB 검토는
[별도 검토 문서](channel-style-advertising-and-storage-review-2026-09-13.md)에 제안으로 등록했다.
광고 집계/과금·운영 인프라·새 DB를 구현하거나 동결 소스 스냅샷을 덮어쓰지 않았다.

## 8. 최신 구현 배치 — 소식·혜택 안내와 로딩

- 헤더와 탐색 탭은 같은 `--c-header-bg` 및 20px 블러를 사용한다. 라이트 90%·다크 85% 면으로,
  완전 투명으로 만들어 아래 콘텐츠와 겹쳐 읽기 어렵게 만들지는 않는다. 높이 64px+44px은 유지한다.
- 혜택 목록은 작은 썸네일·가게명·제목·요약·등록일의 행이다. 모바일 1열, 900px 이상 2열이며
  서버 12건 페이지네이션을 기존 AntD 번호 UI로 넘긴다. 소식 상세는 탭을 숨기고 가게/목록으로 연결한다.
- 공개 `/api/promotions/public`과 `/api/promotions/public/{id}` GET만 추가했다. 목록·전체 건수·상세에
  ACTIVE·미삭제 가게 조건을 동일하게 적용한다. 작성자/임의 홍보 이미지/조회·좋아요 수는 공개 DTO에서 제외한다.
  상세는 조회수를 변경하지 않는다. 본문은 React 텍스트로만 표시하며 원문 HTML을 실행하지 않는다.
- 기존 가게 원본 사진 중 소유 CDN/로컬 업로드 경로만 읽고 실패 시 보유 R 자산으로 대체한다.
  외부 사이트 사진·코드를 가져오거나 쿠폰 할인·유효기간·재고를 꾸며내지 않았다.
- 25 URL/24 페이지 파일 및 관리자·사업자 내부 탭의 최초 조회·재조회·작업 중·실패·0건을 구분해 점검했다.
  페이지 청크, 가게 수정, 예약 날짜/시간, 메신저 목록/방의 골격을 보완하고 일부 실패→빈 목록 오표시를 분리했다.
  로그인/저장/전송/결제 검증의 실제 진행 상태와 인증·예약·환불 조건은 보존한다.
- 변경 전 108개 소스 ZIP은 그대로 유지했다. 기존 Core의 시각 계약을 교체하지 않고 RESERVE Patterns만
  점진 확장한다. 페이지별 상세 현황·미해결 항목·실측·검사 경계는 [전수 점검](skeleton-audit-2026-09-13.md)이다.

위 목록은 9월 13일 소식/로딩 배치의 이력이다. 최신 순서는 안정화·명시적 회귀 확인 → 승인 후 최신 dev 통합 →
**혜택 기획전 v2** → 상세/내 예약 대표 패턴 → 나머지 화면 전환 → 웨이팅 접수·호출/취소 → 피드 게시/신고다.
Git 승인 전에는 독립적인 프리뷰 디자인 작업을 진행할 수 있다. 실제 쿠폰과 인기 검색어는 독립 백로그로 유지한다.
운영 배포·실제 계정 쓰기·알림 발송·새 DB 도입은 이 로컬 배치에 포함하지 않는다.

## 9. 메신저·홈 정리와 다음 시안

메신저 하단 `홈 · 대화 · 설정`, 관리자 문의 카드, 상대별 실제 대화 행, 알림의 설정 이동과
PC 420px 단일 패널을 구현했다. 사용자 확정은 여러 상대와 각각 대화이며 그룹방 확장은 아니다.
홈 우측 ‘현재 위치로’는 명시적 클릭에서 기존 위치 훅/거리순 목록을 사용한다.
일반 헤더·탭·텍스트의 scale을 제거하고 사진/3D 효과를 보존했다. 홈 간격은 섹션20·내용16·구분선4px이다.
실행/미실행과 정확한 참고 범위: [정리 기록](messenger-home-refinement-2026-09-13.md).

### 배너 번호 — 계획만, 현재 동작 보존

추천은 **현재/전체 번호 유지 + 시각적으로 작은 표시 + 조작 의미 분리**다. 다음 배너가 있다는 단서를
완전히 없애지 않는다. 현재 `2/3 >`는 다음 배너 버튼인데, 캐치테이블의 ‘전체’는 전체 배너 보기여서 의미가 다르다.
번호 면은 약 28px로 작게 보이되 조작 영역은 최소44px을 유지하는 시안을 먼저 확인한다.
모바일 스와이프와 PC 다음/이전 조작, 마지막→처음, reduced-motion·번호 동기화를 함께 설계한다.
전체 배너 모음을 구현하기 전에는 ‘전체’라는 버튼을 붙이지 않는다. 이번엔 번호/CSS/동작을 수정하지 않았다.

### 지역 설정 — 계획만, 현재 전체 지역 링크 보존

- 캐치테이블의 작은 관심지역 선택 레이어처럼 **주요 지역 → 시·도/세부 지역 → 초기화/적용**을 제안한다.
  PC는 약640px 모달, 모바일은 90svh 내 시트와 고정 적용행으로 시안을 비교한다. 두 리스트의 내부 스크롤을 분리한다.
- v1은 단일 관심지역을 권한다. 적용 전 임시 선택과 실제 필터를 분리하고 취소 시 기존 상태를 보존한다.
  전체 지역/현재 위치(거리순)/선택 지역 필터는 서로 다른 의미다. 위치는 클릭에서만 요청하고 거부·미지원 대안을 유지한다.
- 현재 전체 지역은 `/stores` 링크이며 관심지역 저장·지역 계층/API·지역별 가게 count는 구현되어 있지 않다.
  주소 문자열에서 지역을 임의 추정하기보다 지역 코드/분류와 데이터 보정·필터 API부터 확정한다.
  계정 설정 저장·스키마/기존 가게 backfill·운영 반영은 별도 승인 범위다.
- 둥근 사진 바로가기는 소유/허가된 지역 자산을 확보한 뒤 넣는다. 실제 집계가 없으면 ‘인기 지역’ 대신
  편집 선정 ‘주요 지역’으로 표기하며 수치·인기 순위를 꾸며내지 않는다. 음식 전용 지역 분류를 범용 업종에 강제하지 않는다.

다른 공개 화면도 같은 종류의 섹션에서20/16/4px 패턴을 검토하되, 두 번째 실제 사용처와 검증 뒤에 추출한다.
업무 화면·폼·스켈레톤의 회색 면은 별개 의미이므로 일괄 축소하지 않는다.

## 10. 기초 레이아웃 회귀 보정 (2026-09-14)

확장 전에 사용자 보고 배너·탈퇴 확인창·모바일 등록/수정 폼을 우선 보정했다.
홈 메인 배너는 scroll-snap 좌표를 지키는 투명도 피드백으로 분리하고, PageContainer는 패딩 포함
너비로 통일했다. 등록·수정 공통 폼만 모바일44px·라벨22px·작은 정책 두 칸을 적용했다.
확인창은 긴 본문 스크롤과 고정 버튼 행을 보강했다. 탈퇴 차단/실제 실행 조건과 폼 저장 기능은 유지한다.
실제 계정에서 완전히 안 보이는 탈퇴창 원인은 확정하지 않았으며 인증/API 없는 표본에서만 확인했다.

[실측·29개 테스트·시각 증거·미확인 범위](layout-regressions-2026-09-14.md).
Core 전체/동결108개 소스 ZIP은 일괄 교체하지 않는다. §9의 번호 시안과 지역 설정은 여전히 계획이고,
이번 안정화로 혜택·웨이팅·피드·광고·저장소 확장이나 운영 반영을 완료 처리하지 않는다.

## 11. 최신 혜택 목표 — 기획전 v2 (첫 UI 구현·조건 탐색 계획)

사용자 제공 캐치테이블 혜택 화면의 핵심은 단순 소식 행이 아니라 **기획전 → 주요 혜택 → 조건별 탐색 → 가게**다.
공개 소식 v1에 이어 브랜드 기획전·소식 카드·서비스별 일반 가게 탐색의 첫 UI를 로컬 구현했다.
조건별 혜택 탐색의 완성판은 아니며, 실제 쿠폰은 뒤로 미룬다는 선택을 유지한다.
아래 표는 최종 목표이고 첫 배치의 실제 범위/미확인은 [최신 체크포인트](benefits-campaign-progress-2026-09-14.md)다.

| 영역 | RESERVE에 적용할 구조 | 데이터/보존 조건 |
|---|---|---|
| 기획전 배너 | RESERVE 브랜드 면·분명한 제목·짧은 설명. 모바일 세로 위계, PC는 별도 넓은 편집 레이아웃 | 외부 서비스 로고/이미지 복사 금지. 실제 캠페인 기간/할인이 없으면 임의 ‘이번 달 한정’ 문구를 넣지 않음 |
| 주요 혜택/소식 | 소유 사진·가게·안내 제목의 짧은 카드에서 상세/가게로 연결 | 운영 선정과 실제 인기 순위를 구분. 가게 상태·권한과 공개 가능한 본문 유지 |
| 혜택 종류 | 할인·기념일·메뉴/서비스 등 실제 조건 분류가 생긴 뒤 표시 | 기존 promotion.category는 업종이다. 혜택 종류와 별도 필드/계약이 필요하며 추정 분류하지 않음 |
| 지역·서비스 필터 | 서비스는 현재 업종 모델, 지역은 정규 코드/필터 API와 연결 | 현재 문자열 주소를 임의 지역 필터로 바꾸지 않음. 전체 지역과 현재 위치/거리순을 구분 |
| 가게 목록 | 실제 조건에 맞는 가게/소식과 실제 전체 건수·12건 페이지 번호 | 가게 원본 사진·예약 조건·실제 평점·0건/실패/로딩 구분. PC는 모바일 고정 폭 프레임을 사용하지 않음 |
| 상세 | 기간·대상·조건·출처가 있는 안내와 가게로 이동하는 단일 주 행동 | 발급/사용 원장이 없으면 ‘쿠폰 받기’ 버튼을 만들지 않음. React 텍스트 경계 유지 |

선행 작업은 혜택 분류·기간·조건·캠페인 선정 계약을 정하고 기존 홍보글의 값을 보정하는 것이다.
새 필드/조회 API·스키마 반영은 이 계약이 확정된 후 별도 구현·검증한다. 그 전에는 현재 실데이터로 가능한
브랜드 기획전/소식·서비스 탐색만 제공하고 없는 필터·할인·기간을 가짜 UI로 채우지 않는다.

골격/간격/작은 필터/번호 UI는 기존 Core를 유지하며 RESERVE Patterns에서 점진 확장한다.
모바일·PC에서 기본/hover/키보드/로딩/0건/실패/페이지 경계를 함께 확인한다. 신규 starter나 동결 ZIP은 변경하지 않는다.

첫 UI는 현재 DTO로 가능한 범위만 연결한다. 일반 가게 domain/정렬은 소식이나 혜택 적용 조건이 아니며
`page`와 `storePage`를 분리했다. 켜진 로컬 공개 소식 API의HTTP404는 실패로 유지했고 백엔드 재시작은 실행하지 않았다.
성공/0건/여러 페이지는 지정 회귀·개발 전용 예시 검증이며 실제 공개 데이터 연결 완료로 계산하지 않는다.

## 12. 이전 후속 — 작은 콘텐츠·사진 카드·톡 커버

큰 세로 블루 배너는 현재 목표에서 제외했다. 혜택 상단은 작은 탐색 콘텐츠3개이며 소식과 일반 가게는
모바일2열·PC3열이다. 조건별 혜택/기간/쿠폰 모델은 §11의 별도 계획으로 남긴다.
홈 추천은 작은 사진 카드(모바일2열·중간폭3열·PC4열)와 같은 골격으로 전환했다.
톡은 RESERVE 커버·문의 카드 하나·고정 footer, 실제 상대 목록은 대화 탭으로 정리했다.
내부 커버 prop과 실제 활성 지원 ADMIN의 사진 표시 계약을 추가했지만 업로드 설정·관리자 배정 UI는 없다.

최신 [구현/실측/검사 경계](messenger-and-discovery-refinement-2026-09-14.md)가 앞선 큰 배너·가로 추천 행 설명을 대체한다.
이전 HTTP404는 당시 기록이며 이번 공개 소식 GET은 HTTP200·실제 화면 정상0개였다. 재시작 원인을 추정하지 않는다.
실제 지원 프로필/두 계정 대화 검수 → 상세/내 예약 대표 패턴 → 나머지 화면 전환을 다음 순서로 유지한다.
동결 ZIP·Core·실제 쿠폰 후순위·배너 번호 계획·지역/웨이팅/피드/광고/첨부/AI의 권한 관문은 유지한다.

## 13. 최신 후속 — 가로 혜택 배너·현재 사용자 설정 사진

최신 사용자 사진에 따라 혜택의 작은 메뉴3개·반복 설명·일반 가게 목록을 제거하고,
실제 공개 소식을 **사진 배경·큰 가게명·실제 제목 티켓**의 가로 배너로 보여준다.
모바일/중간폭은1열,900px부터2열이며 소식 상세·12건 페이지·조회 실패/재시도를 보존한다.
일반 가게는 `/stores`에서 탐색하며 혜택 제공 여부를 추정하지 않는다. 조건별 혜택/쿠폰 모델은 여전히 계획이다.

메시지 설정에는 관리자 사진이 아니라 현재 사용자 프로필 사진을 표시한다. 실제 알림 컨트롤이 없는
환경 섹션·모바일 PC 안내·초안 보존 설명을 없앴다. 지원 ADMIN/런처/커버 사진 계약은 그대로다.
현행 [구현·검사·실제 계정 미확인 경계](benefit-banners-and-account-avatar-2026-09-14.md)를 따른다.
기존 스냅샷·Core·실제 두 계정 검수와 dev 통합 승인·운영 반영 관문은 유지한다.
