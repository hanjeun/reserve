# API 버전 관리

제품 JSON API에 `/api/v1/...` 경로를 도입할 때 따르는 규칙이에요.

## 규칙

- 표준 경로는 `/api/v1/...`이에요.
- API 버전 `v1`과 앱 릴리스 버전(`v2.x.y`)은 별개예요. API 버전은 외부 계약 세대, 앱 버전은 배포 묶음이에요.
- 기존 `/api/...`는 한 릴리스 이상 `/api/v1/...`과 같은 컨트롤러에 함께 연결해 두고, 프론트를 먼저 옮겨요.
- URL만 바뀌고 응답 계약이 같으면 컨트롤러·서비스를 복제하지 않아요.

## 구현 방식

1. `ApiPaths`에 `LEGACY_PREFIX = "/api"`, `V1_PREFIX = "/api/v1"`를 둬요.
2. 각 제품 컨트롤러의 클래스 매핑에 구 경로와 v1 경로를 함께 선언해요.
3. Spring Security 공개·인증·관리자 매처에 두 경로를 같은 정책으로 추가해요.
4. 프론트 `API_ENDPOINTS`를 `/api/v1`으로 한 번에 전환해요.
5. MockMvc 계약 테스트로 두 경로의 상태·응답 본문·권한을 대조해요.

nginx rewrite나 서블릿 필터로 경로를 바꾸지 않아요.

## 대상

v1 대상:

- 가게, 예약, 리뷰, 즐겨찾기, 광고, 결제, 회원, 사업자 인증
- 채팅·문의·메일함과 관리자 JSON API
- 주소 검색 프록시

따로 다루는 경로:

| 경로 | 처리 |
|---|---|
| PortOne 웹훅 | 구 경로와 v1 경로를 오래 병행 |
| OAuth 시작·콜백 `/oauth2/...` | 제품 API 버전과 분리 |
| `/actuator/...`, 정적 자산, SPA 라우트 | 대상 아님 |
| CSP 보고 수집 | 정책 헤더와 함께 따로 전환 |

## 릴리스 순서

1. **v1 도입(2.x 마이너)**: `/api/v1`과 `/api`를 병행하고 프론트를 v1로 전환해요.
2. **구 경로 제거**: 구 경로 사용이 없고 공지 기간이 끝난 뒤 제거해요. 공개 계약을 깨는 제거는 앱 메이저 버전으로 내요.
