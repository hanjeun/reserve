# 가게 등록·수정 임시저장

가게 등록과 수정 화면은 같은 임시저장 UX를 쓰고, 초안은 브라우저 IndexedDB에만 저장해요.

## 동작

- 회색 보조 버튼은 `취소`가 아니라 **임시저장**이에요.
- 입력·이미지 변경이 1초 멈추면 자동 저장해요. 계속 입력해도 첫 변경 뒤 최대 5초 안에 한 번은 저장해요. 큰 이미지 Blob을 키 입력마다 다시 쓰지 않으면서 손실 구간을 제한하기 위해서예요.
- 다시 들어오면 저장 시각을 보여 주고 **이어서 작성 / 새로 작성**(등록) 또는 **이어서 작성 / 최신 정보 유지**(수정)를 고르게 해요.
- 새로 작성·최신 정보 유지를 고르면 오래된 초안을 지워요. 최종 등록·수정이 성공해도 초안을 지워요.
- 편집 중 서버 원본이 바뀌면 fingerprint 차이로 감지해, 초안이 최신 값을 덮을 수 있다고 먼저 알려요.

수정 화면에도 임시저장이 필요해요. 긴 운영시간·휴무일·소개·이미지를 고치다 이탈하는 손실도 크기 때문이에요. 두 화면은 `useStoreForm` 관문과 `StoreFormActions`를 공유해 버튼·자동저장 정책을 한 곳에서 강제해요.

## 저장 위치

`frontend/src/utils/storeDraftStorage.js`가 origin별 **IndexedDB** `reserve-local-drafts/store-forms`에 저장해요. 키는 회원·모드·가게별로 나눠요.

```text
member:{memberId}:store:create:new
member:{memberId}:store:edit:{storeId}
```

- 폼 값의 dayjs는 문자열로 직렬화하고, 새 이미지는 structured clone이 지원하는 `File/Blob`으로 보관해요.
- 만료는 30일이에요. 가게 폼에 들어올 때 다른 가게의 만료 초안까지 함께 정리해요.
- 키 입력마다 API·MySQL·S3 요청이 생기지 않고, 최종 제출 때 기존 multipart 요청 한 번만 보내요. 현재 규모에서 가장 싼 구조예요.

IndexedDB를 고른 이유는 큰 Blob과 구조화 값을 브라우저가 관리해 localStorage보다 적합하기 때문이에요. File System Access API는 지원 범위가 좁고 매번 권한이 필요해 폼 초안에 맞지 않아요.

## 한계와 안전 경계

- 같은 기기·브라우저 프로필·origin에서만 이어져요. 다른 기기 동기화는 없어요.
- 시크릿 모드, 사이트 데이터 삭제, 저장공간 회수, quota 부족 때 사라질 수 있어요.
- 로컬 초안은 정본이 아니에요. 서버 원본이 달라지면 사용자 확인 없이 합치지 않아요.
- IndexedDB도 XSS가 실행되면 읽힐 수 있어요. 비밀번호·토큰·결제정보 같은 시크릿은 절대 넣지 않아요.
- 새 이미지까지 저장하므로 quota 오류를 보여 주고 이미지 수·크기를 줄이도록 안내해요.
- `beforeunload`는 로컬 저장이 끝나지 않은 변경이 있을 때만 브라우저 기본 이탈 경고를 요청해요. 경고 표시는 보장되지 않아서 `pagehide`와 컴포넌트 unmount에서도 마지막 저장을 시작해요.

## 서버 초안으로 바꾸는 조건

다음 요구가 실제로 생길 때만 별도 `store_draft` 도메인을 만들어요.

1. PC에서 쓰던 내용을 휴대폰에서 이어야 할 때
2. 관리자와 사장님이 같은 초안을 공동 편집해야 할 때
3. 브라우저 데이터 삭제 뒤에도 복구해야 할 때

그때도 키 입력마다 DB write는 금지예요. 변경 병합 키·낙관적 버전·10초 안팎 debounce·명시적 저장·만료 배치를 함께 설계하고, 이미지는 초안 전용 S3 prefix와 만료 lifecycle을 써요. 지금은 운영비와 충돌 복잡도가 사용자 가치보다 커서 만들지 않아요.
