# 예약금과 환불

## 결제

서버가 예약과 금액을 확인해 결제 시도를 만들고, 결제창이 끝나면 PortOne의 주문·상점·통화·금액·상태를 검증해요. 화면의 완료 표시만으로 성공을 확정하지 않아요.

네이버페이 결제형 전용 채널은 `VITE_PORTONE_NAVERPAY_CHANNEL_KEY`로 연결해요. 개인 샌드박스는 `VITE_PORTONE_NAVERPAY_TEST_CHANNEL_KEY`를 사용하며 개발 서버의 `VITE_PORTONE_PAYMENT_ENV=TEST`에서만 선택해요. 배포 빌드는 이 TEST 항목을 무시해요. 같은 네이버 수단의 KCP·토스 경유보다 전용 채널을 우선하며, 채널이 없으면 기존 설정을 유지해요. PC는 POPUP, 모바일은 REDIRECTION으로 호출해요.

PortOne의 공용 TEST 키와 [Npay 개발자센터의 개인 샌드박스 인증정보](https://developers.pay.naver.com/user/merchant/auth)는 구분해요. 개인 샌드박스의 가맹점 ID·Client ID·Client Secret·Chain ID는 개발환경 API용이며 운영환경에서 사용할 수 없어요. 전용 TEST 채널에는 해당 환경의 인증정보를 등록하고 PortOne과의 호환을 확인해야 해요. LIVE 인증정보와 가맹 승인·검수는 별도예요.

서버가 준비한 예약·광고 ID와 상품명을 `bypass.naverpay.productItems`에 전달하며 예약금·광고 각 한 건을 수량 1로 표현해요. [네이버 공식 분류 안내](https://developers.pay.naver.com/support/faq/payment)에 따라 범용 서비스는 ETC/ETC를 사용하고, 계약에서 정한 분류가 있으면 그 값을 적용해야 해요. 100원 미만·상품 정보 누락은 호출 전에 차단하며 다른 PG로 자동 전환하지 않아요.

실제 전용 채널 생성과 TEST/LIVE 인증값 구분, 계약에 필요한 하위 판매자·이용완료일·세금 정보, [네이버 결제형 검수 규칙](https://developers.portone.io/opi/ko/integration/pg/v2/naverpay?v=v2)의 실패 사유 원문 안내는 운영 전환 전 확인·보완 대상이에요. 상품 분류와 선택 필드의 계약 조건을 추측해서 채우지 않아요. 채널 키는 공개 SDK용 식별자이며 API 시크릿을 프론트에 넣지 않아요.

로컬 개발 서버에서 `VITE_PORTONE_PAYMENT_ENV=TEST`와 `VITE_PORTONE_KCP_TEST_CHANNEL_KEY`를 함께 설정하면 카드는 KCP V2 직접 호출을 사용해요. `VITE_PORTONE_KCP_TEST_EASY_PAY_PROVIDERS`에 해당 MID의 지원을 확인한 NAVERPAY·SAMSUNGPAY·APPLEPAY를 지정하면 그 수단도 KCP로 직접 호출해요. 비어 있으면 기존 간편결제 채널을 유지하고 배포 빌드는 이 TEST 전용 설정을 무시해요. KCP에는 상호명·100바이트 이내 주문명을 전달하며 카드 직접 호출은 일시불이에요.

[KCP 공식 제휴간편결제 안내](https://developer.kcp.co.kr/guide/directpay)에 따르면 공용 T0000은 카카오페이 머니·네이버페이 포인트만 시험할 수 있고, 카카오페이 머니는 실제 결제로 처리돼요. KCP TEST 네이버페이는 SDK의 `easyPay.availablePayMethods: ['CHARGE']`로 포인트만 요청해요. 삼성월렛·Apple Pay 등은 계약·MID의 서비스 권한을 별도로 확인해야 해요. 코드의 지원과 해당 채널의 사용 가능 여부를 구분하고 PG·카드사 외곽 화면의 완전한 제거를 보장하지 않아요.

새 예약금·광고 주문번호는 영문·숫자 40자 이내로 발급해요. 기존 READY 주문번호와 조회·환불·멱등 키는 교체하지 않아요. KCP와 호환되지 않는 기존 주문은 카드 선택을 비활성화하며 다른 카드 PG로 자동 전환하지 않아요.

SDK 호출부터 외부 창 복귀와 PortOne 최상위 프레임의 수명을 관찰해요. SDK 응답 없이 확인된 프레임이 사라지면 로딩을 끝내고 같은 주문 결과로 이동해요. SDK 응답을 기다리는 팝업은 프레임이 없어도 시간·부모 창 포커스만으로 중단하지 않아요. SDK가 이동을 인계한 뒤의 복귀·이동 중단은 같은 주문을 다시 확인해요. 명시적인 취소 응답은 공통 안내를 표시하며, 불명확한 종료를 결제 실패·성공이나 새 결제 요청으로 바꾸지 않아요. 이전 계정·종료한 화면의 늦은 SDK 응답은 결제 검증과 화면 이동을 실행하지 않아요.

KCP의 사용자 종료 코드 `3001`과 `[3001] 사용자 Web Close`는 선택한 KCP 경로에서 정상 닫기로 구분해요. PC·모바일의 취소·오류·응답 중단은 본인 주문을 `POST /api/payment/checkout-return`으로 다시 확인해요. 소유권을 먼저 확인하고 PG 조회는 DB 잠금 밖에서 수행한 뒤, 금융 잠금 안에서 현재 상태와 미결 원장을 다시 확인해요. 선결제 필수 예약의 미결제가 확인되면 결제를 시작한 내 예약 또는 해당 가게 화면에서 같은 작은 안내 모달을 표시해요. 복귀 위치는 주문·회원별로 같은 탭에 30분간 보관하며 목록 조건만 유지해요. 위치가 없거나 다른 주문·회원·가게이면 내 예약으로 돌아가요. 결제 완료·환불·대사 필요·조회 불명확 상태는 결과 화면으로 이어지며 실패로 단정하지 않아요.

결제 수단 선택만 취소하면 현재 화면을 유지해요. 결제를 다시 시도하거나 외부 인증에서 복귀할 때는 같은 요청 번호로 기존 예약을 복구해요. 첫 신청은 결제 대기로, 같은 신청의 재시도는 기존 예약의 결제 재개로 안내해요. 미결제 복귀와 최종 실패도 예약 목록 캐시를 무효화해요. 만료·종료·삭제된 예약에는 결제를 이어갈 수 있다는 미완료 모달을 표시하지 않아요. 이미 결제된 예약은 결제창을 다시 열지 않으며, 새 신청의 중복 허용 여부는 가게 정책을 유지해요. PG의 비어 있는 응답이나 일반 404 오류는 미결제 증거가 아니에요. 공식 `PAYMENT_NOT_FOUND` 응답만 주문 부재로 구분해요.

예약 신청 복구는 `POST /api/reservations/requests/result`의 `outcome`으로 구분해요. `NOT_SUBMITTED`는 기존 신청 키로 생성 관문을 다시 거치고, `RESERVED`는 반환된 기존 예약을 이어가요. 취소·거절 또는 삭제된 종료 예약의 `CLOSED`만 새 신청 키로 재예약하며 입장·정원·중복 정책을 다시 확인해요. 종료된 신청의 원문은 반환하지 않고 이전 예약·결제·요청 기록도 바꾸지 않아요. 일반 404·조회 실패나 아직 취소되지 않은 만료 예약은 새 신청의 근거가 아니에요.

예약금을 0원으로 설정하면 결제 없이 예약해요. 결제 금액은 예약 당시 값을 사용해요. 결제 대기 만료는 예약 상태와 가게 설정을 함께 확인해요.

미결제 대기 예약의 paymentDeadline은 만료 작업과 같은 서버 시계에서 계산해 시간대가 있는 시각으로 전달해요. 목록·카드는 이 시각까지 남은 시간을 표시하며 매초 추가 조회를 하지 않아요. 남은 1분부터 임박 색상, 기한 경과 후 만료 표시를 사용해요. 표시가 0이 되어도 예약 상태나 결제 결과는 서버 확인 없이 바꾸지 않아요. 결제 준비와 만료 작업은 ReservationPaymentPolicy의 같은 기한을 사용하며 기한부터 새 결제 준비를 거부해요. 나중 결제를 허용하지 않은 예약은 예약금을 확인한 뒤에만 수동 승인할 수 있어요. 목록·카드의 실행 도구와 변경 API도 같은 기한을 확인해요. 만료 표시는 금액 바로 옆에 두고 만료 뒤 결제·변경·승인 도구만 숨겨요. 취소·거절·목록에서 삭제는 각 화면과 서버의 상태·소유권 규칙을 따라요. 서버가 취소를 확정하면 삭제 도구를 표시하고, 화면 만료만으로 예약을 취소하거나 삭제하지 않아요.

목록·카드는 기한이 지났지만 서버 상태가 아직 대기 중이면 `자동 취소 확인 중`을 표시해요. 취소·거절 도구와 오른쪽 상세 클릭 차단은 유지하며, 서버가 취소를 확정한 뒤에 삭제 도구로 전환해요. 실행 도구가 없는 미확인 예약에는 가게의 이용 확인을 기다리는 상태를 표시해요.

본인·가게 소유자의 종료 예약 삭제는 남은 READY 결제를 잠금 밖에서 PG와 재확인한 뒤 기존 금융 잠금과 환불·대사 관문을 다시 검사해요. 확인된 미결제만 닫으며 늦은 결제 완료·조회 장애·미확정 환불은 삭제하지 않아요. 이 흐름은 결제·환불을 발신하지 않으며 토스·KCP에 같은 정책을 적용해요.

일반 만료 작업은 기존 5분 주기를 사용해요. 자동 작업을 끈 로컬 프리뷰는 만료도 실행하지 않으므로, 필요한 경우 시작 도구의 -DisableBackgroundJobs -EnableUnpaidExpiry로 미결제 만료만 30초 간격으로 허용해요. 이 경로는 local 프로필·127.0.0.1의 reserve DB만 허용하며 진단 기동과 함께 사용할 수 없어요. PG 재확인 뒤 미결제만 취소하고 결제 완료·불명확 건은 보존해요. 다른 자동 작업과 환불 발신은 켜지 않아요.

| 상태 | 의미 |
|---|---|
| READY | 결제 준비 |
| PAID | 결제 완료 |
| CANCELLED·FAILED | 취소·실패 |
| REFUND_PENDING | 환불 결과 확인 중 |
| REFUNDED·PARTIAL_REFUNDED | 전액·부분 환불 완료 |

결과 화면은 본인 주문의 DB 상태와 연결된 예약 정보를 읽어요. 주문번호·결제 유형이 다른 응답은 표시하지 않으며 전액·부분 환불과 환불 확인 중을 구분해요. 일반 상태 GET은 결제 검증이나 환불을 실행하지 않으며 결제창 복귀 재확인만 전용 POST를 사용해요. 간편결제사 정보가 없는 과거 기록은 이름을 추정하지 않아요. 결제 완료·금액 불일치·환불 충돌 기록은 이후의 미결제 관측만으로 자동 해소하지 않아요.

## 방문 보증금

새 예약은 정상 방문 후 보증금 전액을 환불해요. QR 체크인으로 방문을 확인하고 승인 상태를 유지해요.

가게 등록·수정에서 이용 완료를 자동·수동으로 선택해요. 자동 완료는 체크인한 예약의 이용 종료 시각 이후에 실행하고, 수동 완료는 사업자가 처리해요. 완료와 환불 요청 기록은 같은 트랜잭션에 저장해요.

시간대·회차 예약은 예약 시각과 이용 시간, 날짜 예약은 영업 종료 시각을 사용해요. 영업 종료가 없는 기존 날짜 예약은 다음 날 0시를 사용해요. 자동 완료 여부·이용 시간·종료 시각은 예약에 저장하며, 가게 설정 변경으로 기존 예약을 바꾸지 않아요. 이용 시간은 완료 기준이며 기존 정원 계산 단위를 바꾸지 않아요.

`reserve.reservation.auto-completion-enabled=true`에서 자동 완료 작업을 실행해요. 기존 예약은 새 정책으로 일괄 보정하지 않아요. 보증금 환불 대상의 완료는 되돌릴 수 없어요.

## 환불 원장

취소·거절·이용 완료와 환불 요청 기록을 먼저 함께 저장해요. PG 호출은 DB 잠금 밖에서 수행해요.

- 확정한 환불액을 다시 요청하지 않아요.
- 접수·결과 미확정은 완료로 처리하거나 새 요청으로 재발신하지 않아요.
- 최종 실패 원장은 반복 작업으로 되살리지 않아요. 별도 재시도는 원장 금액과 권한을 검증해요.
- 환불이 확정되면 결제·예약의 결제 표시를 함께 반영해요.
- 웹훅은 서명을 검사하고 저장한 뒤 처리해요.

가게의 이용 시간은 1~1,440분으로 설정해요. 기존 가게의 미설정 값인 0·null은 조회와 새 예약에서 기본 60분으로 해석하고, 새 설정의 0분은 거부해요. 이 처리는 기존 DB 값이나 예약을 보정하지 않아요.

## TEST 가상 정산

`reserve.settlement.test-enabled=true`에서 사업자 패널의 TEST 가상 정산을 사용해요. 준비 상태를 먼저 조회하며 비활성일 때는 목록·모의 지급을 요청하지 않아요. 수수료는 모두 0원이며 실제 송금 API를 호출하지 않아요.

서버가 확인한 TEST 채널의 결제만 계산해요. 정상 방문·전액 환불 건의 정산예정액은 0원이고, 전날까지 노쇼로 확정한 건은 확정 환불을 뺀 금액을 대상으로 해요. 미결 환불·대사·분쟁·불명확한 채널은 보류해요.

모의 지급 전에 PG 결과를 다시 조회하고, 같은 요청 번호의 결과는 중복 지급 없이 복구해요. 이후 환불이 생기면 잔액을 음수로 표시해 조정할 금액을 숨기지 않아요. 과거 결제를 TEST로 추정해 채우지 않아요.

## 결제 수단

예약금과 광고는 같은 결제 확인창을 사용해요. 예약·주문 요약은 가게 상세의 공통 정보 행을 재사용하고, 결제 수단은 카드결제·네이버페이·카카오페이·토스페이·삼성페이·Apple Pay만 사용해요. 서버가 준비한 주문과 금액을 유지한 채 PortOne SDK로 넘겨요. 결제 전 예약·주문 내용과 결제·취소·환불 안내의 확인 체크를 요구해요. 이 화면의 체크는 별도 개인정보 제공 동의나 서버에 보관한 동의 증적을 대신하지 않아요.

결제·취소·환불 안내는 같은 탭의 약관으로 이동해요. 같은 계정·방문 기록에서 30분 이내 뒤로 돌아오면 현재 내역에서 결제를 이어가도록 안내해요. 동의 체크와 결제 정보는 복원하지 않으며, 결제를 다시 선택할 때 서버의 현재 주문·금액·기한을 확인해요.

카드는 RESERVE에서 카드사를 선택해 `card.cardCompany`로 인증창을 호출해요. 현재 직접 호출은 일시불이며 카드번호·CVC를 입력받거나 저장하지 않아요. 간편결제는 `easyPay.easyPayProvider`를 지정하고, 카카오페이·토스페이 단독 채널이 있으면 이를 우선해요. PG 인증·약관·기기 전환 화면은 해당 결제사의 계약과 환경을 따라요.

PortOne 토스페이먼츠 연동은 PC에서 IFRAME, 모바일에서 REDIRECTION만 지원해요. 카드사·간편결제 직접 호출로 수단 선택을 생략해도 PG 외곽창과 로딩은 남을 수 있어요. 외부 인증창의 DOM·스타일을 덮어쓰지 않아요.

Apple Pay는 토스페이먼츠의 Apple 기기·Safari 지원 조건과 브라우저의 결제 가능 여부를 확인해요. 삼성페이는 PC를 허용하고 미지원 모바일은 제한해요. Android의 기기 정보만으로 지원 모델을 확정하지 않으며, 최종 이용 가능 여부는 결제사가 확인해요.

| 설정 | 용도 |
|---|---|
| VITE_PORTONE_TOSS_CHANNEL_KEY | 토스페이먼츠 카드 채널 |
| VITE_PORTONE_KCP_TEST_CHANNEL_KEY | 로컬 TEST KCP 카드 채널 |
| VITE_PORTONE_KCP_TEST_EASY_PAY_PROVIDERS | KCP MID 지원을 확인한 로컬 TEST 간편결제 목록 |
| VITE_PORTONE_CHANNEL_KEY | 기존 카카오페이 채널 |
| VITE_PORTONE_NAVERPAY_CHANNEL_KEY | 네이버페이 결제형 단독 채널 |
| VITE_PORTONE_NAVERPAY_TEST_CHANNEL_KEY | 개발 TEST에서만 사용하는 개인 Npay 샌드박스 단독 채널 |
| VITE_PORTONE_TOSSPAY_CHANNEL_KEY | 토스페이 V2 단독 TEST·LIVE 채널 |

| VITE_PORTONE_PAYMENT_ENV·VITE_PORTONE_TOSS_TEST_EASY_PAY_PROVIDERS | 개발 서버의 TEST 전용 간편결제 시험 목록 |

간편결제 설정은 쉼표로 구분하며 NAVERPAY·KAKAOPAY·TOSSPAY·SAMSUNGPAY·APPLEPAY만 사용해요. 비어 있으면 토스 간편결제를 켜지 않아요. 같은 설정을 CI의 프론트 빌드에도 전달해요. API 시크릿은 프론트 설정에 넣지 않아요.

미확인 수단의 시험 목록은 개발 서버이면서 PAYMENT_ENV가 TEST일 때만 표시해요. 배포 빌드에는 포함하지 않으며, TEST 표시는 결제 성공을 뜻하지 않아요.

PC는 SDK 응답 뒤 서버 검증, 모바일은 기존 전용 리다이렉트에서 검증해요. 선택창이 닫힌 뒤 PG로 넘기고 계정 전환·중복 클릭·다른 주문 응답으로 새 결제를 시작하지 않아요. SDK가 이동으로 인계한 뒤 외부 화면에서 돌아오거나 10초 동안 이동하지 못하면 같은 주문의 결과 화면으로 이어져요. 결과 미확정을 실패·취소로 바꾸거나 새 PG 요청을 보내지 않아요. 이전 계정의 응답은 새 결제의 로딩과 중복 방지 상태를 바꾸지 않아요.

## 결제 이름

채널 표시 이름은 `RESERVE 결제사 TEST` 또는 `RESERVE 결제사 LIVE`로 구분해요. 날짜·임시 접두사는 넣지 않아요. 채널 이름과 결제 요청 번호는 구분하며 기존 거래의 식별자를 바꾸지 않아요.

## 토스 TEST 채널

PortOne의 범용 MID iamporttest_3은 일반 카드 시험용이에요. 간편결제는 MID 계약·기기 조건에 따라 제한되므로 Toss 직접 연동의 지원 목록을 우리 채널의 성공으로 해석하지 않아요.

지원 조건은 [PortOne 토스 연동](https://developers.portone.io/opi/ko/integration/pg/v2/tosspayments)에서 확인해요. 단독 토스페이는 [V2 연동](https://developers.portone.io/opi/ko/integration/pg/v2/tosspay-v2)의 채널을 사용해요. 실제 결제·환불·판매자 지급은 계약과 별도 운영 승인 범위에서 진행해요. 네이버페이 단독 결제형은 별도 채널·계약과 상품 정보가 필요하며, 토스 경유 설정만 바꿔 단독 창으로 전환하지 않아요.

관련 코드는 backend의 payment·reservation 영역에 있어요.

## 예약 안내와 동의 증거

`reserve.reservation-consent.enabled`는 기본 false예요. 활성화 전에 reservation-consent.sql·제한 계정 권한·호환 복구와 가게의 실제 판매자 정보·개인정보 보유기간을 확인해요. `reserve.reservation-consent.recipient-retention`은 승인한 안내 문구이며 비어 있거나 증거 테이블이 없으면 활성 기동을 거부해요. 이 JDBC 테이블은 Hibernate 매핑 validate만으로 검증되지 않아요.

예약 접수에서 조건 확인과 개인정보 제3자 제공 동의를 분리해요. 제공받는 가게·목적·항목·보유기간·거부 영향을 안내하며, 서버는 가게 잠금 후 현재 정책의 버전·해시와 두 동의를 확인해요. 가게 소유자·금액·환불 조건이 바뀌면 다시 확인해야 해요. 같은 요청의 결과 복구는 최초 접수의 증거를 유지해요.

증거는 예약 저장과 같은 트랜잭션에 예약·회원·가게·제공받는 자의 식별자, 안내 내용·해시·버전, 두 동의와 서버 시각을 보관해요. 이름·연락처·자유 입력 요청사항의 사본은 추가하지 않아요. 가게의 일반 조회에서는 이름·이메일·요청사항과 자유 입력 사유를 이용 종료 30일 후 가리며 개인정보 검색도 제한해요. 본인 예약 조회는 유지해요.

`/api/admin/reservation-retention`은 추가 인증을 마친 관리자에게 목적을 확인하고 별도 거래 증거를 제공해요. 조회·사건별 보류·해제는 감사 기록을 남기고 응답을 캐시하지 않아요. 진행 중 분쟁은 파기를 보류하며, 거래·이용 종료의 가장 늦은 기준부터 5년과 종결 분쟁 기록 3년 중 더 긴 기간을 보호해요. 휴지통 숨김·복구는 이 기간을 다시 시작하지 않아요.

예약 전용 파기는 종료 상태·금전 대사·진행 중 환불·미처리 웹훅과 보류를 잠금 아래 확인해요. 예약·동의·결제 증거를 한 트랜잭션에서 파기하고 공개 리뷰는 내용과 작성자를 보존한 채 예약 연결만 해제해요. 숨김은 진행 중 예약과 미해결 금전 건을 거부하며 보유기간을 대신하지 않아요. 동의·보유기간 활성화와 자동 파기는 기본 비활성이고 수동 SQL 적용·제한 계정 검증·독립 복원·호환 복구 확인과 별도 승인이 필요해요.

## 외부 지연과 실행 풀

결제 조회·환불의 PortOne 외부 호출은 `portone.max-concurrent-requests`의 동시 상한을 공유하며 기본 4개예요. 별도 대기열 없이 포화 요청을 503으로 거부하고 모든 종료 경로에서 슬롯을 반환해요. 연결 5초·읽기 10초 제한과 외부 호출의 트랜잭션 분리를 유지해요. 발신 전에 로컬 상한으로 거절된 환불만 같은 원장·멱등 키로 다시 대기하고, 발신 후 결과 미확정은 재발신 없이 대사해요.

점유·상한·거절 수는 `reserve.payment.pg.inflight`·`reserve.payment.pg.limit`·`reserve.payment.pg.rejected`로 확인해요. 환불은 refundExecutor의 2개 스레드·32개 대기열로 발신해요. 커밋 콜백은 작업 등록 후 즉시 반환하며, 포화·종료로 발신하지 못한 의도는 원장에 남아 정기 재시도 대상이 돼요. 메일은 mailExecutor의 2개 스레드·32개 대기열, 이미지는 imageUploadExecutor의 4개 스레드·20개 대기열로 분리해요. 거절한 작업을 요청 스레드에서 대신 실행하지 않아요. 이 설정은 검증된 운영 수용량이 아니며 Hikari 점유·대기·획득시간, SQL 잠금, HTTP 지연과 함께 부하를 비교해요.

## 파트너 정산 연결

현재 TEST 가상 지급과 실제 은행 이체를 구분해요. 정상 방문 후 전액 환불한 건은 판매자 지급 대상에 넣지 않고, 확정된 노쇼의 잔액에서 미해결 환불·분쟁·대사 오류를 제외해요.

PortOne 연결은 계약·판매자와 계좌 확인 → 주문/취소 정산 전송 → 명세 확정 → 계약한 지급대행 → 이체 결과 대사 순서예요. API 요청 번호·제공사 식별자·요청 상태를 먼저 보관하고 외부 작업은 DB 잠금 밖에서 처리해요. 타임아웃은 미확정으로 두고 같은 요청을 조회·복구하며 새 요청으로 중복 이체하지 않아요.

TEST 호출은 쿼리 `test=true`를 명시해요. 대상 API는 `/platform/partners`·`/platform/contracts`·`/platform/transfers/order`·`/platform/transfers/order-cancel`·`/platform/payouts`예요. 지급 완료 표시를 실제 은행 이체 성공으로 사용하지 않아요. 실제 계좌 검증·지급대행 권한·수수료·자금 흐름은 별도 계약과 승인 대상이며, TEST의 0원 수수료를 실제 지급에 대입하지 않아요.
