# 첫 고객지원 문의 · 로컬 조회 오류 · 초기화 경계

> 2026-09-14 `local-preview-all-changes`의 이번 작업 기록. 소스 구현, mock/시각 검사, 실제 로컬 HTTP 관측을 구분한다. 커밋·통합·운영 배포·백엔드 재시작·DB 삭제는 하지 않았다.

## 이번에 구현한 것

- `MessengerSupportIntro`: 흰 대화 화면의 짧은 공지, 현재 이용자 이름이 들어간 인사, 관리자 답변 안내와 네 개의 오른쪽 정렬 질문 버튼.
- 질문은 예약 확인 / 변경·취소 / 가게 등록·이용 / 기타 문의다. 선택하면 기존 초안 뒤에 추가하고, **보내기에서만 전송**한다. 2000자 상한은 그대로 지킨다.
- 로드에 성공한 전송 가능한 MEMBER/SUPPORT 방에 메시지·이전 이력이 모두 없을 때만 표시한다. 로딩·조회 실패·차단·다른 역할·기존 대화에는 첫 문의 안내를 끼워 넣지 않는다.
- 안내는 화면 컴포넌트이지 저장된 메시지·실제 상담원의 답변·AI 생성물이 아니다. 가짜 답변 시간도 붙이지 않는다. 표시 가능한 실제 관리자 사진이 없으면 기존 브랜드 fallback을 사용한다.
- 디자인 시스템 Core를 일괄 변경하지 않고 기존 메신저 Pattern과 색상 토큰을 사용했다. 질문 hover는 전경·테두리만 변경하며 축소 효과를 넣지 않는다.
- `useChatThread`의 같은 방 재조회도 새 요청 세대로 격리한다. 재조회 즉시 이전 load/poll/send 응답을 무효화하고, 로드 실패·대기 중에는 폴링/전송을 시작하지 않는다. 같은 본문 재시도의 `clientMessageId`는 같은 방 재조회 후에도 보존한다.
- 이미 보낸 읽음 요청의 늦은 응답이 방·설정·로그인 세션 전환 후 다른 캐시를 갱신하지 않도록 `MessengerContent`에도 세대 검사를 추가했다. 이미 발행한 서버 읽음 요청을 취소하거나 되돌리는 기능은 아니다.

## 실제 로컬 오류: 아직 해결 완료가 아님

현재 로그인 환경의 새 임시 Chrome 탭에서 `관리자에게 문의`로 진입하고 응답 상태를 관측했다. 실제 메시지는 보내지 않았다.

| 실제 요청 | 결과 |
|---|---|
| `http://localhost:8080/api/chat/conversations?page=0` | 404 |
| `http://localhost:8080/api/chat/store-inbox?page=0` | 404 |
| `http://localhost:8080/api/chat/support` | 404, `요청하신 경로를 찾을 수 없습니다.` |

현재 `ChatApiController` 소스에는 세 경로가 존재한다. 실행 중인 8080 애플리케이션에 현재 경로가 등록됐는지 확인해야 한다. 과거 프로세스 시작 시각만으로 stale을 확정하지 않으며, 실제 백엔드 예외/런타임 매핑 및 재시작 후 정상 응답은 아직 확인하지 않았다. **프론트 경합 보강이나 내역 삭제를 이 404의 해결로 보고하지 않는다.**

개발 중 기존 탭에서 관측한 Fast Refresh의 hook-order 오류와 이 새 탭의 HTTP 404도 별개다.

## 로컬 초기화: 삭제 범위 답변 대기

IDE의 `localhost` 연결에서 `reserve` 스키마·MySQL 8.0.42·포트 3306을 읽기 전용으로 확인했다. 운영 연결에는 접속하지 않았다.

- 현재 `chat_room` 2개, `chat_message` 7개, `chat_report` 0개.
- 동일 회원의 중복 SUPPORT 방을 가진 회원 수는 0이다.
- 세 테이블과 현재 컬럼·OWNER 등 enum을 확인했다. 메시지/신고의 room FK와 방의 member FK도 확인했다.
- 대화 본문·자격증명은 조회/출력하지 않았다. 방 생성과 읽음을 겸하는 지원 GET은 위 사용자 UI 재현에서만 실행했다.
- 현재 계정만 / 로컬 모든 계정 중 범위를 사용자에게 물었다. **아직 삭제하지 않았다.**

초기화 실행 전에는 범위와 대상 ID를 다시 확인하고 복구 수단 및 원자적 처리 경계를 확보한다. 어떤 상태든 신고가 연결된 방은 제외한다. 운영 데이터, 회원·가게·예약·결제 데이터, FK 비활성화, TRUNCATE, ID 재설정은 대상이 아니다. 실행 후 실제 삭제 건수·복구 수단을 기록한다.

로컬 백엔드는 `ddl-auto: update`와 파일 삭제/OAuth/결제 관련 scheduler를 포함하므로, 현재 프리뷰 전체를 재시작하는 것은 UI 변경만 실행하는 것과 다르다. 재시작 전에 현재 실행 설정과 외부 작업 경계를 확인한다.

## 이번에 실행한 검사

- Vitest: `MessengerSupportIntro.test.jsx`, `MessengerContent.test.jsx`, `MessengerVisuals.test.jsx`, `useChatThread.test.jsx` **4개 파일 76/76**.
- 위 변경 JSX/hook/test 및 DEV fixture 7개 경로 ESLint: 경고 0.
- Vite production build 및 bundle budget 통과. 초기 gzip 321.1 KiB, 최대 JS 563.9 KiB.
- `index.css`, `feature-surfaces.css` PostCSS 파싱 및 잘못된 한글 selector 검사 통과.
- 변경 tracked hook/test/CSS의 `git diff --check` 통과. 새 파일은 별도로 공백 검사를 한다.
- 실제 첫 문의 컴포넌트를 쓰는 **DEV 전용 무API fixture**: 320×740, 390×844, 960×900에서 가로 넘침 없음, 질문 터치 높이 44px, 흰 대화 배경 확인. 질문 클릭은 fixture 초안에만 반영되고 실제 전송하지 않는다.
- 실제 로그인 로컬 HTTP: 위 404 재현. 실제 두 계정 왕복·정상 조회·재접속·운영 DB/배포는 이번 검사에서 완료하지 않았다.

사용자 Chrome 창 크기와 나무위키 탭은 변경하지 않았다. 별도 IAB에만 임시 뷰포트를 적용했고 확인용 임시 탭과 크기 override는 작업 종료 때 정리한다.

## 후속: 헤더 정렬과 로딩 오류 재확인

[후속 기록](messenger-header-and-runtime-routing-2026-09-14.md)에서 목록 헤더·중복 커버 로고를 보정하고 경로/권한 오류의 반복 자동 요청을 줄였다. 새 확인용 Chrome 탭의 동일 로그인 세션에서 계정 조회는 200, 대화 목록·받은 문의는 404였다. 응답은 ‘요청하신 경로를 찾을 수 없습니다.’이며 현재 소스의 경로와 호출 경로는 일치한다. 내역 초기화·백엔드 재시작은 여전히 실행하지 않았다. 위 이전 검사와 삭제 대상 건수는 당시 확인 기록이며 현재 건수로 재사용하지 않는다.
