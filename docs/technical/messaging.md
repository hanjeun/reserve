# 통합 메시지와 가게 문의

고객지원과 가게 문의를 하나의 메신저에서 보여 주되, 권한과 읽음 상태는 대화 유형별로 따로 관리해요.

## 제품 경계

하나의 `MessengerShell`이 두 대화 유형을 보여 줘요.

| 유형 | 참가자 | 시작 조건 | 상대 받은편지함 |
|---|---|---|---|
| `SUPPORT` | 회원 ↔ RESERVE 관리자 | 로그인 회원이 고객지원 열기/첫 전송 | 관리자 채팅 탭 |
| `STORE` | 회원 ↔ 해당 가게의 현재 소유자 | 로그인 회원이 공개·운영 가능한 타인 가게에서 문의 | 사장님 `가게 받은 문의` |

- 가게 문의는 예약 전 질문용이라 예약 보유를 요구하지 않아요. 자기 가게에는 문의할 수 없고, 삭제·정지된 가게에는 새 메시지를 보낼 수 없어요. 닫힌 가게의 기존 대화는 읽을 수 있어요.
- 관리자 고객지원 API는 `SUPPORT`만, 사장님 받은편지함은 `STORE`만 받아요. 유형 혼동으로 권한이 넓어지지 않게 하기 위해서예요.
- 기존 `Inquiry`(비회원도 남기는 단건 문의)는 로그인 사용자의 연속 대화인 `ChatRoom`과 합치지 않아요.
- 대화 모델은 회원별 `SUPPORT`, 회원×가게별 `STORE`, 사장님 받은 문의예요. 그룹방·직원 초대·담당자 배정·회원 간 자유 DM·주제별 새 문의방은 없어요.

## 화면

### 진입과 구성

- 우측 하단의 단일 launcher가 PC에서는 독립 패널, 모바일에서는 `/messages` 전체 화면을 열어요. 가게 상세의 문의 버튼은 `/messages?storeId={id}`로 들어가 브라우저 뒤로가기가 자연스럽게 동작해요.
- launcher는 라이트·다크 모두 흰 배경에 브랜드 색 아이콘이에요. 선택형 `launcherImageSrc`로 사진을 연결할 수 있고(기본 App은 지정하지 않음), PC 패널이 열리면 X, 사진 로드 실패 시 기본 메시지 아이콘을 보여 줘요.
- 하단 메뉴는 `홈 · 대화 · 설정`이에요. 홈은 사진 커버와 ‘고객지원에 문의’ 카드 하나, 대화는 실제 상대별 목록, 설정은 현재 계정과 PC 세션 알림이에요. 대화 안에서는 하단 메뉴 대신 입력란을 써요.
- 홈 커버 사진은 `coverImageSrc`로 바꿀 수 있고 기본은 `/og-image.png`예요. 설정/업로드 UI는 없어요.
- PC 패널은 최대 420px이에요. 패널과 모바일에서 상대를 고르면 목록 대신 대화가 나오고, 내부 뒤로가기로 목록에 돌아가요. PC `/messages`는 목록·내용 두 칸 구성을 유지해요.
- 목록 제목·새로고침은 `MessengerListHeading`의 72px 헤더에 가운데 정렬하고, PC 닫기도 같은 높이예요. 새로고침·닫기는 각각 44px 터치 영역이에요. 접근성 제목 ‘메시지’는 시각적으로만 숨겨요.
- `내 대화`와 `가게 받은 문의`를 분리해, 같은 사람이 손님·사장님 역할을 동시에 가져도 읽음 수가 섞이지 않아요.

### 표시 이름과 사진

- `SUPPORT` 상대와 ADMIN 발신자는 관리자 개인 이름·사진 대신 고객지원 표시 이름(기본 `RESERVE 고객지원`)으로 보여 줘요. 표시 이름·사진은 [채팅 관리](#채팅-관리)에서 바꿔요.
- 회원의 `STORE` 문의에는 가게 이름, 사장님 받은 문의에는 고객 이름을 보여 줘요. 회원 ID·이메일은 새로 공개하지 않아요.
- 설정의 내 사진은 현재 로그인 사용자의 `profileImageUrl` 우선, `profileImage` fallback이에요. 없거나 실패하면 이니셜·사용자 아이콘으로 표시하고, 사진·계정이 바뀌면 이전 실패 상태를 버려요.
- 마지막 대화 미리보기는 저장값을 우선하고, 기존 방의 값이 비었을 때만 권한 확인된 방의 마지막 메시지를 읽기 전용으로 조회해요.

### 입력

- 입력 박스 50px, 한 줄 textarea 40px(줄 높이 24px), 전송 터치 영역 44px이에요. 모바일 글꼴은 16px이고 여러 줄은 내부 스크롤해요.
- Enter 전송, Shift+Enter 줄바꿈, 한글 조합 중 전송 안 함, 2000자 제한이에요.
- 사장님 `OWNER` 작성란의 `답변 문구`는 프로젝트가 직접 쓴 고정 안내 문구예요. 기존 입력 뒤에 삽입만 하고 자동 전송하지 않으며, AI 생성·예약 확정·환불 보장을 뜻하지 않아요.

### 자동 갱신

- 홈·목록·설정을 여는 것만으로는 방 생성, 4초 방 폴링, 읽음 처리를 시작하지 않아요. 명시적 ‘고객지원에 문의’나 기존 상대 선택에서만 방을 열어요. 목록/받은편지함의 30초 갱신은 홈·설정에서도 돌아요.
- 방이 없는 고객지원을 가짜 ‘최근 대화’로 끼워 넣지 않아요. unread는 각 대화 행에 표시하고, 로딩한 일부 페이지의 합을 전체 배지로 쓰지 않아요.
- 목록·받은 문의·unread 조회는 즉시 재시도하지 않아요. 429를 뺀 4xx가 나면 주기·포커스·재연결 자동 갱신을 멈추고 오류와 ‘다시 시도’만 남겨요. 네트워크 장애·429·5xx는 주기 갱신으로 복구를 시도해요.
- 일반 사용자에게는 목록 새로고침으로 사업자 받은 문의를 호출하지 않아요.

### 접근성

- 패널은 focus trap, `Escape`, 닫힌 뒤 launcher focus 복귀, reduced-motion, 44px 터치 목표를 지켜요.
- 대화 전체를 live region으로 두지 않아요. 첫 로드와 과거 메시지 50개를 화면 낭독기가 매번 다시 읽는 부작용이 더 크기 때문이에요. 최초 이력은 PC 세션 알림 입력으로도 쓰지 않아요.

## 저장과 전송 안정성

- 메시지는 DB `chat_message`, 방 요약은 `chat_room`에 저장해요. 컨테이너 메모리에 대화 본문을 두지 않아요.
- 클라이언트가 전송마다 `clientMessageId`를 만들고, 응답을 잃은 같은 본문 재시도에 같은 값을 써요. 서버의 `(room_id, sender_member_id, client_message_id)` 유일 제약과 방 행 잠금이 중복 저장을 막아요.
- 첫 화면은 최근 50개만 받고, 위로 올리면 `beforeId` cursor로 과거 50개를 가져와요. 전체 count는 하지 않아요.
- 열린 대화만 4초 증분 폴링하고, 목록은 30초, 닫힌 launcher 배지는 60초 주기로 갱신해요. 서버에 WebSocket 연결 상태를 두지 않아요.
- A → B → A처럼 빠르게 방을 바꿔도 요청 세대로 load/poll/send를 fencing해 이전 응답이 새 화면을 덮지 않아요. 과거 조회·읽음 응답의 캐시 갱신도 방/화면/세션 세대를 검사하고, 전환 때 과거 조회의 스크롤 복원값을 버려요.
- 같은 방 재조회도 이전 요청을 즉시 무효화해요. 로드 실패·대기 중에는 폴링과 전송을 막고, 응답 유실 재시도 키는 보존해요.
- 전송 말풍선은 먼저 보이고, 실패하면 제거한 뒤 새 입력이 없을 때만 입력을 복원해요. 늦은 실패가 새 입력이나 새 로그인 세션을 덮지 않아요.
- 읽지 않은 수는 회원·관리자·사장님 세 축이에요. 메시지 추가와 증가는 같은 방의 비관적 잠금 아래에서 처리하고, 창이 실제로 보이고 focus가 있을 때만 폴링 수신분을 읽음 처리해요.
- 입력 초안은 대화별 세션 메모리에만 둬요. 최대 20개·각 2000자, 최근 편집 순 보존이에요. DB·localStorage·sessionStorage에 쓰지 않고, 새로고침·로그아웃·재로그인·계정/역할 전환 때 버려요.

## API

| 경로 | 역할 |
|---|---|
| `GET /api/chat/conversations` | 회원 관점의 고객지원·가게 문의 목록 |
| `GET /api/chat/support` / `POST /api/chat/support/messages` | 고객지원 열기·전송 |
| `GET /api/chat/stores/{storeId}` / `POST .../messages` | 손님 관점 가게 문의 열기·전송 |
| `GET /api/chat/store-inbox` | 소유 가게의 받은 문의 목록 |
| `GET /api/chat/store-inbox/{roomId}` / `POST .../messages` | 사장님 관점 열기·답장 |
| `GET /api/chat/rooms/{roomId}/messages?afterId=` | 참가자 증분 폴링 |
| `GET /api/chat/rooms/{roomId}/history?beforeId=&size=` | 참가자 cursor 과거 내역 |
| `POST /api/chat/rooms/{roomId}/read?viewerRole=` | 보이는 화면의 명시적 읽음 처리 |
| `PUT /api/chat/rooms/{roomId}/block?viewerRole=&blocked=` | 역할별 차단·자기 차단 해제 |
| `POST /api/chat/rooms/{roomId}/reports?viewerRole=` | 대화 전체 또는 상대 메시지 신고 |
| `GET /api/chat/unread` | 회원·소유 가게를 합친 launcher 배지 |
| `GET /api/admin/chat/reports` / `GET .../{id}/context` | 관리자 신고 목록·읽음 상태를 바꾸지 않는 문맥 조회 |
| `PATCH /api/admin/chat/reports/{id}` | 검토 시작·근거 있는 조치 완료/기각 |

- 이전 `/api/chat/my*`와 관리자 `/api/admin/chat*` 계약은 기존 화면 호환을 위해 유지해요.
- 관리자 증분 조회(`getNewMessagesAsAdmin`)도 `SUPPORT`만 허용해요. 관리자라는 이유만으로 임의 `STORE` 방을 폴링할 수 없고, 가게 신고 검토는 신고 문맥 API로 분리해요.

전송 취소·목록 숨김·보존 기간은 [채팅 입력·설정·전송 취소](chat-controls.md)에 있어요.

## 보존·차단·신고

메시지는 수정·삭제 API가 없는 append-only 기록이고, 회원 탈퇴·가게 폐업 뒤에도 보존해요. 법적 보존 기간이 확정됐다는 뜻은 아니에요.

- 회원·가게 중 한쪽이라도 차단하면 양쪽 새 전송이 모두 멈춰요. 각 참가자는 자기 차단만 해제할 수 있어요.
- 가게 쪽 차단은 개인이 아니라 가게 역할의 운영 상태라 소유자가 바뀌어도 승계돼요.
- 신고 사유는 스팸·괴롭힘·부적절한 내용·사기·기타이고, 기타는 설명이 필수예요.
- 대화 전체 또는 상대가 보낸 특정 메시지를 신고할 수 있어요. 같은 참가자의 같은 대상 신고는 안정 키로 한 번만 저장해요.
- 신고는 회원별 10분 5건으로 제한해요. 신고만으로 자동 차단·회원 정지·가게 제재를 하지 않아요.
- 관리자는 접수 → 검토 중 → 조치 완료/기각을 관리하고, 종결에는 처리 근거가 필수예요.

> 주의: 신고·분쟁 중인 대화의 법적 보존 hold 기간과 회원 파기 요청 예외는 아직 정하지 않았어요. 정하기 전에는 신고·메시지 자동 삭제 배치를 만들지 않아요.

## 채팅 첫 안내와 자동 문답

손님이 메시지가 없는 대화를 처음 열 때 보이는 안내예요. 고객지원은 관리자가, 가게 문의는 사장님이 설정하고, 설정이 없으면 기본 안내가 보여요.

- **구성**: ① 확성기 줄 = 공지사항(없으면 "안녕하세요. {이름}입니다.") ② 인사말 ③ 자주 묻는 질문. 보낸 사람 표시(아바타 + 이름)는 대화창 헤더와 겹쳐서 두지 않아요.
- **동작**: 질문 버튼을 누르면 저장된 답변이 바로 보여요. 서버 메시지로 보내지 않으므로 문의함·읽지 않음 수·알림에 영향이 없어요. 고객지원은 설정 전에도 서버 기본 문답 4개(답변 포함)가 동작해요. 서버를 부를 수 없을 때의 화면 대체값만 답변 없이 입력칸에 질문을 채워요.
- **한도**: 공지사항 100자(한 줄, 줄바꿈·연속 공백은 한 칸), 인사말 200자, 질문 최대 5개(질문 40자·답변 300자), 같은 질문 중복 금지(대소문자·공백 무시). 화면에서 칸별로 먼저 막고(`useFormErrors`), 서버가 다시 검사해요.
- **저장 모델**: `chat_intro`(`scope_key` = `SUPPORT` 또는 `STORE:{가게ID}`, UNIQUE, notice, greeting) + `chat_intro_item`(질문·답변·sort_order). MySQL UNIQUE는 NULL을 여러 개 허용하므로 `store_id` NULL로 고객지원을 표시하지 않아요. 저장은 항상 전체 교체이고, 입력 검증이 끝난 뒤에만 설정 행을 만들어요.

| 메서드 | 경로 | 권한 |
|---|---|---|
| GET | `/api/chat/intro/support` | 로그인 |
| GET | `/api/chat/intro/stores/{storeId}` | 로그인 (삭제된 가게 404) |
| PUT | `/api/chat/intro/stores/{storeId}` | 그 가게의 사장님(사업자 역할 + 소유) |
| PUT | `/api/admin/chat/intro` | 관리자 |
| POST | `/api/admin/chat/intro/avatar` | 관리자 (고객지원 사진 업로드) |

### 채팅 관리

- 사업자 패널·관리자 패널의 `채팅 관리` 탭은 같은 편집기(`ChatIntroEditor`)와 스켈레톤(`ChatIntroEditorSkeleton`)을 써요. 구성은 프로필 · 공지사항 · 인사말 · 자주 묻는 질문이에요.
- 사업자 패널은 가게별로 설정해요. 공통 FilterToolbar를 쓰고, 가게가 2개 이상이면 선택한 가게를 URL `chatIntroStore`에 남겨요. 모바일은 `설정 | 미리보기`를 전환해요.
- 인사말은 `{이름}`(손님 이름, 모르면 "회원")과 빈 줄 문단을 지원하고, 저장 전에는 서버 기본 문구가 칸에 채워져 있어요.
- 표시 이름·사진은 **고객지원만** 바꿔요(`display_name` 30자, `avatar_url`은 `POST /api/admin/chat/intro/avatar`로 올린 `support/chat` 아래 파일만, 바뀐 옛 파일은 삭제 대기열). 메신저가 `SupportIdentityContext`로 헤더·목록·홈·답변 말풍선에 내려줘요.
- 가게는 가게 이름·대표 사진을 읽기 전용으로 써요. 채팅에서 따로 바꾸면 "RESERVE 고객지원" 사칭이 가능해서예요. 서버도 가게 요청의 표시 이름·사진을 버려요.
- 미리보기(`ChatIntroPreview`)는 메신저 대화창의 실제 클래스로 그린 창 안에 같은 `ChatIntro`를 그려요. 저장하면 손님 메신저와 같은 캐시 키(`chatKeys.intro(scope)`)를 갱신해 바로 반영돼요.

## 확장 기능 관문

### 알림

앱 안 unread 배지와 받은편지함 정렬 외에 **선택형 PC 세션 알림**이 있어요.

- 기본 OFF예요. `PC 알림 켜기` 클릭에서만 권한을 요청하고, 로그인·페이지 로드로 권한 창을 띄우지 않아요.
- 선택한 대화를 열어둔 동안의 증분 폴링만 써요. 화면이 보이고 focus가 있으면 OS 알림을 띄우지 않아요.
- 제목·본문·tag는 고정 익명 문구예요. 이름·가게명·메시지 내용·방 id를 OS payload에 넣지 않아요.
- 서버 메시지 id로 중복을 막고, 전역 60초 간격·50방 cursor 상한·동시 한 알림을 둬요. 초기 이력·내 전송은 제외해요.
- 권한 거부·미지원·비보안 연결·표시 실패를 UI에 안내하고, 패널/페이지 종료·세션 전환 때 정리해요. 닫힌 페이지를 깨우는 Service Worker나 외부 push는 아니에요.

브라우저 권한·보안 연결과 모바일 생성자 제한은 [MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)를 기준으로 해요.

페이지가 닫혀도 오는 외부 push와 이메일은 채팅 수신 동의, 조용한 시간, 수신 거부, transactional outbox·전달 실패 재시도·중복 정책과 공급자 연결을 정한 뒤 추가해요. 대화 본문은 push payload나 일반 로그에 넣지 않아요.

### 파일

일반 첨부 파일은 아직 열지 않아요. 공개 이미지 버킷에 chat key를 두고 UUID만 숨기는 건 비공개 설계가 아니기 때문이에요. 다음을 모두 갖춘 뒤에 첨부 버튼과 업로드 API를 열어요.

1. 공개 이미지와 분리된 private object 경계 또는 서명 URL만 허용하는 별도 behavior
2. 방 참가자 확인 뒤 짧은 만료 URL 발급, 원본 파일명·경로 비로그
3. 브라우저 MIME·확장자가 아닌 실제 형식/크기 검사와 악성 파일 검사
4. 업로드 실패 보상 삭제, 메시지 커밋 실패 정리, 영구 삭제 outbox
5. 신고 hold·회원 탈퇴·가게 폐업·만료 보존 정책

채팅 사진은 암호화된 별도 경로로 지원해요. [채팅 사진 키](chat-images.md)를 참고하세요.

### AI (도입안)

현재 구현이 아니라 단계별 도입안이에요. 보낼 데이터 범위, 사용자 고지·동의, 공급자 보존/학습 옵트아웃, prompt injection 경계, 월 비용 상한, timeout/circuit breaker, 사람 답과 AI 초안의 표시를 승인한 뒤 **사장님용 답변 초안**부터 시작해요. AI가 자동 전송하거나 예약·환불 상태를 바꾸지 않아요.

```text
Messenger UI
  -> AI Assistant API (로그인, 동의, rate limit, 월 예산)
  -> Orchestrator / Model gateway (호스팅 또는 로컬 모델)
  -> Typed tool gateway
  -> 기존 StoreService / ReservationService / Payment 경계
  -> MySQL
```

- 내부 기능만 연결할 때는 MCP 서버부터 만들지 않아요. 서버의 tool gateway를 먼저 만들고, 외부 AI 클라이언트가 같은 도구를 써야 할 때 MCP adapter를 덧붙여요. MCP의 사용자 확인 흐름이 RESERVE의 권한·가격·슬롯 검사를 대신하지 않아요.
- 모델은 repository·DB를 직접 호출하지 않아요. 인증 사용자, 가게 소유권, 상태, 슬롯, 가격, 비관적 잠금, 환불 규칙의 권한자는 기존 서비스예요.
- 채팅 본문·가게 설명·검색 결과는 신뢰하지 않는 입력이에요. 모델이 만든 `memberId`, `ownerId`, 가격, 상태는 버리고 서버 세션과 현재 DB 값으로 다시 계산해요. tool input은 고정 JSON schema와 허용 목록으로 검사해요.
- 1단계 조회 도구는 `searchStores`, `getStorePolicy`, `getAvailability`, `getMyReservations`만 열어요. 2단계는 `prepareReservation`, `prepareReservationChange`, `prepareCancellation`으로 실행 전 요약안을 만들어요.
- 실제 변경은 날짜·시간·인원·금액·취소 결과를 다시 보여 주고 사용자가 명시적으로 확인한 뒤에만 해요. 확인 토큰에 사용자, 작업 hash, 만료 시각, 일회용 nonce를 묶고 idempotency key로 중복 실행을 막아요.
- 결제는 AI tool이 실행하지 않아요. 기존 결제 화면으로 보내고 PortOne 검증 결과만 신뢰해요. 환불, 사장님 승인·거절, 관리자 조치, QR 체크인은 초기 자동화에서 빼요.
- 로그에는 원문 대신 actor, tool 이름, 대상의 안전한 식별자, 확인 여부, 결과 코드, 모델, latency, token 수를 남겨요. timeout, circuit breaker, 동시 호출 제한, 사용자별 제한, 월 예산 상한, kill switch를 둬요.

도입 순서:

1. 고정 FAQ·가게 정책 검색과 사장님 답변 초안. AI 표시와 피드백만, 자동 전송 없음
2. 로그인 사용자의 예약·빈 시간 읽기 전용 조회. 다른 회원·가게 정보가 섞이지 않는지 두 계정으로 검사
3. 예약 생성·변경·취소의 실행 전 요약안. 명시적 확인과 만료되는 일회용 토큰
4. 무예약금 예약 생성 같은 낮은 위험 작업부터 제한 실행. 결제·환불·QR·관리자 작업은 별도 승인 전까지 사람 흐름 유지

모델은 한 공급자에 묶지 않도록 `ModelGateway`로 감싸요. 개발 PC에서는 Ollama로 작은 한국어 tool-calling 모델을 검증하고, 동시 요청이 필요한 별도 GPU 서버는 vLLM을 검토해요. 웹·DB 서버와 모델을 같은 인스턴스에 두지 않아요. 복잡한 요청만 호스팅 모델로 넘기는 hybrid가 초기 비용과 품질 위험이 가장 작아요.

비용은 `월 요청 수 × 평균 입력/출력 token × 모델 단가`에 embedding·로그·GPU·저장소 비용을 더해 계산해요. 실제 대화 1~2주 분량을 개인정보 제거 후 replay해 품질, p95 지연, 건당 비용을 측정한 뒤 월 상한을 정해요.

## 배포 관문

`chat_room`, `chat_message`, `chat_report`의 스키마 변경은 추가형(column/table/index/unique constraint)이에요. `ddl-auto: update`여도 운영 반영 전 백업·격리 복원을 끝내고, 배포 뒤 실제 MySQL의 컬럼·인덱스·제약과 기존 `SUPPORT` 행을 읽기 전용으로 확인해요.

> 주의: `STORE` enum 값을 `STORE_CHAT`으로 바꾸지 않아요. 이미 저장된 문자열 값과 어긋나기 때문이에요.

## 테스트 범위

- 백엔드: 방 상태, 손님/사장님 권한, 유형 격리, 멱등 재시도, cursor history, 읽음 축, 양방향 차단, 신고 대상·중복·관리자 종결 근거, PII 로그 경계
- 프론트: deep link, 모바일 목록→대화, 사장님 받은편지함 분리, 과거 cursor 병합, A→B→A fencing, 모호한 실패의 client ID 재사용, `Escape`와 focus 복귀, 차단/신고, 관리자 문맥 지연 조회
