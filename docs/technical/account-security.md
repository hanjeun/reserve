# 계정 보안

## 로그인

이메일·비밀번호와 Google·Kakao·Naver를 지원해요. access token은 API 인증, refresh token은 기기별 로그인 유지에 사용해요. 서버는 서명·발급자·용도·만료·회원 상태·인증 버전·현재 세션을 확인해요.

로그인 유지는 기본 미선택이며 로그인 화면의 하나의 선택을 이메일·패스키·소셜 로그인에 함께 적용해요. 미선택은 브라우저 세션 쿠키, 선택은 만료 기간이 있는 쿠키를 사용해요. 서버의 기본 만료 상한은 두 경우 모두 14일 갱신·최대 30일 절대 만료예요. 비밀번호·패스키·소셜 로그인과 추가 인증에서 같은 선택을 보존해요. 기존 세션의 유지 정책은 바꾸지 않아요. 안내에 필요한 만료 기간은 공개 읽기 API인 `GET /api/auth/login-policy`에서 조회해요.

갱신은 서명한 선택을 사용하고, 소셜 콜백은 state로 확인한 최초 요청의 선택을 사용해요. 탭 닫기는 로그아웃이 아니며 세션 쿠키도 브라우저의 세션 복원 기능으로 복원될 수 있어요. 공용 기기에서는 사용 후 명시적으로 로그아웃해요. [쿠키 수명](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)을 참고해요.

비밀번호 변경·탈퇴·인증 수단 변경은 기존 인증을 폐기해요. 공급자 계정 변경 알림도 서명과 대상을 확인해 처리해요.

로그인 초기 상태는 캐시하지 않는 `GET /api/auth/session`에서 확인해요. 익명 방문도 200으로 응답하며 유효한 refresh token 여부만 갱신 가능성으로 안내해요. 이 조회는 쿠키를 발급하지 않아요. 실제 갱신은 기존 검증·회전 절차를 거쳐요.

## 접속 환경과 시간제 제한

IP 보호는 `reserve.security.ip-protection.enabled`의 기본값이 `false`예요. 활성화에는 환경별 Redis와 별도 32바이트 키의 base64 값인 `reserve.security.ip-protection.fingerprint-key`, 실제 nginx만 포함하는 `trusted-proxies` CIDR 목록이 필요해요. 키는 보호 설정으로 전달하고 프론트·로그·저장소에 넣지 않아요. 앱 포트 직접 접근 차단과 프록시의 X-Real-IP 덮어쓰기를 먼저 확인해요. 신뢰 프록시를 지정하지 않으면 직접 연결 주소만 사용해요.

배포는 `RESERVE_SECURITY_IP_PROTECTION_ENABLED`·`RESERVE_SECURITY_IP_PROTECTION_TRUSTED_PROXIES` 변수와 `RESERVE_SECURITY_IP_PROTECTION_FINGERPRINT_KEY` Secret을 전달해요. 운영 활성화에는 Redis의 제한 계정 `reserve_app`과 내부망 nginx 주소 `172.30.30.2/32`가 필요해요. 공유 네트워크 전체를 신뢰하지 않아요. Redis·키·프록시 준비 검사가 실패하면 컨테이너 전환 전에 중단해요. 프록시와 직접 접근 차단의 전환 절차는 [배포](deployments.md)를 따라요.

Redis 앱 권한은 `scripts/redis-app.rules`의 명령과 `reserve:prod:*` 키·채널로 제한하고 기존 관리자 인증과 분리해요. 비밀번호 대신 해시를 담은 ACL 파일을 보호된 경로에 저장하고 읽기 전용으로 연결해요. 활성화 전 검사에서는 호스트 포트 미공개·권한 범위·ACL 지속 설정·메모리 여유 25% 이상·`noeviction`을 확인해요. IP Lua는 OOM 실행을 허용하지 않으며, 메모리·권한·연결 장애를 추가 인증 성공으로 취급하지 않아요. Redis 상태가 유실되면 신뢰 이력은 다시 확인하고 기존 관리자 MFA는 유지해요.

활성화하면 새 로그인에서 최근 확인한 IP인지 검사해요. 새 환경은 등록한 패스키·인증 앱·복구코드로 확인하며, 추가 수단이 없는 일반 회원·사업자는 등록 이메일의 일회용 코드로 확인해요. 새 수단 등록·유예로 확인을 건너뛸 수 없고 관리자 MFA를 이메일로 대체하지 않아요. 회원·인증 버전·5분 요청·현재 IP를 확인한 뒤 세션을 발급하고, DB 커밋 후에만 신뢰 이력을 남겨요. 기존 세션의 망 변경·refresh만으로 계정을 잠그지 않아요.

IP·회원 식별자는 전용 HMAC으로 가명화해 Redis에 보관해요. 신뢰 이력은 회원별 최대 8개·각 30일이고 확인 요청은 5분이에요. 이메일 코드는 해시만 보관하며 1분 재발송 제한·최대 5회 확인·일회용 소비를 적용해요. 인증 실패·인증 제한 응답이 한 IP에서 5분 동안 20회 누적되면 15분 제한하고, 24시간 안에 반복되면 1시간 제한해요. 제한 중 재요청으로 기한을 연장하거나 계정을 영구 정지하지 않아요. 응답은 `429`와 `Retry-After`를 사용해요.

서명된 공급자 이벤트·PG 웹훅, 로그아웃·세션 복구·인증 취소와 진행 중 OAuth 콜백은 각자의 기존 인증 관문을 유지해요. Redis 장애 때 기존 로컬 요청 제한을 유지하고, 새 환경의 기본 인증만으로 신뢰 확인을 우회하지 않아요. 관리자 MFA·직접 패스키 로그인은 이력 조회 장애만으로 잠그지 않아요. 이 정책은 VPN·국가를 판정하지 않아요. 격리 Redis 검사는 기존 `RESERVE_REDIS_INTEGRATION=true` 시험 관문에서 실행해요. 실제 활성화는 프록시·키·Redis 용량과 장애·복구 확인 뒤 별도로 진행해요.

## 패스키와 인증 앱

`reserve.mfa.enabled=true`이면 관리자만 추가 인증이 필수예요. 일반 회원·사업자는 기본적으로 등록 여부와 관계없이 선택한 이메일·소셜 방법으로 로그인하며, IP 보호를 켠 경우 새 환경의 확인을 추가해요. 패스키는 로그인 화면에서 직접 선택할 때 사용하며 마이페이지에서 등록·해제할 수 있어요. 신규 등록을 중지해도 관리자가 설정한 인증은 유지해요.

- 로그인 화면의 패스키 버튼은 브라우저의 저장된 인증 수단 선택창으로 바로 이어져요. 관리자의 기본 로그인 뒤에는 등록한 추가 인증을 확인하며, 패스키를 취소하면 인증 앱·복구코드로 전환할 수 있어요.
- 로그인 화면의 등록 아이콘은 먼저 로그인한 뒤 본인 계정의 보안 설정으로 이어져요. 일반 회원·사업자는 같은 설정에서 선택해 등록하며, 등록 전 기본 인증과 현재 기기 세션을 확인해요.
- 패스키는 기기·비밀번호 관리자에 저장해요. 브라우저·운영체제의 기본 WebAuthn 창을 사용하고 특정 저장소나 인증기 종류로 제한하지 않아요. WebAuthn의 challenge·RP ID·허용 출처·서명·사용자 확인을 서버에서 검증하며 개인 키와 생체 정보는 서버에 보내지 않아요. 인증 앱의 QR·6자리 코드와는 다른 수단이에요.
- OTP는 30초·6자리 TOTP를 사용해요. ±1 구간만 허용하고 이미 사용한 구간을 다시 받지 않아요.
- 관리자는 기본 로그인 뒤 추가 인증을 마쳐야 앱 토큰을 발급해요. 로그인 유지 선택과 인증 버전·만료 검증을 보존하며 관리·패스키 로그인 요청으로 이를 건너뛸 수 없어요. 중간 요청은 5분·최대 5회·일회용이며 HttpOnly 쿠키에 연결해요.
- 일반 회원·사업자의 수단 추가·해제·복구코드 재발급은 현재 비밀번호 또는 5분 이내에 확인한 연결 소셜 계정으로 관리할 수 있어요. 관리자에게는 등록한 인증 수단의 추가 확인을 요구해요. 관리 요청은 현재 회원·기기 세션·인증 버전에 묶고, 기본 인증만 확인한 관리를 MFA 완료 세션으로 승격하지 않아요.
- 등록·해제 뒤 기존 세션을 폐기해요. 복구코드는 10개를 한 번만 표시하고 해시만 저장해요. 사용한 코드는 폐기해요.
- 일반 회원·사업자는 마지막 인증 수단도 해제할 수 있어요. 관리자의 추가 인증과 마지막 수단은 해제할 수 없어요. 관리자가 모든 수단과 복구코드를 잃은 경우의 수동 복구는 별도 운영 절차로 처리해요.

`reserve.mfa.rp-id`와 `reserve.mfa.origins`는 실제 앱 출처로 고정해요. OTP의 `reserve.mfa.encryption-key`는 독립된 Base64 AES-256 키예요. 활성화 시 출처와 키를 검사하고, 백업·복구에도 같은 키가 필요해요. 로컬은 localhost용 RP·출처와 운영과 다른 키를 사용해요. 개발용 localhost 출처를 운영에 섞지 않아요.

## 예약 관리 권한

사업자 예약 조회·집계는 관리자 계정으로 접속해도 본인 가게로 제한해요. 가게의 승인·거절·완료·노쇼·취소·숨김은 실제 소유권을 검사하며 관리자 역할로 우회하지 않아요. 관리자 전체 예약은 별도 읽기 API `GET /api/reservations/admin/page`를 사용해요. 관리자 휴지통·감사 기능은 기존 관리 경로에서 처리해요.

직접 휴지통 경로도 회원 → 예약 → 결제 잠금을 공유하고 진행 중 예약·미해결 결제·환불을 숨기지 않아요. 거래 증거는 일반 가게·관리자 목록의 개인정보 가림과 분리하며, 별도 경로에서 추가 인증·목적·접근 기록을 확인해요.

## 키와 빌드 경계

서버 키는 브라우저의 `VITE_` 환경변수에 넣지 않아요. 결제 채널·지도 JavaScript 식별자와 Sentry DSN은 브라우저에 공개되는 값이므로 공급자에서 실제 앱 출처를 제한해요. 권한이 있는 서버 키와 혼용하지 않아요.

키·로컬 설정은 Git과 Docker 빌드 문맥에서 제외해요. `scripts/check-secret-boundaries.mjs`는 현재 소스와 지정한 빌드 환경 파일을 검사하고 값 대신 경로·행·규칙만 출력해요. Git 이력과 공급자에서의 실제 폐기는 별도로 확인해요. 로컬 DB 암호는 공개 기본값 대신 보호한 로컬 설정이나 `DB_PASSWORD_LOCAL`에서 받아요.

JWT·MFA·채팅·피드·공급자 토큰 키를 분리해요. 암호화 키를 교체하기 전에 기존 자료와 복구 이미지의 복호화 가능성을 확인하며, 로컬 키를 운영 키로 복사하지 않아요. 키 보관 위치·권한·배포 전달·대응 복구를 함께 확인해요. Sentry는 헤더·검색 매개변수·본문을 수집하지 않고 세션 재현의 텍스트·미디어 가림을 유지해요.

## 비밀번호와 이메일

비밀번호는 8~64자·영문과 숫자를 포함하고 UTF-8 72바이트 이하여야 해요. bcrypt로 저장하고 알려진 유출 목록과 대조해요. 이메일 인증은 목적·만료·시도 제한을 확인해요.

인증 코드·등록 비밀·복구코드는 URL이나 브라우저 저장소에 남기지 않아요. 공급자 토큰은 별도 키로 암호화하고, 탈퇴 후 연결 해제는 저장한 작업으로 재시도해요.

## 개인 검색

개인 검색은 현재 회원의 예약·웨이팅·대화 권한으로 제한해요. 검색만으로 읽음·업무 상태를 바꾸지 않아요. 공개 캐시에 저장하지 않으며 계정·세션이 바뀌면 이전 결과를 폐기해요.

관련 코드는 backend의 config·member·email 영역에 있어요.
