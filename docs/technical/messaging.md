# 통합 메시지와 가게 문의

> 2026-09-13 `local-preview-all-changes` 로컬 프리뷰 기준. 아래 로컬 구현과 실제 운영·두 계정 실행 증거를 구분한다. 아직 통합·배포하지 않았다.

## 제품 경계

하나의 `MessengerShell`이 두 대화 유형을 보여주되 권한과 읽음 상태는 섞지 않는다.

| 유형 | 참가자 | 시작 조건 | 상대 받은편지함 |
|---|---|---|---|
| `SUPPORT` | 회원 ↔ RESERVE 관리자 | 로그인 회원이 고객지원 열기/첫 전송 | 관리자 채팅 탭 |
| `STORE` | 회원 ↔ 해당 가게의 현재 소유자 | 로그인 회원이 공개·운영 가능한 타인 가게에서 문의 | 사장님 `가게 받은 문의` |

가게 문의는 예약 전 질문을 위한 기능이므로 예약 보유를 필수 조건으로 두지 않는다. 대신 자기 가게에는
문의할 수 없고, 삭제·정지된 가게에는 새 메시지를 보낼 수 없다. 가게가 나중에 닫혀도 기존 대화는 읽을 수 있다.
관리자 고객지원 API는 `SUPPORT`만, 사장님 받은편지함은 `STORE`만 받아 유형 혼동으로 권한이 넓어지지 않게 한다.

기존 `Inquiry`는 비회원도 남길 수 있는 단건 문의다. 로그인 사용자의 연속 대화인 `ChatRoom`과 자동으로
합치지 않는다.

## 화면

- 우측 하단의 단일 launcher는 PC에서 독립 패널, 모바일에서 `/messages` 전체 화면을 연다. 프로필 메뉴의 중복 메시지 링크는 제거했다.
- launcher는 라이트·다크 모두 흰 배경과 브랜드 전경 아이콘을 사용한다. 선택형 `launcherImageSrc`로 소유 사진을 연결할 수 있으며 PC 패널이 열리면 X, 사진 로드 실패 시 기본 메시지 아이콘이다. 기본 App은 사진을 지정하지 않는다. 크기·hover/눌림·focus·모션 정책은 유지한다. [시각 확인·광고/저장소 후속 검토](history/2026-09-preview/channel-style-advertising-and-storage-review-2026-09-13.md)는 실제 로그인 대화의 실행 증거와 구분한다.
- 이동 메뉴는 본문 아래 고정 `홈 · 대화 · 설정`이다. 홈은 RESERVE 사진 커버와 ‘고객지원에 문의’ 카드 하나, 대화는 실제 상대별 목록, 설정은 현재 계정과 기존 PC 세션 알림이다. 최근 목록·상단 SegmentedControl·중복 설명·알림 설정·사장님 바로가기를 홈에 반복하지 않는다. footer hover는 투명 배경에 아이콘만 primary이며 선택/포커스/배지는 유지한다.
- 내부 사진은 런처와 별개인 `coverImageSrc`로 교체 가능하며 기본은 기존 `/og-image.png`다. 설정/업로드 UI는 없다. SUPPORT 상대와 ADMIN 발신자는 API와 화면에서 항상 `RESERVE 고객지원`으로 표시하고 개인 이름·사진을 제공하지 않는다. 회원의 STORE 문의에서는 가게 이름, OWNER 받은 문의에서는 고객 이름을 보여준다. 마지막 대화 미리보기는 저장값을 우선하고, 기존 방의 값이 비었을 때만 권한 확인된 방의 마지막 실제 메시지를 한 페이지 단위로 읽기 전용 조회한다. 신규 회원 ID·이메일 공개나 담당자 배정은 하지 않는다. [이전 계정별 표시 검토 기록](history/2026-09-preview/messenger-and-discovery-refinement-2026-09-14.md)은 현재 계약이 아니다.
- **설정의 내 사진은 현재 로그인 사용자**의 안전한 `profileImageUrl` 우선·`profileImage` fallback이다. 관리자/브랜드 사진으로 대체하지 않고 부재/실패는 본인 이니셜·사용자 아이콘으로 표시한다. 사진/계정 변경 시 이전 실패 상태를 폐기한다. 실제 `notificationControl`이 있을 때만 대화 환경/구분선을 표시하고 모바일 PC 안내·초안 설명은 제거했다. 권한/초안 저장 정책은 변경하지 않았다. [현재 검사·실계정 경계](history/2026-09-preview/benefit-banners-and-account-avatar-2026-09-14.md).
- PC 패널은 홈/목록/설정/대화 모두 최대 420px이다. 패널과 모바일에서 상대를 선택하면 목록 대신 대화가 나오고, 내부 뒤로가기로 목록에 복귀한다. 대화 안에서는 하단 메뉴 대신 입력란을 사용한다. PC `/messages` 작업 화면의 두 칸 목록·내용과 목록 하단 메뉴는 유지한다.
- 대화 목록 하단의 중복 ‘관리자에게 문의’ 버튼은 제거했다. 홈의 문의 카드와 실제 기존 상대 선택에서만 시작하며 빈/오류 목록도 footer의 홈으로 돌아갈 수 있다. 입력 박스는 50px, 한 줄 textarea는 40px/24px 줄 높이, 전송 터치 영역은 44px로 가운데 정렬한다. 모바일 글꼴은 16px이며 여러 줄은 내부 스크롤한다. 아래의 초안·키보드 안내 문구만 제거했고 Enter 전송·Shift+Enter 줄바꿈·한글 조합·2000자 제한·세션 초안 정책은 유지했다. [국소 변경과 검사](history/2026-09-preview/compact-messenger-and-home-store-rows-2026-09-14.md).
- 목록 제목·새로고침은 `MessengerListHeading`의 72px 헤더에서 가운데 정렬하며 PC 닫기도 같은 높이를 사용한다. 새로고침·닫기는 각각 44px 터치 영역이다. 사진 위에 중복되던 RESERVE 제목은 제거하고 접근성 제목 ‘메시지’만 시각적으로 숨겨 유지한다. 사진 자체에 포함된 브랜드는 보존하고 관리자 개인 표시 정보는 사용하지 않는다.
- 목록·받은 문의·unread 조회는 즉시 재시도를 하지 않으며 429를 제외한 4xx가 발생하면 주기·포커스·재연결 자동 갱신을 멈춘다. 오류와 명시적 ‘다시 시도’는 유지한다. 네트워크 장애·429·5xx는 기존 주기 갱신으로 복구를 시도한다. 일반 사용자에게는 목록 새로고침으로 사업자 받은 문의를 호출하지 않는다. [헤더 실측·실제 로컬 경로 404](history/2026-09-preview/messenger-header-and-runtime-routing-2026-09-14.md).
- 홈/목록/설정 열기는 방 생성·방 메시지 4초 폴링·읽음 처리를 시작하지 않는다. 대화 목록/받은편지함의 30초 갱신은 홈·설정에서도 실행되므로 ‘폴링이 전혀 없다’는 뜻은 아니다. 실제 방이 없는 고객지원을 가짜 ‘최근 대화’로 끼워 넣지 않으며, 명시적 ‘고객지원에 문의’ 또는 기존 상대 선택에서만 방을 연다. 실제 unread는 각 대화 행에서 표시하며 로딩한 일부 페이지의 합을 전체 배지로 표시하지 않는다.
- 2026-09-13 사용자 확정: ‘여러 사람’은 여러 상대와 각각 대화하는 목록이다. 기존 회원별 SUPPORT·회원×가게별 STORE와 사장님 받은 문의 모델을 유지한다. 그룹방·직원 초대·담당자 배정·회원끼리 자유 DM·주제별 새 문의방은 구현하지 않았다.
- 중복되는 고정 하단 페이지 메뉴는 제거했고 대화 화면도 그 공간을 사용한다. 가게 상세의 문의 버튼은
  `/messages?storeId={id}`로 들어가 브라우저 뒤로가기가 자연스럽게 동작한다.
- 패널은 focus trap, `Escape`, 닫힌 뒤 launcher focus 복귀, reduced-motion, 44px 터치 목표를 지킨다.
- `내 대화`와 `가게 받은 문의`를 분리해 같은 사람이 손님과 사장님 역할을 동시에 가져도 읽음 수가 섞이지 않는다.
- 대화 전체 영역을 live region으로 두지 않는다. 첫 로드와 과거 메시지 50개를 화면 낭독기가 매번 다시 읽는
  부작용이 더 크기 때문이다. 최초 이력은 PC 세션 알림의 입력으로도 사용하지 않는다.
- 첫 MEMBER/SUPPORT 문의는 조회 성공·전송 가능·현재/이전 이력 없음이 확인된 뒤 짧은 인사와 흰 질문 버튼을 보여준다. 질문은 초안에만 추가하며 보내기에서 전송한다. 안내는 서버 메시지나 실제 상담원 답변으로 저장하지 않는다. [이번 구현·76개 검사·실제 로컬 404·초기화 보류](history/2026-09-preview/support-inquiry-and-chat-reset-2026-09-14.md).

## 저장과 전송 안정성

- 메시지는 DB의 `chat_message`, 방 요약은 `chat_room`에 영속화한다. 컨테이너 메모리에 대화 본문을 보관하지 않는다.
- 클라이언트는 전송 시 `clientMessageId`를 만들고 응답을 잃은 같은 본문 재시도에 같은 값을 쓴다.
  서버의 `(room_id, sender_member_id, client_message_id)` 유일 제약과 방 행 잠금이 중복 저장을 막는다.
- 첫 화면은 최근 50개만 받고, 위로 요청할 때 `beforeId` cursor로 과거 50개를 가져온다. 전체 건수 count는 하지 않는다.
- 열린 대화만 4초 증분 폴링하고 목록은 30초, 닫힌 launcher 배지는 60초 주기로 갱신한다. 목록·배지의 경로/권한 4xx에서는 위 자동 갱신 중단 정책을 적용한다.
  WebSocket 연결 상태를 서버에 두지 않는다.
- A → B → A처럼 빠르게 방을 바꿔도 요청 세대로 load/poll/send를 fencing하여 이전 A 응답이 새 A를 덮지 않는다.
  수동 과거 조회도 방/화면 세대를 검사해 늦은 성공·오류·finally가 다른 대화나 설정 전환 후 화면에 반영되지 않게 한다.
  전환 때 과거 조회의 이전 스크롤 복원값도 폐기한다.
- 같은 방 재조회도 이전 요청을 즉시 무효화한다. 로드 실패·대기 중에는 폴링과 전송을 막고 같은 방의 응답 유실 재시도 키는 보존한다. 읽음 응답의 캐시 갱신도 방/화면/세션 세대를 검사한다. 이것은 실행 중인 서버의 API 404를 해결하는 기능이 아니다.
- 전송 말풍선은 먼저 보이되 실패하면 제거하고, 새 입력이 없을 때만 해당 대화의 입력을 복원한다. 늦은 실패가 새 입력이나 새 로그인 세션을 덮지 않는다. 응답 유실 뒤 재시도는 위 멱등 키를 재사용한다.
- 읽지 않은 수는 회원·관리자·사장님 세 축이다. 메시지 추가와 증가는 같은 방의 비관적 잠금 아래 처리하고,
  현재 창이 실제로 보이고 focus가 있을 때만 폴링 수신분을 읽음 처리한다.
- 입력 초안은 대화별로 세션 메모리에만 둔다. 최대 20개/각 2000자이며 최근 편집 순으로 보존한다. DB·localStorage·sessionStorage에는 쓰지 않고 새로고침·로그아웃·같은 계정 재로그인·계정/역할 전환 때 폐기한다.
- 사장님 `OWNER` 작성란의 `답변 문구`는 프로젝트가 직접 작성한 고정 안내 문구이다. 기존 입력 뒤에 삽입할 뿐 자동 전송하지 않으며 AI 생성·예약 확정·환불 보장을 의미하지 않는다.

## API

| 경로 | 역할 |
|---|---|
| `GET /api/chat/conversations` | 회원 관점의 고객지원·가게 문의 목록 |
| `GET /api/chat/support` / `POST /api/chat/support/messages` | 고객지원 열기·전송 |
| `GET /api/chat/stores/{storeId}` / `POST .../messages` | 손님 관점 가게 문의 열기·전송 |
| `GET /api/chat/store-inbox` | 소유 가게의 받은 문의 목록 |
| `GET /api/chat/store-inbox/{roomId}` / `POST .../messages` | 사장님 관점 열기·답장 |
| `GET /api/chat/rooms/{roomId}/messages?afterId=` | 참가자 증분 폴링 |
| `GET /api/chat/rooms/{roomId}/history?beforeId=&size=` | 참가자 cursor 과거 내역 |
| `POST /api/chat/rooms/{roomId}/read?viewerRole=` | 보이는 화면의 명시적 읽음 처리 |
| `PUT /api/chat/rooms/{roomId}/block?viewerRole=&blocked=` | 역할별 차단·자기 차단 해제 |
| `POST /api/chat/rooms/{roomId}/reports?viewerRole=` | 대화 전체 또는 상대 메시지 신고 |
| `GET /api/chat/unread` | 회원·소유 가게를 합친 launcher 배지 |
| `GET /api/admin/chat/reports` / `GET .../{id}/context` | 관리자 신고 목록·읽음 상태를 바꾸지 않는 문맥 조회 |
| `PATCH /api/admin/chat/reports/{id}` | 검토 시작·근거 있는 조치 완료/기각 |

이전 `/api/chat/my*`와 관리자 `/api/admin/chat*` 계약은 기존 화면 호환을 위해 유지한다.
관리자 증분 조회도 `getNewMessagesAsAdmin`에서 `SUPPORT`만 허용한다. 관리자라는 이유만으로
임의 `STORE` 방을 폴링할 수 없으며, 가게 신고 검토는 기존 신고 문맥 API로 분리한다.

## 보존·차단·신고

메시지는 현재 수정·삭제 API가 없는 append-only 기록이며 회원 탈퇴·가게 폐업 뒤에도 보존한다. 이것은
최종 법적 보존기간이 확정됐다는 뜻이 아니다. 자동 파기는 승인된 기간과 분쟁 hold 규칙이 생기기 전까지 추가하지 않는다.

차단·신고는 2026-09-12 로컬 프리뷰에 다음 정책으로 구현했다.

- 회원 또는 가게 역할 중 한쪽이라도 차단하면 양쪽 새 전송을 모두 멈춘다. 각 참가자는 자기 차단만 해제할 수 있다.
- 가게 쪽 차단은 개인 계정이 아니라 가게 역할의 운영 상태이므로 소유자가 바뀌어도 승계한다.
- 신고 사유는 스팸·괴롭힘·부적절한 내용·사기·기타이며, 기타는 설명을 필수로 받는다.
- 대화 전체 또는 상대가 보낸 특정 메시지를 신고할 수 있다. 같은 참가자의 같은 대상 신고는 안정 키로 한 번만 저장한다.
- 신고는 회원별 10분 5건으로 제한한다. 신고만으로 자동 차단·회원 정지·가게 제재를 하지 않는다.
- 관리자는 접수 → 검토 중 → 조치 완료/기각 상태를 관리하고, 종결에는 처리 근거를 필수로 남긴다.

아직 확정되지 않은 것은 신고·분쟁 중인 대화의 법적 보존 hold 기간과 회원 파기 요청 예외다. 이 결정 전에는
신고·메시지 자동 삭제 배치를 만들지 않는다.

## 확장 기능 관문

### 알림

앱 안 unread 배지와 받은편지함 정렬 외에 **선택형 PC 세션 알림**을 로컬 구현했다.

- 기본 OFF이며 `PC 알림 켜기` 사용자 클릭에서만 권한을 요청한다. 로그인·페이지 로드로 권한 창을 띄우지 않는다.
- 선택한 대화를 열어둔 동안 새 증분 폴링만 사용한다. 화면이 보이고 focus가 있으면 OS 알림은 띄우지 않는다.
- 알림 제목·본문·tag는 고정 익명 문구이다. 이름·가게명·메시지 내용·방 id를 OS payload에 넣지 않는다.
- 서버 메시지 id로 중복을 막고 전역 60초 간격·50방 cursor 상한·동시 한 알림을 둔다. 초기 이력·내 전송은 제외한다.
- 권한 거부·미지원·비보안 연결·표시 실패를 UI에 안내하며 패널/페이지 종료·세션 전환 시 정리한다. 닫힌 페이지를 깨우는 Service Worker나 외부 push가 아니다.

브라우저 권한·보안 연결과 모바일 생성자 제한은 [MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)를 기준으로 구분했다.
실제 OS 알림·권한 창은 이번 검사에서 실행하지 않았으며 mock 검사만으로 전달 성공을 주장하지 않는다.

페이지가 닫혀도 오는 외부 push와 이메일은 채팅 수신 동의, 조용한 시간, 수신 거부,
transactional outbox·전달 실패 재시도·중복 정책 및 공급자 연결을 정한 뒤 추가한다. 대화 본문을
push payload나 일반 로그에 넣지 않는다.

### 파일

현재 이미지 버킷은 CloudFront 공개 전달과 함께 쓰이므로 chat key를 같은 버킷에 저장하고 UUID만 숨기는 것은
비공개 설계가 아니다. 다음 조건을 모두 충족하기 전에는 첨부 버튼이나 업로드 API를 열지 않는다.

1. 공개 이미지와 분리된 private object 경계 또는 서명 URL만 허용하는 별도 behavior
2. 방 참가자 확인 뒤 짧은 만료 URL 발급, 원본 파일명·경로 비로그
3. 브라우저 MIME·확장자가 아닌 실제 형식/크기 검사와 악성 파일 검사
4. 업로드 실패 보상 삭제, 메시지 커밋 실패 정리, 영구 삭제 outbox
5. 신고 hold·회원 탈퇴·가게 폐업·만료 보존정책

### AI

AI 답변은 공급자와 모델만 고르면 끝나는 기능이 아니다. 보낼 데이터 범위, 사용자 고지·동의, 공급자 보존/학습
옵트아웃, prompt injection 경계, 월 비용 상한, timeout/circuit breaker, 사람이 보낸 답과 AI 초안의 표시를
승인한 뒤 **사장님용 답변 초안**부터 시작한다. AI가 자동 전송하거나 예약·환불 상태를 바꾸게 하지 않는다.

아래는 현재 구현이 아니라 단계별 도입안이다. 내부 기능만 연결할 때는 별도 MCP 서버부터 만들 필요가 없다.
서버의 tool gateway를 먼저 만들고, 이후 외부의 신뢰된 AI 클라이언트에서도 같은 도구를 써야 할 때 MCP adapter를
덧붙인다. 최신 MCP 규격은 사용자 입력·확인을 요청하는 흐름을 지원하지만, 그 확인만으로 RESERVE의 권한·가격·슬롯
검사를 대신하지 않는다.

```text
Messenger UI
  -> AI Assistant API (로그인, 동의, rate limit, 월 예산)
  -> Orchestrator / Model gateway (호스팅 또는 로컬 모델)
  -> Typed tool gateway
  -> 기존 StoreService / ReservationService / Payment 경계
  -> MySQL
```

- 모델은 repository와 DB를 직접 호출하지 않는다. 기존 서비스가 인증 사용자, 가게 소유권, 상태, 슬롯, 가격,
  비관적 잠금과 환불 규칙의 유일한 권한자다.
- 채팅 본문·가게 설명·검색 결과는 모두 신뢰하지 않는 입력이다. 모델이 만든 `memberId`, `ownerId`, 가격, 상태는
  버리고 서버 세션과 현재 DB 값으로 다시 계산한다. tool input은 고정 JSON schema와 허용 목록으로 검사한다.
- 1단계 조회 도구는 `searchStores`, `getStorePolicy`, `getAvailability`, `getMyReservations`만 연다.
- 2단계는 `prepareReservation`, `prepareReservationChange`, `prepareCancellation`로 실행 전 요약안을 만든다.
- 실제 변경은 화면에서 날짜·시간·인원·금액·취소 결과를 다시 보여주고 사용자가 명시적으로 확인한 뒤에만 한다.
  확인 토큰에는 사용자, 작업 hash, 만료시각, 일회용 nonce를 묶고 idempotency key로 중복 실행을 막는다.
- 결제는 AI tool이 실행하지 않는다. 기존 결제 화면으로 이동시키고 기존 PortOne 검증 결과만 신뢰한다. 환불,
  사장님 승인·거절, 관리자 조치, QR 체크인은 초기 자동화 대상에서 제외한다.
- 로그에는 원문 대화와 개인정보 대신 actor, tool 이름, 대상의 안전한 식별자, 확인 여부, 결과 코드, 모델,
  latency와 token 수를 남긴다. timeout, circuit breaker, 동시 호출 제한, 사용자별 제한, 월 예산 상한과 즉시 끄는
  kill switch를 둔다.

도입 순서는 다음과 같다.

1. 고정 FAQ·가게 정책 검색과 **사장님 답변 초안**. AI 표시와 피드백만 제공하고 자동 전송하지 않는다.
2. 로그인 사용자의 예약·빈 시간 읽기 전용 조회. 다른 회원·다른 가게 정보가 섞이지 않는 두 계정 검사를 한다.
3. 예약 생성·변경·취소의 실행 전 요약안. 명시적 확인과 만료되는 일회용 토큰을 구현한다.
4. 무예약금 예약 생성 같은 낮은 위험 작업부터 제한적으로 실행한다. 결제·환불·QR·관리자 작업은 별도 승인과
   결제 장애/재시도/감사 검증 전까지 사람 흐름을 유지한다.

모델 운영은 처음부터 한 공급자에 묶지 않는 `ModelGateway`로 감싼다. 개발 PC의 작은 한국어 tool-calling 모델은
Ollama로 빠르게 검증하고, 동시 요청이 필요한 별도 GPU 서버는 OpenAI 호환 API와 batching을 제공하는 vLLM을
검토한다. 현재 웹·DB 서버와 모델을 같은 인스턴스에 올리지 않는다. 양자화 8B급은 개발/FAQ 분류, 14B급은 초안과
간단한 도구 선택의 출발점으로 삼되, 한국어 예약 조건·도구 인자 정확도·지연시간을 실제 데이터에서 측정해 결정한다.
복잡한 요청만 호스팅 모델로 넘기는 hybrid가 초기 비용과 품질 위험이 가장 작다.

비용은 `월 요청 수 × 평균 입력/출력 token × 모델 단가`에 embedding, 로그, GPU, 저장소 비용을 더해 계산한다.
호스팅 모델은 호출량이 적을 때 싸고 운영 부담이 낮다. 로컬 모델은 token 청구가 없지만 GPU 임대/구매, 전력,
모니터링, 모델 업데이트와 장애 대응 비용이 생긴다. 실제 대화 1~2주 분량을 개인정보 제거 후 replay하여 품질,
p95 지연시간, 건당 비용을 함께 측정한 뒤 월 상한을 정한다.

## 배포 관문

이번 구현은 `chat_room`, `chat_message`, `chat_report`에 additive column/table/index/unique constraint를 추가한다. 저장소가
`ddl-auto: update`를 쓰더라도 운영 반영 전 백업·격리 복원을 완료하고, 배포 뒤 실제 MySQL의 컬럼·인덱스·제약과

있는 문자열 값의 drift를 피하기 위해서다.

## 채팅 첫 안내 · 자동 문답 (2026-09-23)

손님이 대화를 처음 열었을 때(메시지 0개) 보이는 안내다. 고객지원은 관리자가, 가게 문의는 사장님이 설정한다.

- **구성(2026-09-24 통일)**: ① 확성기 줄 = 공지사항(없으면 "안녕하세요. {이름}입니다.") ② 고객지원·가게 공통 인사 문장(답하는 사람만 관리자/사장님) ③ 자주 묻는 질문. 보낸 사람 표시(아바타 + 이름)는 대화창 헤더와 겹쳐서 두지 않는다.

- **동작**: 질문 버튼을 누르면 저장된 답변이 바로 보인다(자동 문답). 서버 메시지로 보내지 않으므로
  사장님·관리자 문의함, 읽지 않음 수, 알림에 영향이 없다. 고객지원은 관리자가 설정하기 전에도 기본 문답 4개(서버 기본값, 답변 포함)가 자동 문답으로 동작한다.
  서버를 부를 수 없을 때의 화면 대체값만 답변 없이 입력칸에 질문을 채운다.
- **가게 문의**는 사장님이 공지사항이나 질문을 하나라도 설정했을 때만 안내를 보인다. 없으면 기존 빈 화면 문구 그대로다.
- **한도**: 공지사항 100자(한 줄 — 줄바꿈·연속 공백은 한 칸), 질문 최대 5개(질문 40자, 답변 300자), 같은 질문 중복 금지(대소문자·공백 무시).
  화면에서 칸별로 먼저 막고(useFormErrors), 서버가 다시 검사한다.
- **저장 모델**: `chat_intro`(scope_key = `SUPPORT` 또는 `STORE:{가게ID}`, UNIQUE, notice) + `chat_intro_item`(질문·답변·sort_order).
  store_id 를 NULL 로 고객지원을 표시하지 않는 이유 — MySQL UNIQUE 는 NULL 을 여러 개 허용한다.
  저장은 항상 전체 교체이며, 입력 검증이 끝난 뒤에만 설정 행을 만든다.
- **API**
  | 메서드 | 경로 | 권한 |
  |---|---|---|
  | GET | `/api/chat/intro/support` | 로그인 |
  | GET | `/api/chat/intro/stores/{storeId}` | 로그인 (삭제된 가게 404) |
  | PUT | `/api/chat/intro/stores/{storeId}` | 그 가게의 사장님(사업자 역할 + 소유) |
  | PUT | `/api/admin/chat/intro` | 관리자 |
- **화면**: 사업자 패널 › 자동 응답(가게별, 공통 FilterToolbar·가게 2개 이상일 때 선택·URL `chatIntroStore`), 관리자 패널 › 자동 응답(고객지원). 둘 다 `ChatIntroEditor` 를 쓰고(공지사항 카드·질문 카드·되돌리기/저장 = 모달 푸터와 같은 outline sm + primary sm, 모바일은 `설정 | 미리보기` 전환),
  미리보기(`ChatIntroPreview`)는 메신저 대화창의 실제 클래스로 그린 대화창 안에 같은 `ChatIntro` 를 그린다. 안내 여부는 손님 메신저와 같은 `hasIntroContent` 로 판정해, 아무것도 설정하지 않은 가게는 미리보기도 빈 대화창 문구를 보인다. 저장하면 손님 메신저가 쓰는 같은 캐시 키
  (`chatKeys.intro(scope)`)를 갱신해 바로 반영된다.

### 채팅 관리 (2026-09-24)

- 사업자 패널·관리자 패널의 `채팅 관리` 탭이 같은 편집기(`ChatIntroEditor`)·스켈레톤(`ChatIntroEditorSkeleton`)을 쓴다: 프로필 · 공지사항 · 인사말 · 자주 묻는 질문.
- 인사말은 `{이름}`(손님 이름, 모르면 "회원")과 빈 줄 문단을 지원하고, 저장 전에는 서버 기본 문구가 칸에 채워져 있다(`chat_intro.greeting`, 200자).
- 표시 이름·사진은 **고객지원만** 바꾼다(`display_name` 30자, `avatar_url` — `POST /api/admin/chat/intro/avatar` 로 올린 `support/chat` 아래 파일만, 바뀐 옛 파일은 삭제 대기열). 메신저 본문이 `SupportIdentityContext` 로 헤더·목록·홈·답변 말풍선에 내려준다.
- 가게는 가게 이름·대표 사진을 그대로 쓴다(읽기 전용) — 채팅에서 따로 바꾸면 "RESERVE 고객지원" 사칭이 가능해서다. 서버도 가게 요청의 표시 이름·사진을 버린다.
- 가게 문의도 고객지원처럼 첫 대화에는 항상 안내가 보인다(설정이 없으면 기본 안내).
