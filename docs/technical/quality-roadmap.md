# 품질 상태와 다음 작업

검증일: **2026-09-09**. 기준은 v2.5.1 운영 배포와 PR #196까지 머지된 `dev`다.
품질·정책 묶음은 Node 22 기준, 실행 가능한 ESLint 규칙, PR 감사 도구와 CI 단계를 포함한다.
GitHub 머지·검사 상태는 문구가 아니라 해당 PR과 현재 dev head에서 다시 확인한다.
코드·실행 결과·운영 증거를 현재 사실로 취급하고, 과거 대화와 프리뷰 문서는 변경 배경으로만 사용한다.

## 3. GitHub와 배포 관문

2026-09-09 GitHub API 읽기 전용 확인 결과:

- dev/main 모두 `build-backend`·`build-frontend`를 strict로 요구한다.
- dev/main 모두 관리자에게도 브랜치 보호를 적용한다. main은 선형 히스토리를 강제한다.
- production Environment는 `main` 브랜치만 허용한다.
- production Environment의 관리자 우회는 여전히 허용된다. 브랜치 관리자 강제와 다른 설정이다.
- GitHub Secret 값은 저장 후 다시 읽지 않는다. 로그·명령 인자·문서에 값을 노출하지 않는다.
- `chore`·`dependencies`·`feat` 라벨은 생성돼 있다. 기존 Dependabot PR에는 자동 소급 적용되지 않았다.

같은 날 PR 감사 스크립트로 확인한 열린 의존성 PR은 6개다. #184와 #162는 `build-frontend` 실패,
#110은 필수 build 체크가 없어서 준비되지 않았다. #168·#165·#164는 각 head의 필수 build가 성공했지만
현재 dev와 다시 결합한 결과가 아니며, 각각 Actions·백엔드 묶음·framer-motion 메이저 변경을 별도 검토해야 한다.
이 판정은 읽기 전용 상태 보고일 뿐 머지 승인이 아니다.

실패한 Actions 실행은 임의 삭제하지 않는다. 특히 `34319244608`은 서버 변경 전 SSH 지문 검증에서
멈췄고, 후속 성공 실행 `34336480904`와 함께 원인·영향·복구를 증명한다. 로그·artifact는 저장소의
retention 정책으로 만료되게 두고, 법적·보안상 삭제 사유가 생기면 별도 판단한다.

## 4. 다음 production 릴리스 전 필수 관문

1. 품질·정책 테스트와 전체 테스트가 현재 dev head의 Linux CI에서도 통과하는지 확인한다.
2. v2.6.0 범위와 CHANGELOG를 다시 검토한다. main PR·태그·릴리스·배포는 별도 승인 없이는 실행하지 않는다.
3. 배포 전에 추가 엔티티·필드가 `ddl-auto: update`로 만드는 범위를 확인한다. 삭제·타입·제약 변경은
   자동 반영되지 않으므로 [수동 DDL 런북](manual-ddl.md)을 따른다.
4. 배포 뒤 새 테이블·`checked_in_at`·인덱스·열린 대사/삭제 outbox를 읽기 전용으로 확인한다.
5. 실제 TEST PG 쓰기 승인을 받은 뒤에만 서명 PAID/취소 웹훅, 응답 유실, 중복 이벤트,
   두 동시 환불의 단일 PG 호출을 검증한다. 기존 호출 테스트용 `FAILED` 행도 자동 재처리하지 않는다.
6. 별도 검증 MySQL에서 광고 lease/폐업·제재 경합, 201건 이상 검색·count·LIKE 특수문자와
   FULLTEXT 쿼리 계획을 확인한다. 운영 DB 쓰기로 대체하지 않는다.

## 5. 후속 품질 작업

- 사업자 광고 관리는 현재 전건 `List`다. 예약의 100건 누락과 같은 버그는 아니지만 광고가 늘기 전에
  서버 검색·count·페이지 경계로 전환한다.
- 남은 빈 catch와 통신 실패를 빈 목록으로 보이는 화면을 조사한다. 조용한 폴링 일시 실패와
  사용자가 조치해야 하는 실패를 구분한다.
- CSP Report-Only는 실제 배포일로부터 최소 7일 관측하고, 공개/비공개 경로의 실제
  `X-Robots-Tag` 헤더를 확인한 뒤 강제 CSP 전환 여부를 결정한다.
- 이미지 최초 열기·닫기·뒤로가기와 예약 카드 동작을 일반 모션 PC/390px 실제 DOM으로 확인한다.
  reduced-motion smoke만으로 애니메이션을 증명하지 않는다.
- 큰 JS 청크와 전체 결과를 메모리에 올리는 거리순 검색은 import graph·실기 성능·EXPLAIN을 먼저 측정한다.
- 관리자 문의·사용자 채팅은 DB 영속화라 정상 배포만으로 내역이 지워져서는 안 된다. dev의 지연 응답
  격리와 v2.5.1 운영 데이터 보존은 별개이므로 다음 배포 후 읽기 전용 건수·화면 검증을 남긴다.
- 자동 로그인 지연은 PR #194에서 시작 인증 재시도와 계정 세대 격리를 보강했다. 운영 배포 뒤 실제
  쿠키 만료·새로고침·직접 진입·다른 탭 전환을 수동 확인한다.

## 6. 공개 사이트와 앱 분리 제안

장기적으로 `reserve.it.kr`은 브랜드·검색 유입·공개 가게/서비스 탐색에,
`app.reserve.it.kr`은 로그인·예약·결제·사업자·관리자 작업에 두는 방향이 적절하다.
호스트부터 나누지 않고 다음 순서로 진행한다.

1. 현재 호스트에서 검색 → 운영 배너/공지 → 서비스 도메인 → 추천 콘텐츠 구조를 디자인 시스템으로 검증한다.
2. 자유 문자열 `category`와 별도인 정규화 `ServiceDomain`을 설계한다. 탐색 분류와
   `SLOT`/`SESSION`/`DAY` 예약 방식을 섞지 않는다.
3. 오프라인 대기는 예약 상태가 아니라 번호표·호출·만료·재입장 규칙을 가진 별도 도메인으로 둔다.
4. 공개 URL 소유권·canonical·redirect 표를 먼저 정하고, 그 뒤 DNS·TLS·OAuth callback·쿠키/CORS·
   CSP·모니터링·배포 파이프라인을 한 번에 전환할 수 있는 롤백 계획을 만든다.

캐치테이블은 정보 구조만 참고하고 시각 스타일은 복제하지 않는다. RESERVE 토큰·공통 컴포넌트·포커스·
모션 규칙을 유지하며 PC 화면을 모바일 고정 폭으로 제한하지 않는다.

## 7. 보류한 인프라와 승인 경계

Lightsail 자동 스냅샷, 백업 전용 S3·버전 관리·라이프사이클, IAM 분리, cron 설치와 복원 훈련은
사용자 결정으로 보류 중이다. 보류는 완료나 불필요를 뜻하지 않는다.

운영 DB·PortOne·S3 쓰기, TEST 결제, 운영 롤백, v2.6.0 production 배포, 백업·IAM 변경은
각각 별도 승인 대상이다. 읽기 전용 점검도 결과 시점과 범위를 기록하며, 과거 증거를 현재 실행처럼 쓰지 않는다.
